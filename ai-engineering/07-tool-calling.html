Tool calling

Also called function calling. You describe capabilities, the model decides when to use them, your code executes them. This is the mechanism every agent is built on.

What actually happens

The model never calls anything It emits a structured request — "call get_weather with {"city": "Cluj"}" — and stops. Your code decides whether to run it, runs it, and sends the result back. Every security boundary lives on your side. Nothing executes that you did not execute. 
1. You send: messages + tool definitions
2. Model replies with stop_reason = "tool_use" and a tool_use block
3. You execute the function
4. You send back: history + assistant turn + a tool_result block
5. Model replies with the final answer (or another tool call — loop)

Defining tools

tools = [
    {
        "name": "search_orders",
        "description": (
            "Search a customer's orders. Use when the user asks about an order's "
            "status, contents, or delivery date. Returns at most 20 orders."
        ),
        "input_schema": {
            "type": "object",
            "properties": {
                "customer_id": {"type": "string", "description": "Internal customer id"},
                "status": {
                    "type": "string",
                    "enum": ["pending", "shipped", "delivered", "cancelled"],
                    "description": "Optional filter",
                },
                "since": {"type": "string", "description": "ISO date, only orders after this"},
            },
            "required": ["customer_id"],
            "additionalProperties": False,
        },
    },
]

The description is not documentation — it is the prompt that decides whether the tool gets used correctly. Say what the tool does, when to use it, what it returns, and any limits. Vague descriptions produce tools that are called at the wrong moment or not at all.

The loop, written out

import anthropic, json

client = anthropic.Anthropic()

def execute_tool(name: str, args: dict) -> str:
    if name == "search_orders":
        return json.dumps(db.search_orders(**args))
    if name == "cancel_order":
        return json.dumps(db.cancel_order(**args))
    raise ValueError(f"unknown tool {name}")

def run(user_input: str, max_iterations: int = 10) -> str:
    messages = [{"role": "user", "content": user_input}]

    for _ in range(max_iterations):
        response = client.messages.create(
            model="claude-opus-5",
            max_tokens=8000,
            system=SYSTEM_PROMPT,
            tools=tools,
            messages=messages,
        )

        if response.stop_reason != "tool_use":
            return "".join(b.text for b in response.content if b.type == "text")

        messages.append({"role": "assistant", "content": response.content})

        results = []
        for block in response.content:
            if block.type != "tool_use":
                continue
            try:
                output = execute_tool(block.name, block.input)
                results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,
                    "content": output,
                })
            except Exception as e:
                results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,
                    "content": f"Error: {e}",
                    "is_error": True,
                })

        messages.append({"role": "user", "content": results})

    raise RuntimeError("tool loop did not converge")

Five details that matter:

  • Append the whole response.content, not just the text — the tool_use blocks must be in the history or the results have nothing to attach to.
  • tool_use_id must match.
  • Return every result in one user message. Splitting parallel results across messages teaches the model to stop making parallel calls.
  • Report errors as results with is_error, do not drop them. The model can often recover — retry with a corrected argument, or explain the failure to the user.
  • Bound the loop. Always. An unbounded loop is an unbounded bill.

Or let the SDK drive it

from anthropic import beta_tool

@beta_tool
def search_orders(customer_id: str, status: str | None = None) -> str:
    """Search a customer's orders.

    Args:
        customer_id: Internal customer id.
        status: Optional status filter: pending, shipped, delivered or cancelled.
    """
    return json.dumps(db.search_orders(customer_id, status))

runner = client.beta.messages.tool_runner(
    model="claude-opus-5",
    max_tokens=8000,
    tools=[search_orders],
    messages=[{"role": "user", "content": user_input}],
)

for message in runner:
    ...   # each iteration is one turn; the runner executes tools for you

The schema is derived from the signature and docstring. Convenient — but write the manual loop once first, because when an agent misbehaves in production you will be debugging exactly those steps.

Designing a good tool surface

  • Few tools, clearly distinct. Twenty overlapping tools produce wrong choices. If two tools are easy to confuse, merge them or rename them.
  • Match the user's mental model, not your database. find_customer_orders beats select_from_orders_join_customers.
  • Return concise, structured results. Every byte a tool returns enters the context and is billed on every subsequent turn. Return the ten fields that matter, not the row.
  • Make results self-describing. {"orders": [], "note": "no orders found for this customer"} is far more useful than [].
  • Prefer idempotent tools, and make destructive ones require an explicit confirmation argument.
  • Do not expose a raw SQL tool to a model that talks to untrusted users. If you must, use a read-only role, a query timeout and a row limit.

Controlling when tools are used

tool_choice={"type": "auto"}                        # default: model decides
tool_choice={"type": "any"}                        # must call some tool
tool_choice={"type": "tool", "name": "search"}     # must call this one
tool_choice={"type": "none"}                       # answer without tools

Support for the forced variants differs by model and generation — some current models reject them and expect you to use auto plus an explicit instruction, or structured output when the forced call only existed to get JSON back. Check the reference for your model.

Parallel calls

One assistant turn can contain several tool_use blocks. Execute them concurrently when they are independent:

import asyncio

async def run_tools(blocks) -> list[dict]:
    async def one(block):
        output = await execute_tool_async(block.name, block.input)
        return {"type": "tool_result", "tool_use_id": block.id, "content": output}
    return await asyncio.gather(*(one(b) for b in blocks))

Then return them all in a single user message, as above.

Human approval

DANGEROUS = {"cancel_order", "issue_refund", "send_email", "delete_document"}

def execute_tool(name: str, args: dict, *, approved: set[str]) -> str:
    if name in DANGEROUS and name not in approved:
        return json.dumps({
            "status": "declined",
            "reason": "This action needs user confirmation. Ask the user to confirm, then retry.",
        })
    return _run(name, args)

Notice that the refusal is returned as a normal tool result. The model then asks the user rather than crashing or silently giving up. Gate by reversibility: reads are free, writes need thought, irreversible external actions (money, email, deletion) need explicit confirmation.

Server-side tools

Providers also offer tools that run on their infrastructure — web search, web fetch, code execution — that you declare and do not implement:

tools=[
    {"type": "web_search_20260209", "name": "web_search", "max_uses": 5},
]

Useful for current information and for sandboxed computation you do not want to host. The exact type strings are versioned and model-dependent; look them up rather than copying from a blog post. Note also that server-side tool failures typically come back as a normal response containing an error result, not as a raised exception — check the block, do not just wrap in try/except.

MCP, in one paragraph

The Model Context Protocol is a standard way to expose tools and data to models, so a capability written once (a GitHub server, a Postgres server, an internal API server) can be used by any MCP-aware client. Practically: instead of hand-writing a tool per integration, you connect to a server that already publishes them. Worth knowing because it is increasingly how tools are distributed; lesson 14 revisits it in the agent context.

Debugging tool use

SymptomCause and fix
The tool is never calledDescription too vague, or the system prompt does not mention that the capability exists. Say when to use it.
Called with wrong argumentsAdd descriptions and enums to the schema; set strict: True.
Called endlesslyResults are unhelpful or ambiguous, so the model retries. Improve the result payload; cap iterations.
Answers without using the toolIt thinks it already knows. Instruct it that the tool is the source of truth for that data.
SlowSerial calls; a chatty tool surface. Parallelise and consolidate.
ExpensiveTool results are too large — they are re-sent every turn.

Log every tool call and result with the message id. Ninety percent of agent debugging is reading that log and spotting the moment the model was given something confusing.

Practice
  1. Build three tools over a small SQLite database (search products, get order, check stock) and write the manual loop.
  2. Ask a question requiring two tools in sequence, and print the whole message history to see the loop.
  3. Make a tool fail on purpose and confirm the model recovers gracefully with is_error.
  4. Add a destructive tool with an approval gate, and verify the model asks before acting.
  5. Shrink a fat tool result to the fields that matter and compare the token usage of a five-turn conversation.
  6. Rewrite the same agent with the SDK tool runner and note what you gave up in visibility.
