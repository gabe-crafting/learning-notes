Vector stores

Where the vectors live, how nearest-neighbour search works at scale, and why the answer is often "just use Postgres".

What a vector database gives you

  • Approximate nearest-neighbour search — top-k similar vectors in milliseconds over millions of rows, without comparing against every one.
  • Metadata filters — "only documents this user may see, only from 2026, only type=contract".
  • Persistence and updates — insert, update and delete without rebuilding everything.
  • Operational basics — backups, replication, scaling.

Exact search compares your query against every vector: correct, and fine up to roughly tens of thousands of items. Beyond that you use an index that trades a small amount of recall for a very large amount of speed.

Indexes, briefly

Flat / brute forceCompare everything. Perfect recall, linear cost. Correct choice for small collections.
HNSWA navigable graph. The default in most engines: excellent recall/speed, higher memory, fast queries. Tunables: m, ef_construction (build), ef_search (query — higher means better recall, slower).
IVF / IVFFlatCluster the space, search only the nearest clusters. Cheaper to build, needs training data, tuned with lists and probes.
Quantisation (PQ, int8, binary)Compress vectors to cut memory, at some accuracy cost. Often combined with the above.

You do not need to implement these. You do need to know that approximate means approximate: if your retrieval is mysteriously missing an obviously relevant chunk, an aggressive index setting is one candidate explanation — test against a flat index to rule it in or out.

Start with pgvector unless you have a reason not to A separate vector database is another service to deploy, secure, back up and keep in sync with your source of truth — and keeping two stores consistent is a real, recurring source of bugs. Postgres with pgvector comfortably handles millions of vectors, and you get filtering, joins and transactions for free. Move to a dedicated engine when you have measured a reason.

pgvector, concretely

create extension if not exists vector;

create table documents (
    id          bigserial primary key,
    source      text        not null,
    title       text,
    created_at  timestamptz not null default now()
);

create table chunks (
    id           bigserial primary key,
    document_id  bigint      not null references documents (id) on delete cascade,
    ordinal      int         not null,
    content      text        not null,
    token_count  int         not null,
    metadata     jsonb       not null default '{}',
    embedding    vector(1024) not null,          -- must match your model's dimension
    created_at   timestamptz not null default now()
);

create index on chunks using hnsw (embedding vector_cosine_ops);
create index on chunks (document_id);
create index on chunks using gin (metadata jsonb_path_ops);
-- top 5 most similar chunks, filtered by tenant and recency
select c.id, c.content, d.title, d.source,
       1 - (c.embedding <=> $1) as similarity     -- <=> is cosine distance
from chunks c
join documents d on d.id = c.document_id
where c.metadata @> '{"tenant": "acme"}'
  and d.created_at > now() - interval '2 years'
order by c.embedding <=> $1                        -- distance ascending = most similar first
limit 5;

Operators: <=> cosine distance, <-> L2, <#> negative inner product. Use the one matching how your vectors were normalised, and make sure the index operator class matches the operator in your query — a mismatch silently falls back to a sequential scan.

import psycopg
from pgvector.psycopg import register_vector

conn = psycopg.connect(DSN)
register_vector(conn)

def search(query_vector, tenant: str, k: int = 5):
    with conn.cursor() as cur:
        cur.execute(
            """
            select c.id, c.content, d.title, d.source,
                   1 - (c.embedding <=> %s) as similarity
            from chunks c join documents d on d.id = c.document_id
            where c.metadata @> %s
            order by c.embedding <=> %s
            limit %s
            """,
            (query_vector, json.dumps({"tenant": tenant}), query_vector, k),
        )
        return cur.fetchall()

Chroma, for a five-minute prototype

import chromadb

client = chromadb.PersistentClient(path="./chroma")
collection = client.get_or_create_collection("docs", metadata={"hnsw:space": "cosine"})

collection.add(
    ids=[c.id for c in chunks],
    documents=[c.text for c in chunks],
    embeddings=[c.vector for c in chunks],
    metadatas=[{"source": c.source, "page": c.page} for c in chunks],
)

result = collection.query(
    query_embeddings=[query_vector],
    n_results=5,
    where={"source": "handbook.pdf"},
)

Perfect for learning and for tests. Do not build a multi-tenant production system on it without understanding its operational limits.

Metadata is not optional

Store enough alongside each vector to filter, cite and debug:

{
  "chunk_id": "doc42:7",
  "document_id": "doc42",
  "source": "employee-handbook-2026.pdf",
  "title": "Employee Handbook 2026",
  "url": "https://intranet/handbook.pdf#page=14",
  "page": 14,
  "section": "Leave policy",
  "tenant": "acme",
  "acl": ["hr", "all-staff"],
  "language": "en",
  "updated_at": "2026-03-02",
  "embedding_model": "bge-m3",
  "content_hash": "9f2a..."
}
  • ACL fields decide what a user may retrieve. Filter on them in the query, never after — "fetch then filter" leaks data and returns fewer results than requested.
  • Source, page and URL are what make citations possible (lesson 11).
  • Content hash lets you skip re-embedding unchanged chunks.
  • Embedding model lets you migrate models without guessing which rows are stale.
Multi-tenancy is a security boundary A missing tenant filter shows one customer another customer's documents. Put the filter in a single shared query function, never in each call site, and write a test that asserts a query for tenant A returns nothing belonging to tenant B.

Keeping the index in sync

for document in source_documents:
    stored = db.get_document(document.id)
    if stored and stored.content_hash == document.content_hash:
        continue                                   # unchanged, skip

    db.delete_chunks(document_id=document.id)      # replace atomically
    chunks = chunk(document)
    vectors = embed([c.text for c in chunks])
    db.insert_chunks(document.id, chunks, vectors)
    db.upsert_document(document)

Decide up front how updates and deletions reach the index. A knowledge base that answers from a deleted document, or from last quarter's price list, destroys trust faster than a wrong-but-honest "I do not know".

Performance notes

  • Insert in batches inside a transaction; commit per document, not per chunk.
  • Build the index after a large bulk load, not before.
  • Tune recall explicitly — in pgvector, set hnsw.ef_search = 100; raises recall at some latency cost.
  • Measure with explain analyze: if you see a sequential scan, your index is not being used.
  • Vectors are large. Do not select * when you only need ids, content and score.
Practice
  1. Run Postgres with pgvector in Docker, create the schema above, and insert 1,000 chunks.
  2. Query for the top 5 with and without an HNSW index, and compare timings with explain analyze.
  3. Add a tenant field, insert two tenants, and write a test proving one cannot retrieve the other's data.
  4. Build the same collection in Chroma and compare the developer experience.
  5. Implement content-hash-based incremental re-indexing and confirm unchanged documents are skipped.
  6. Delete a document and verify it disappears from search results immediately.
