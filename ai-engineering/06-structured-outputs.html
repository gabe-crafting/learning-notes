Structured outputs

Turning a text generator into a component your program can rely on. This is the single most useful technique in applied LLM work.

The problem

# asking nicely and hoping
prompt = "Extract the invoice total. Reply with JSON like {\"total\": 123.45}"

# what you get, across a few hundred calls:
{"total": 123.45}
```json\n{"total": 123.45}\n```
Sure! Here is the JSON you requested: {"total": 123.45}
{"total": "123.45 EUR"}
{"total": 123.45, "currency": "EUR"}      # a field you did not ask for

Every one of those variants breaks json.loads or your downstream code. Regex-and-pray parsing is the classic beginner solution, and it fails in production at exactly the rate that makes it annoying to debug.

The solution: constrain the output

Modern APIs let you specify a JSON Schema that the response must conform to. The provider enforces it during generation, so what comes back is valid by construction — not by luck.

With Pydantic (the ergonomic path)

from pydantic import BaseModel, Field
import anthropic

class Invoice(BaseModel):
    vendor: str
    invoice_number: str
    issue_date: str = Field(description="ISO date, YYYY-MM-DD")
    currency: str = Field(description="ISO 4217 code, e.g. EUR")
    total: float
    line_items: list[str]

client = anthropic.Anthropic()

response = client.messages.parse(
    model="claude-opus-5",
    max_tokens=4000,
    messages=[{"role": "user", "content": f"Extract the invoice data:\n\n{document_text}"}],
    output_format=Invoice,
)

invoice: Invoice = response.parsed_output    # already validated
print(invoice.total, invoice.currency)

Your class is the contract in both directions: it generates the schema sent to the model, and it validates what comes back. One definition, no drift.

With a raw JSON Schema

response = client.messages.create(
    model="claude-opus-5",
    max_tokens=4000,
    messages=[{"role": "user", "content": document_text}],
    output_config={
        "format": {
            "type": "json_schema",
            "schema": {
                "type": "object",
                "properties": {
                    "vendor":   {"type": "string"},
                    "total":    {"type": "number"},
                    "currency": {"type": "string"},
                },
                "required": ["vendor", "total", "currency"],
                "additionalProperties": False,
            },
        }
    },
)

import json
data = json.loads(next(b.text for b in response.content if b.type == "text"))

Use this when the schema is generated at runtime, or in a language without a Pydantic equivalent.

Designing a schema the model can fill in well

Schema design is prompt engineering. The field names and descriptions are instructions.

from enum import Enum
from pydantic import BaseModel, Field

class Category(str, Enum):
    BILLING = "billing"
    BUG = "bug"
    FEATURE_REQUEST = "feature_request"
    ACCOUNT = "account"
    OTHER = "other"

class TicketAnalysis(BaseModel):
    category: Category
    priority: int = Field(ge=1, le=4, description="1 = low, 4 = production outage")
    needs_human: bool = Field(description="True if angry, threatening to leave, or data loss")
    reason: str = Field(max_length=200, description="One sentence justifying the classification")
    mentioned_features: list[str] = Field(default_factory=list)
  • Enums beat free strings wherever the value set is known — no normalisation code, no "Billing"/"billing"/"BILLING".
  • Descriptions are read by the model. Use them to define what the field means; this is where the precision goes.
  • Name fields as their meaning — needs_human, not flag2.
  • Nullable is honest. Give the model a way to say "not present" (str | None) rather than forcing it to invent a value.
  • Keep it flat and small. Deeply nested schemas are harder to fill correctly and cost more tokens.

Ask for reasoning inside the schema

class Decision(BaseModel):
    evidence: list[str] = Field(description="Quotes from the source supporting the decision")
    reasoning: str = Field(description="Brief justification, written before deciding")
    approved: bool

Field order matters: fields are generated in order, so a reasoning field placed before the verdict lets the model work before it commits. It also gives you something to audit when the verdict is wrong.

The mechanisms are related — both are schema-constrained — and they compose: a tool call with strict: True guarantees the arguments validate against your schema.

tools=[{

        "properties": {
            "title":    {"type": "string"},
            "priority": {"type": "string", "enum": ["low", "medium", "high", "urgent"]},
        },
        "required": ["title", "priority"],
        "additionalProperties": False,
    },
}]

What schemas do not guarantee

Valid is not correct A schema guarantees the shape, never the truth. {"total": 999.99} is perfectly valid and may be the wrong number. Structured output eliminates parsing bugs; it does not eliminate hallucination. You still need grounding, validation and evaluation.

Business validation belongs in your code, after the parse:

def validate_invoice(invoice: Invoice, source_text: str) -> list[str]:
    problems = []
    if invoice.total <= 0:
        problems.append("total must be positive")
    if str(invoice.total) not in source_text.replace(",", "."):
        problems.append("total does not appear verbatim in the source")   # cheap anti-hallucination check
    if invoice.currency not in {"EUR", "USD", "RON", "GBP"}:
        problems.append(f"unexpected currency {invoice.currency}")
    return problems

Repair loops

When you cannot constrain generation — an older model, a provider without schema support, or business rules a schema cannot express — validate and retry with the error message attached:

from pydantic import ValidationError

def extract(text: str, attempts: int = 3) -> Invoice:
    messages = [{"role": "user", "content": PROMPT.format(text=text)}]

    for attempt in range(attempts):
        raw = call_model(messages)
        try:
            invoice = Invoice.model_validate_json(raw)
        except ValidationError as e:
            messages += [
                {"role": "assistant", "content": raw},
                {"role": "user", "content":
                    f"That response failed validation:\n{e}\nReturn corrected JSON only."},
            ]
            continue

        problems = validate_invoice(invoice, text)
        if not problems:
            return invoice
        messages += [
            {"role": "assistant", "content": raw},
            {"role": "user", "content": "Fix these problems and return JSON only:\n- " + "\n- ".join(problems)},
        ]

    raise ValueError(f"could not extract a valid invoice after {attempts} attempts")

Cap the attempts, log how often repairs happen, and treat a rising repair rate as a signal that the prompt or the schema needs work — not as a cost of doing business.

Batch extraction, concretely

import asyncio
from anthropic import AsyncAnthropic

client = AsyncAnthropic()
semaphore = asyncio.Semaphore(5)

async def extract_one(doc: str) -> Invoice | None:
    async with semaphore:
        try:
            response = await client.messages.parse(
                model="claude-sonnet-5",           # cheaper tier is often plenty for extraction
                max_tokens=2000,
                messages=[{"role": "user", "content": doc}],
                output_format=Invoice,
            )
            return response.parsed_output
        except Exception as e:
            log.warning("extraction failed: %s", e)
            return None

async def extract_all(docs: list[str]) -> list[Invoice]:
    results = await asyncio.gather(*(extract_one(d) for d in docs))
    return [r for r in results if r is not None]

Note the model choice: extraction into a tight schema is one of the tasks where a cheaper model usually holds up. Verify that claim on your data rather than trusting it.
