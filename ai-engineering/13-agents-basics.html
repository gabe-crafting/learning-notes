Agents: the loop

An agent is a loop where the model decides what to do next. That is the whole idea — and the reason they are powerful, expensive, and hard to make reliable.

Workflow versus agent

WORKFLOW — you decide the steps, in code
   classify(ticket) → retrieve(kb) → draft_reply() → validate() → send()
   Predictable cost and latency. Testable. Debuggable. Fails in known ways.

AGENT — the model decides the steps, in a loop
   goal → [think → choose tool → observe result] × N → answer
   Handles tasks you cannot enumerate in advance. Variable cost. Novel failures.
Most production "AI agents" are workflows And that is the correct choice. Use an agent when the sequence genuinely cannot be fixed ahead of time — research, debugging, open-ended data work. If you can draw the flowchart, write the flowchart. It will be cheaper, faster, and you will be able to test it.

The four questions before building one

  1. Complexity — is the task genuinely multi-step and impossible to specify in advance?
  2. Value — does the outcome justify higher cost and latency?
  3. Viability — is the model actually good at this kind of task today?
  4. Cost of error — can mistakes be caught and undone (tests, review, rollback)?

Any "no" and you should stay with a workflow.

ReAct: the pattern under almost every agent

Reason → Act → Observe, repeated. In modern APIs you do not prompt this pattern by hand; tool calling implements it, and the model's reasoning mode supplies the "reason" step.

User: "Which of our overdue invoices are from customers who churned last quarter?"

Thought:  I need overdue invoices first.
Action:   search_invoices(status="overdue")
Observe:  12 invoices, customer ids [...]
Thought:  Now I need churn status for those customers.
Action:   get_customers(ids=[...], fields=["churned_at"])
Observe:  4 churned in Q1
Thought:  I can answer now.
Answer:   4 of the 12 overdue invoices belong to churned customers: ...

The loop, with the controls that matter

import time, anthropic

client = anthropic.Anthropic()

class Budget:
    def __init__(self, max_iterations=12, max_tokens=200_000, max_seconds=120):
        self.max_iterations, self.max_tokens, self.max_seconds = max_iterations, max_tokens, max_seconds
        self.iterations, self.tokens, self.started = 0, 0, time.monotonic()

    def check(self) -> str | None:
        if self.iterations >= self.max_iterations:      return "iteration limit reached"
        if self.tokens >= self.max_tokens:              return "token budget exhausted"
        if time.monotonic() - self.started > self.max_seconds: return "time limit reached"
        return None


def run_agent(goal: str, tools, execute, budget: Budget | None = None) -> dict:
    budget = budget or Budget()
    messages = [{"role": "user", "content": goal}]
    trace = []

    while True:
        stop = budget.check()
        if stop:
            return {"status": "stopped", "reason": stop, "trace": trace}

        response = client.messages.create(
            model="claude-opus-5",
            max_tokens=8000,
            system=AGENT_SYSTEM,
            thinking={"type": "adaptive"},
            output_config={"effort": "high"},
            tools=tools,
            messages=messages,
        )
        budget.iterations += 1
        budget.tokens += response.usage.input_tokens + response.usage.output_tokens

        if response.stop_reason != "tool_use":
            text = "".join(b.text for b in response.content if b.type == "text")
            return {"status": "done", "answer": text, "trace": trace,
                    "iterations": budget.iterations, "tokens": budget.tokens}

        messages.append({"role": "assistant", "content": response.content})

        results = []
        for block in response.content:
            if block.type != "tool_use":
                continue
            started = time.monotonic()
            try:
                output = execute(block.name, block.input)
                is_error = False
            except Exception as e:
                output, is_error = f"Error: {e}", True
            trace.append({
                "tool": block.name, "input": block.input,
                "ok": not is_error, "ms": int((time.monotonic() - started) * 1000),
                "output_preview": str(output)[:200],
            })
            results.append({"type": "tool_result", "tool_use_id": block.id,
                            "content": str(output), "is_error": is_error})

        messages.append({"role": "user", "content": results})

Everything that makes this production code rather than a demo is in the non-model parts: budgets, a trace, error results instead of exceptions, and a structured return that says why it stopped.

The agent's system prompt

AGENT_SYSTEM = """You are an operations assistant for a B2B SaaS company.

Goal: answer the user's question using the tools available. Work in steps.

Guidance:
- Use tools to obtain facts. Never state a figure you did not retrieve.
- Search before you conclude; if a result is empty, try a different query once,
  then report that you found nothing.
- Prefer one broad query over many narrow ones.
- Before any action that writes data or contacts a customer, state what you are
  about to do and wait for confirmation.
- When you have enough information, stop and answer. Do not keep exploring.
- If you cannot complete the task, say what you tried and what is blocking you.

Answer format: a short direct answer first, then the supporting detail.
"""

Agents fail in two directions: stopping too early with a half-answer, and never stopping. Both are addressed here — an explicit stop condition, and an explicit instruction to report failure rather than loop.

Stopping conditions

NaturalThe model answers without calling a tool. The normal case.
Iteration capHard limit. Always present.
Token / cost budgetStop before the bill surprises you. Some APIs also accept an advisory task budget so the model paces itself.
Wall clockEspecially behind an HTTP request.
Explicit finish toolA submit_answer(answer, confidence) tool makes completion structured and unambiguous.
Repetition detectorSame tool, same arguments, three times → break the loop; the agent is stuck.

Designing tools for agents

Everything from lesson 7 applies, with extra emphasis because an agent uses tools unsupervised:

  • Errors must be instructive. "Error: unknown field 'customer'. Valid fields: customer_id, status, total." lets the model recover; "Error: 400" does not.
  • Results must be compact. They are resent on every subsequent turn — a fat result is a recurring tax.
  • Prefer few, powerful tools. A general search(entity, filters) often beats fifteen specific ones.
  • Gate writes. Reads are free; anything irreversible needs confirmation.
  • Make tools idempotent where you can — agents retry.

Managing the agent's context

A long run fills the window with tool results, most of which stop being relevant. Options, roughly in order of how often you need them:

  • Return less from tools in the first place.
  • Summarise or drop old tool results — some APIs offer server-side context editing that clears stale results, or compaction that summarises earlier turns.
  • Write to scratch storage: the agent saves findings to a file or a note tool and reads them back on demand instead of carrying everything in context.
  • Delegate a reading-heavy subtask to a subagent whose context you throw away, keeping only its conclusion (lesson 14).

Observability is not optional here

A single agent run may make twenty model calls and forty tool calls. Without a trace you cannot debug it at all. Log, per step: the model call id, the reasoning summary if available, the tool name and arguments, the result size and duration, and the running token count. Lesson 17 turns this into proper tracing.

Typical failure modes

FailureFix
Loops on the same toolBetter tool results, repetition detector, iteration cap
Stops with a partial answerAsk it to verify completeness before answering; add a submit_answer tool with required fields
Invents data instead of calling a toolState in the system prompt that tools are the only source of truth; check the trace for claims with no supporting call
Runs up a huge billBudgets; a cheaper model for routine steps; fewer, larger tool calls
Takes a destructive actionApproval gates on writes; a dry-run mode; make it explain before acting
Unreproducible bugStore the full trace with every run so you can replay it

Evaluating agents

Harder than evaluating a single call, because there are many valid paths to a correct answer. Measure:

  • Task success rate on a fixed set of goals with known outcomes — the headline number.
  • Steps and cost per task — quality that costs three times as much is a trade, not a win.
  • Tool-call correctness — did it use the right tool with sane arguments?
  • Recovery rate — when a tool failed, did it adapt?

Build the harness before you tune the prompt; otherwise you will be adjusting wording based on one anecdote at a time. Lesson 16 covers how.

Practice
  1. Build an agent over three tools (search the web or a local corpus, read a file, do arithmetic) with iteration, token and time budgets.
  2. Give it a task needing at least three steps, and print the full trace. Read it and check every claim in the answer against a tool result.
  3. Break a tool deliberately and observe whether the agent recovers or spirals. Improve the error message until it recovers.
  4. Add a repetition detector and force it to trigger.
  5. Take the same task and implement it as a fixed workflow. Compare cost, latency and reliability over ten runs — and decide honestly which you would ship.
  6. Add an approval gate on a write tool and confirm nothing destructive happens without confirmation.
