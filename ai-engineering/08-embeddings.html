Embeddings and similarity

How text becomes numbers, and how those numbers let you search by meaning instead of by keyword. This is the foundation under every RAG system.

The idea

An embedding model maps a piece of text to a fixed-length vector of floats — typically a few hundred to a few thousand dimensions. Texts with similar meaning land near each other in that space.

"How do I reset my password?"   → [0.021, -0.113, 0.087, ...]   (1536 numbers)
"I forgot my login details"      → [0.019, -0.108, 0.091, ...]   ← close
"What is your refund policy?"    → [-0.204, 0.077, -0.014, ...]  ← far

Note that the two close sentences share no significant words. That is the entire point: keyword search cannot connect "reset my password" to "forgot my login details"; embeddings can.

Measuring similarity

The standard measure is cosine similarity — the angle between two vectors, ignoring their length. It ranges from −1 to 1; for text embeddings you will almost always see values between roughly 0 and 1.

import numpy as np

def cosine(a: np.ndarray, b: np.ndarray) -> float:
    return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))

# most providers return normalised vectors (length 1), in which case
# cosine similarity is just the dot product — cheaper:
def cosine_normalised(a, b) -> float:
    return float(np.dot(a, b))
Absolute scores are not meaningful "0.82" does not mean "82% relevant". Score distributions differ per model and per corpus — one model may put all real matches above 0.8, another around 0.4. Use scores to rank, and if you need a cutoff, calibrate it on your own data rather than copying a threshold from a tutorial.

Generating embeddings

Embeddings come from dedicated models, not from the chat model. Anthropic does not serve an embeddings endpoint — for Claude-based stacks the common choices are Voyage AI (Anthropic's recommended partner), OpenAI's embedding models, Cohere, or an open model you run yourself. The API shape is the same everywhere: text in, vectors out.

# open model, running locally — no API key, no per-token cost
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("BAAI/bge-m3")          # strong multilingual option
vectors = model.encode(
    ["How do I reset my password?", "I forgot my login details"],
    normalize_embeddings=True,
)
print(vectors.shape)            # (2, 1024)
# hosted API — the shape you will meet at every provider
vectors = [item.embedding for item in provider.embeddings.create(
    model="<embedding-model-id>",
    input=[chunk.text for chunk in batch],
).data]

Hosted models are simpler to operate and usually stronger; local models are free per call, keep data on your machines, and make bulk re-indexing painless. Embedding is cheap either way — orders of magnitude cheaper per token than generation.

Choosing an embedding model

CriterionWhat to look at
Retrieval qualityMTEB leaderboard as a starting point, then test on your data — public benchmarks correlate loosely with your corpus
LanguageMany strong models are English-first. For Romanian, or any mixed-language corpus, pick an explicitly multilingual model
Max input lengthTypically 512–8192 tokens. Text beyond it is truncated silently, which quietly ruins retrieval
Dimensions384–3072. Bigger is marginally better and linearly more expensive to store and search
DomainCode, legal and medical text benefit from models trained for them
Cost and hostingAPI per-token, or your own GPU/CPU time
Changing the embedding model means re-embedding everything Vectors from different models are not comparable — not even different sizes of the same family. Swapping models is a full re-index of your corpus. Choose deliberately, and record which model produced each vector so you can migrate later.

Symmetric versus asymmetric search

A short question and a long document chunk are different kinds of text. Many embedding models are trained for this asymmetry and expect a prefix telling them which side they are embedding:

# typical of instruction-tuned embedding models — check YOUR model's docs
query_vector = model.encode("query: how do I reset my password")
doc_vector   = model.encode("passage: To reset your password, open Settings ...")

Forgetting the prefixes, or applying them inconsistently between indexing and querying, degrades retrieval in a way that is very hard to spot afterwards. Read the model card.

A minimal semantic search, end to end

import numpy as np
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("BAAI/bge-m3")

documents = [
    "To reset your password, open Settings and choose Security.",
    "Refunds are issued within 14 days of purchase.",
    "Our office is open Monday to Friday, 9:00 to 17:00.",
    "Two-factor authentication can be enabled from your profile page.",
]

index = model.encode(documents, normalize_embeddings=True)   # (4, 1024)

def search(query: str, k: int = 2) -> list[tuple[float, str]]:
    q = model.encode([query], normalize_embeddings=True)[0]
    scores = index @ q                       # dot product against every document
    top = np.argsort(-scores)[:k]
    return [(float(scores[i]), documents[i]) for i in top]

for score, text in search("I can't log in"):
    print(f"{score:.3f}  {text}")

That is genuinely all semantic search is. The next lesson replaces the in-memory matrix with a database that can do this over millions of vectors with filters and persistence.

What embeddings are bad at

  • Exact identifiers. Invoice number "INV-2024-0917", an error code, a product SKU — keyword search wins decisively. This is the main argument for hybrid search (lesson 12).
  • Negation. "Contracts that are not expired" embeds close to "expired contracts".
  • Numeric and date constraints. "Orders over €500 last month" is a filter, not a similarity — push it to metadata.
  • Long documents as a single vector. One embedding cannot represent twenty pages; averaging meaning across a long text produces something that matches nothing well. Hence chunking (lesson 10).
  • Freshness and authority. Similarity has no idea which document is newer or more official.

Other uses beyond RAG

  • Deduplication — near-identical support tickets, duplicate listings.
  • Clustering — group thousands of feedback items into themes without labels.
  • Classification — embed labelled examples, classify by nearest neighbours; extremely cheap compared with an LLM call per item.
  • Recommendation — "more like this".
  • Semantic caching — if a new question is very close to one you answered recently, reuse the answer (lesson 17).
  • Routing — send a query to the right index or the right prompt.

Storage adds up: one million chunks at 1024 dimensions in float32 is about 4 GB before indexes. Quantisation (float16, int8, or binary) trades a little accuracy for a lot of memory, and most vector databases support it.

Practice
  1. Embed ten sentences on two topics, compute the full similarity matrix, and print it. Confirm the clusters are visible in the numbers.
  2. Find a pair of sentences that mean the opposite but score as highly similar. Explain why.
  3. Compare an English-only and a multilingual model on Romanian text. Which retrieves your intended answer?
  4. Build the in-memory search above over 50 paragraphs from a document you know well, and inspect its top-3 for ten questions. Note every case where it failed and why.
  5. Search for an exact identifier (an order number) and watch semantic search do badly. Keep this example for lesson 12.
  6. Measure how long it takes to embed 1,000 chunks, and estimate the cost or the compute for one million.
