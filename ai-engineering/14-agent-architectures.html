Agent architectures and memory

Patterns beyond the single loop: planning, delegation, memory across sessions, and the protocols that let agents reach the outside world.

Patterns worth knowing

Prompt chaining

outline = model(f"Write an outline for: {topic}")
draft   = model(f"Write the article from this outline:\n{outline}")
final   = model(f"Tighten this draft to 600 words:\n{draft}")

Not an agent at all — a pipeline. Each step is simpler and testable in isolation. Reach for this first.

Routing

class Route(BaseModel):
    destination: Literal["billing", "technical", "sales", "other"]
    confidence: float

route = classify(question, output_format=Route)      # cheap model
handler = HANDLERS[route.destination]                 # different prompt, tools, maybe model
return handler(question)

One cheap call chooses the specialist. Cheaper and more reliable than one giant prompt that tries to be all things, and each branch can be evaluated separately.

Plan and execute

class Step(BaseModel):
    id: int
    description: str
    tool: str
    depends_on: list[int] = []

class Plan(BaseModel):
    steps: list[Step]

plan = model.parse(goal, output_format=Plan)          # plan once, explicitly
for step in topological_order(plan.steps):
    results[step.id] = execute(step, results)         # execute deterministically

Advantages over a free-running loop: the plan is inspectable before anything runs, you can show it to a user for approval, independent steps can run in parallel, and a failed step can be retried without redoing the rest. The cost is rigidity — the plan is made before the agent has seen any results, so allow re-planning when a step surprises it.

Evaluator–optimiser

draft = generate(task)
for _ in range(3):
    critique = evaluate(draft, criteria)              # a second call, often a stronger model
    if critique.acceptable:
        break
    draft = revise(draft, critique.feedback)

Works well where quality is judgeable and iteration is cheap: writing, code, translations. Cap the loop, and make the evaluator's criteria explicit rather than "is this good".

Orchestrator and subagents

main agent (goal, keeps the plan and the summary)
├── researcher subagent  → reads 30 pages, returns 200 words
├── analyst subagent     → crunches the numbers, returns a table
└── writer subagent      → composes the final answer

The real motivation is context, not "specialisation": a subagent reads a great deal and returns only its conclusion, so the orchestrator's window stays clean. Use a cheaper model for reading-heavy subagents. The costs are latency, complexity and the fact that a subagent cannot ask a clarifying question — its brief must be complete.

Reflection

"Before answering, list what you might have missed. Then answer."

Cheap, sometimes helpful, and largely subsumed by models with built-in reasoning. Measure rather than assume.

Memory

The API is stateless; every kind of "memory" is something you build. Four levels, with different mechanisms:

LevelScopeImplementation
Working memoryThis turnThe message list itself
Conversation memoryThis sessionFull history, or last-N plus a rolling summary, or server-side compaction
Long-term memoryAcross sessionsFacts stored in a database, retrieved and injected into the prompt
KnowledgeOrganisationalRAG over your documents (lessons 8–12)

Conversation memory that does not grow forever

MAX_RECENT = 10

def build_messages(history: list[dict], summary: str | None) -> list[dict]:
    recent = history[-MAX_RECENT:]
    if not summary:
        return recent
    return [{"role": "user", "content": f"<conversation_summary>{summary}</conversation_summary>"}] + recent

def maybe_summarise(history: list[dict], summary: str | None) -> str | None:
    if len(history) <= MAX_RECENT * 2:
        return summary
    older = history[:-MAX_RECENT]
    return cheap_model(
        "Summarise this conversation in under 200 words. Keep decisions, facts, "
        "names, numbers and open questions. Drop pleasantries.\n\n"
        + render(older) + (f"\n\nPrevious summary:\n{summary}" if summary else "")
    )

Note what the summary prompt is told to keep. A summary that loses the customer's order number has cost you the conversation.

Long-term memory

class MemoryItem(BaseModel):
    kind: Literal["preference", "fact", "decision"]
    text: str
    confidence: float

# after a session, extract durable facts
items = model.parse(transcript, output_format=list[MemoryItem])
for item in items:
    if item.confidence >= 0.7:
        store.upsert_memory(user_id, item)          # dedupe against existing memories

# at the start of the next session, retrieve the relevant ones
memories = store.search_memories(user_id, embed_query(current_topic), k=5)
system = BASE_SYSTEM + "\n\nKnown about this user:\n" + "\n".join(f"- {m.text}" for m in memories)
Memory is a privacy and correctness liability You are storing statements about people, extracted by a model that sometimes gets things wrong. Show users what is remembered, let them delete it, expire stale entries, never store sensitive categories you do not need, and keep it scoped per user — leaking one user's remembered facts into another's session is a serious incident.

Some APIs offer a memory tool where the model reads and writes files in a memory directory that you back with real storage; that is the same idea with the retrieval decision handed to the model.

MCP: connecting agents to the world

The Model Context Protocol standardises how tools and data sources are exposed to models. A server publishes tools (and resources and prompts); any MCP-aware client can use them. Instead of writing a bespoke integration per system, you connect to a server — for GitHub, Postgres, Slack, your own internal API — and its tools appear.

# conceptually
client connects to MCP server → lists tools → passes them to the model as tool definitions
model calls a tool → client forwards to the server → result returns

# in practice, either:
#  - your SDK converts MCP tools into API tool definitions, or
#  - the API connects to a remote MCP server directly (provider-specific parameters)

Why it matters to you: it is becoming the default distribution format for agent capabilities, and "have you used MCP" is now a live interview question. The security caveat is the important part — an MCP server is code you are trusting with your tool surface, and a malicious or compromised one can inject instructions into your agent's context. Treat third-party servers like third-party dependencies with network access.

Human in the loop

class PendingAction(BaseModel):
    tool: str
    arguments: dict
    rationale: str
    reversible: bool

# 1. agent proposes  → 2. persist and notify  → 3. human approves/edits/rejects  → 4. resume

Design decisions worth making explicitly: which actions require approval (start with everything irreversible), what the human sees (the rationale and the exact arguments, not a summary), what happens on timeout (default to not acting), and how the run resumes — which means the agent state must be persistable, not just an in-memory list.

Multi-agent systems: read this before building one

Multi-agent architectures are fashionable and frequently a mistake. They multiply cost by the number of agents, introduce coordination failures that are miserable to debug, and often produce worse results than one well-prompted agent with good tools — because each hand-off loses information.

Justified when: subtasks are genuinely independent and parallelisable; a subtask reads far more than the main agent should carry; or different subtasks need genuinely different tools, permissions or models. Otherwise, one agent.

Reliability techniques

  • Checkpoint state after every step so a crash or an approval pause can resume rather than restart.
  • Make tool calls idempotent with client-supplied keys, so a retry cannot double-charge anyone.
  • Dry-run mode that logs actions without performing them — invaluable for testing and for demos.
  • Circuit breakers on external tools; degrade gracefully rather than looping on a dead dependency.
  • Timeouts everywhere, including on the whole run.
  • Store the full trace of every run. It is your debugger, your eval data and your audit trail.

Choosing an architecture

If the task…Use
Has fixed known stepsA pipeline (chaining)
Splits into a few known kindsRouting
Is decomposable up frontPlan and execute
Has judgeable qualityEvaluator–optimiser
Requires open-ended explorationA single agent loop
Needs heavy independent readingOrchestrator with subagents
Touches money, customers or dataAny of the above, plus human approval
Practice
  1. Implement routing: a cheap classifier picking between three specialised handlers, each with its own prompt and tools.
  2. Implement plan-and-execute for a research task, and print the plan before running it.
  3. Add conversation summarisation and prove a 30-turn conversation stays under a token budget without losing key facts.
  4. Build long-term memory: extract facts after a session, retrieve them in the next one, and add a "forget" command.
  5. Connect to one public MCP server and use its tools from your agent.
  6. Add human approval to a destructive action, including persistence so the run survives a restart while waiting.
