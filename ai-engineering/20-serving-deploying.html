Serving and deploying

Turning your pipeline into a service: an API, streaming to the browser, background jobs, containers and the operational details that AI workloads add to ordinary backend work.

A FastAPI service

from fastapi import FastAPI, Depends, HTTPException
from fastapi.responses import StreamingResponse
from pydantic import BaseModel, Field

app = FastAPI(title="Docs Assistant")

class AskRequest(BaseModel):
    question: str = Field(min_length=3, max_length=2000)
    conversation_id: str | None = None

class SourceOut(BaseModel):
    id: int
    title: str
    url: str | None
    page: int | None

class AskResponse(BaseModel):
    answer: str
    sources: list[SourceOut]
    conversation_id: str

@app.post("/api/ask", response_model=AskResponse)
async def ask(request: AskRequest, user=Depends(current_user)) -> AskResponse:
    if not rate_limiter.allow(user.id):
        raise HTTPException(429, "Too many requests")
    result = await pipeline.answer(request.question, user=user)
    return AskResponse(**result)

@app.get("/health")
def health():
    return {"status": "ok"}

Nothing here is AI-specific except the pipeline call. Validation at the edge, auth as a dependency, rate limiting, a health endpoint — the same service design you would write for anything else.

Streaming to the browser

Server-sent events are the simplest transport: one-directional, plain HTTP, reconnects for free. Use WebSockets only if you need the client to talk back mid-stream.

import json
from anthropic import AsyncAnthropic

client = AsyncAnthropic()

@app.post("/api/ask/stream")
async def ask_stream(request: AskRequest, user=Depends(current_user)):

    async def events():
        sources = await retrieve(request.question, user=user)
        # send sources first so the UI can render citations while text arrives
        yield f"event: sources\ndata: {json.dumps([s.dict() for s in sources])}\n\n"

        try:
            async with client.messages.stream(
                model="claude-opus-5",
                max_tokens=2000,
                system=SYSTEM,
                messages=build_messages(request.question, sources),
            ) as stream:
                async for text in stream.text_stream:
                    yield f"event: token\ndata: {json.dumps({'text': text})}\n\n"

                final = await stream.get_final_message()
                usage = {"input": final.usage.input_tokens, "output": final.usage.output_tokens}
                yield f"event: done\ndata: {json.dumps({'usage': usage})}\n\n"
        except Exception as e:
            log.exception("stream failed")
            yield f"event: error\ndata: {json.dumps({'message': 'Generation failed'})}\n\n"

    return StreamingResponse(
        events(),
        media_type="text/event-stream",
        headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"},
    )
// browser

Proxies buffer streams nginx, some load balancers and some CDNs will happily collect your entire stream and deliver it in one lump, silently undoing the feature. Disable buffering for the streaming route (proxy_buffering off, X-Accel-Buffering: no) and verify in the deployed environment, not just locally.

If your frontend is TypeScript, the Vercel AI SDK handles this transport plus React hooks for streamed messages and tool calls — worth using rather than hand-rolling, especially if the UI is the part you enjoy.

Long-running work belongs in a queue

@app.post("/api/documents", status_code=202)
async def upload(file: UploadFile, user=Depends(current_user)):
    document_id = await storage.save(file, tenant=user.tenant)
    await queue.enqueue("ingest_document", document_id=document_id)   # returns immediately
    return {"document_id": document_id, "status": "processing"}

@app.get("/api/documents/{document_id}")
async def status(document_id: str):
    return await jobs.status(document_id)     # queued | processing | ready | failed

Ingestion, batch extraction and multi-minute agent runs must not sit inside an HTTP request — they blow past timeouts and they retry badly. Use Celery, RQ, Arq, or your cloud's queue; report progress through a status endpoint or a websocket.

Persisting conversations

create table conversations (
    id          uuid primary key,
    user_id     text not null,
    tenant      text not null,
    title       text,
    summary     text,
    created_at  timestamptz not null default now()
);

create table messages (
    id               bigserial primary key,
    conversation_id  uuid not null references conversations (id) on delete cascade,
    role             text not null,
    content          jsonb not null,        -- content blocks, not a plain string
    model            text,
    input_tokens     int,
    output_tokens    int,
    cost_usd         numeric(10,6),
    trace_id         text,
    created_at       timestamptz not null default now()
);
create index on messages (conversation_id, created_at);

Store content as blocks rather than a flattened string: tool calls and reasoning blocks have to be replayed verbatim to continue a conversation, and flattening them loses the ability to resume. Keeping tokens, cost and trace id per message is what makes lesson 17's queries possible.

Containerising

FROM python:3.12-slim AS base
ENV PYTHONUNBUFFERED=1 PIP_NO_CACHE_DIR=1
WORKDIR /app

COPY pyproject.toml uv.lock ./
RUN pip install uv && uv sync --frozen --no-dev

COPY src/ src/

RUN useradd --create-home app
USER app

EXPOSE 8000
HEALTHCHECK CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8000/health')"
CMD ["uv", "run", "uvicorn", "app.api:app", "--host", "0.0.0.0", "--port", "8000"]
services:
  api:
    build: .
    environment:
      ANTHROPIC_API_KEY: ${ANTHROPIC_API_KEY}
      DATABASE_URL: postgresql://app:app@db:5432/app
    depends_on: [db, redis]
    ports: ["8000:8000"]

  worker:
    build: .
    command: uv run arq app.jobs.WorkerSettings
    environment:
      ANTHROPIC_API_KEY: ${ANTHROPIC_API_KEY}
      DATABASE_URL: postgresql://app:app@db:5432/app
    depends_on: [db, redis]

  db:
    image: pgvector/pgvector:pg16
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app
      POSTGRES_DB: app
    volumes: ["pgdata:/var/lib/postgresql/data"]

  redis:
    image: redis:7

volumes: { pgdata: {} }

Note that the API and the worker are the same image with a different command — the standard shape, and it keeps dependencies identical between them.

Configuration and secrets

from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    anthropic_api_key: str
    database_url: str
    model_default: str = "claude-opus-5"
    model_cheap: str = "claude-haiku-4-5"
    max_cost_per_request: float = 0.50
    embedding_model: str = "BAAI/bge-m3"
    log_prompts: bool = False

    class Config:
        env_file = ".env"

settings = Settings()      # fails loudly at startup if a required value is missing

Keys come from the environment, injected by the platform. Never in the image, never in git. If one leaks, rotate it — deleting the commit is not enough.

Scaling shape

  • Your service is I/O bound, waiting on the model. Async workers handle high concurrency on modest hardware — this is not a CPU problem.
  • The provider's rate limit is your real ceiling. Ten instances share one account limit; scaling out does not raise it. Queue and shed load rather than hammering.
  • Deploy where it makes sense. A container platform (Cloud Run, Fly, Render, Railway, ECS, Kubernetes) is fine. Serverless functions fit awkwardly with streaming and long runs — check the timeout and streaming support before committing.
  • Keep model calls out of the request path whenever the user is not waiting on them.

Pre-launch checklist

Auth on every endpoint; rate limits per user
Input size caps; max_tokens caps; agent iteration and cost budgets
Retrieval filtered by permissions, with a test proving it
Timeouts and retries on every provider call; graceful degradation when it fails
Structured logging with tokens, cost, latency and trace ids
Alerts on error rate, p95 latency and daily spend
Eval suite passing, with the numbers recorded
Adversarial suite passing (lesson 18)
Secrets from the environment; nothing sensitive in logs
Migrations for the database; a documented way to re-index the corpus
A kill switch, and a rollback plan
A README a stranger can follow to run it

After launch

  • Read real conversations weekly. Nothing else tells you as much.
  • Feed failures into the eval set; that is how the system improves over months.
  • Watch cost daily for the first weeks — usage patterns will surprise you.
  • Pin model versions where the provider allows it, test upgrades against your evals, then move deliberately.
  • Re-read your prompts when you change models (lesson 5).
Practice
  1. Wrap your RAG pipeline in FastAPI with validation, auth and rate limiting.
  2. Add a streaming endpoint and a minimal HTML page that renders tokens as they arrive, with citations shown first.
  3. Move ingestion into a background worker with a status endpoint.
  4. Persist conversations, and prove you can resume one after a restart.
  5. Containerise the whole thing with Docker Compose, including Postgres with pgvector.
  6. Deploy it somewhere with a public URL and hit the health endpoint from your phone.
  7. Walk the pre-launch checklist and fix every row you cannot honestly tick.
