Evaluation and testing

How you know whether a change made things better. This is the skill that separates people who ship AI features from people who demo them — and the one most courses skip.

Why the usual testing does not work

assert answer == "The leave policy allows 25 days per year."   # fails on any rewording

Outputs vary, several answers can be correct, and quality is a spectrum rather than a boolean. So you move from "does this pass" to "what fraction of a representative set is acceptable, and is that fraction going up".

Without an eval set you are not engineering Changing a prompt, checking one example and shipping is how systems silently regress. The change that fixed your example may have broken twenty others; you will find out from users. An eval set is the difference between improving a system and stirring it.

Build the dataset first

Start at 30–50 cases. That is enough to see real movement and small enough to build in an afternoon.

Where the cases come from, in order of value:

  1. Real user questions from logs — the only truly representative source.
  2. Every bug you have fixed — a regression suite you get for free.
  3. Edge cases you know are hard — ambiguity, missing data, multiple documents, adversarial input.
  4. Out-of-scope questions where the correct answer is a refusal. Systems that never refuse are systems that hallucinate.
  5. Synthetic cases generated from your documents — useful for volume, weakest for realism.

Split the set: iterate on a training portion, and hold out a test portion you only look at occasionally. Otherwise you will tune until you fit your own 50 examples and learn nothing about the fifty-first.

Grading: pick the cheapest method that works

MethodUse forNotes
Exact / enum matchClassification, routing, extraction fieldsFree, deterministic, unambiguous. Use it wherever the task allows.
Programmatic checks"Contains 25", "cites source X", valid JSON, under 200 wordsCheap and reliable; covers more than people expect.
Retrieval metricsRAG pipelinesrecall@k, MRR (lesson 12). Measure retrieval separately from generation — always.
LLM as judgeOpen-ended quality, faithfulness, tonePowerful, imperfect; must itself be validated against human labels.
Human reviewThe ground truthExpensive. Use it to calibrate the judge, and for the final call before a launch.

An LLM judge with a usable output

from pydantic import BaseModel, Field
from typing import Literal

class Judgement(BaseModel):
    reasoning: str = Field(description="Brief comparison, written before the verdict")
    verdict: Literal["correct", "partially_correct", "incorrect", "refused"]
    faithful: bool = Field(description="Every claim is supported by the provided sources")
    score: int = Field(ge=1, le=5)

JUDGE = """You grade answers from a document question-answering system.

Compare the answer with the reference answer and the sources.
- correct: the same facts, wording may differ
- partially_correct: right but incomplete, or contains one minor error
- incorrect: wrong, or contradicts the reference
- refused: the system said it could not find the answer

faithful = every factual claim in the answer appears in the sources.
An answer can be faithful and still incorrect (correct quoting of the wrong source).
Be strict. An answer that adds unsupported detail is not faithful."""

def judge(case, answer: str, sources: list[str]) -> Judgement:
    return client.messages.parse(
        model="claude-opus-5",              # judge with a strong model
        max_tokens=2000,
        system=JUDGE,
        messages=[{"role": "user", "content":
            f"<question>{case['question']}</question>\n"
            f"<reference>{case['expected']}</reference>\n"
            f"<sources>{chr(10).join(sources)}</sources>\n"
            f"<answer>{answer}</answer>"}],
        output_format=Judgement,
    ).parsed_output

Judge design rules: reasoning field before the verdict; a small discrete scale rather than "score out of 100"; explicit criteria for each label; and one dimension per judgement — correctness and tone should not share a score.

Validate the judge before you trust it Grade 30 cases by hand, run the judge on the same 30, and measure agreement. Below ~80% agreement, fix the judge prompt before using it to make decisions. Also watch for known biases: judges favour longer answers, and favour answers written in a style similar to their own.

The runner

import json, time, statistics
from pathlib import Path

def run_eval(name: str, pipeline, dataset_path="evals/dataset.jsonl") -> dict:
    cases = [json.loads(line) for line in Path(dataset_path).read_text(encoding="utf-8").splitlines()]
    results, started = [], time.time()

    for case in cases:
        t0 = time.perf_counter()
        out = pipeline(case["question"])
        latency_ms = (time.perf_counter() - t0) * 1000

        checks = {
            "includes": all(s.lower() in out["answer"].lower() for s in case.get("must_include", [])),
            "cited": bool(out["sources"]) or not case.get("must_cite"),
        }
        verdict = judge(case, out["answer"], [s["title"] for s in out["sources"]])

        results.append({
            "id": case["id"], "tags": case.get("tags", []),
            "answer": out["answer"], "verdict": verdict.verdict,
            "faithful": verdict.faithful, "score": verdict.score,
            "checks": checks, "latency_ms": latency_ms,
            "cost_usd": estimate_cost(out["usage"]),
        })

    summary = {
        "run": name,
        "n": len(results),
        "accuracy": sum(r["verdict"] == "correct" for r in results) / len(results),
        "faithfulness": sum(r["faithful"] for r in results) / len(results),
        "checks_passed": sum(all(r["checks"].values()) for r in results) / len(results),
        "p50_ms": statistics.median(r["latency_ms"] for r in results),
        "p95_ms": sorted(r["latency_ms"] for r in results)[int(0.95 * len(results)) - 1],
        "cost_usd": sum(r["cost_usd"] for r in results),
        "seconds": time.time() - started,
    }

    Path(f"evals/runs/{name}.json").write_text(json.dumps({"summary": summary, "results": results}, indent=2))
    return summary

That comparison — one change, quality up, latency slightly up, cost roughly flat — is what an engineering decision looks like in this field. Keep every run; the history is the story of the system.

Metrics worth tracking

Accuracy / task successThe headline. Define it per product.
FaithfulnessClaims supported by sources. The anti-hallucination metric.
Recall@kRetrieval health, measured separately.
Refusal correctnessRefuses when it should, does not when it should not.
Format validityParses, matches schema, respects limits.
Latency p50 / p95Averages hide the bad tail users actually complain about.
Cost per taskNot per call — per completed task.

Segment by tag. "86% overall" can hide "45% on the multi-document questions", which is exactly what you needed to know.

Hill-climbing without fooling yourself

  1. Run the baseline. Record everything.
  2. Read the failures — all of them, properly. Group by cause.
  3. Change one thing that addresses the largest group.
  4. Re-run. Compare. Keep the change only if it improved the metric that matters without wrecking another.
  5. Every few rounds, check the held-out set. If train improves and test does not, you are overfitting.
  6. Stop when improvements are within noise — and record where you stopped and why.

Noise is real: with 50 cases, a 2-point move is nothing. Either grow the dataset or run the eval a few times and look at the variance before you believe a small delta.

Evals in CI

# .github/workflows/eval.yml
- run: python -m evals.run "pr-${{ github.event.number }}"
- run: python -m evals.compare --baseline main --against "pr-${{ github.event.number }}" --min-accuracy 0.80

Practical shape: a small, fast, deterministic subset on every pull request (schema validity, classification accuracy, refusals — cheap graders only), and the full LLM-judged suite nightly or before a release. Fail the build on a regression below your threshold. Budget the cost: 50 cases with a judge is a few dollars, which is fine nightly and not fine on every push.

Unit tests still matter

def test_chunking_preserves_content():
    chunks = chunk_recursive(TEXT, size=500, overlap=50)
    assert "".join(c.replace(OVERLAP_MARKER, "") for c in chunks)  # nothing lost

def test_citation_extraction():
    assert extract_citation_ids("As stated [1][3], the policy...") == {1, 3}

def test_tenant_filter(client):
    results = search("anything", tenant="acme")
    assert all(r.metadata["tenant"] == "acme" for r in results)

Everything deterministic around the model — chunking, parsing, filters, citation handling, cost calculation — gets ordinary fast unit tests. Save the expensive evals for the non-deterministic part.

Evaluating in production

  • Collect feedback (thumbs, corrections, "was this helpful") and store it with the trace.
  • Watch implicit signals: repeated rephrasing of the same question, abandonment, escalation to a human.
  • Sample and review a handful of real conversations weekly. Nothing replaces reading them.
  • Feed failures back into the eval set. This is the flywheel: production failures become regression cases become a better system.
  • A/B test significant changes rather than reasoning about them.
Practice
  1. Build a 30-case eval set for your RAG project, including five out-of-scope questions.
  2. Write the runner with programmatic checks only, and record a baseline.
  3. Add an LLM judge, then hand-grade 20 cases and measure agreement with it. Fix the judge until it agrees.
  4. Make one improvement from lesson 12 and prove the delta with numbers.
  5. Segment results by tag and find the category where your system is worst.
  6. Add a fast subset to CI that fails the build on a regression.
