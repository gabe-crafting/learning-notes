Frameworks and orchestration

LangChain, LlamaIndex, LangGraph and friends: what they genuinely give you, what they cost, and why experienced teams often use less of them than you would expect.

The honest position

You have now built, with plain SDK calls: prompting, structured output, tool loops, retrieval, agents and memory. None of it required a framework. That is not an accident — the provider SDKs absorbed a lot of what frameworks were originally for.

Frameworks still earn their place when you want components you would otherwise write yourself (fifty document loaders, a dozen vector-store adapters, retrieval strategies), or when you need something genuinely hard to build, like durable stateful graphs. They cost you an abstraction layer between your code and the provider's documentation, a dependency that changes faster than you would like, and debugging that goes through someone else's call stack.

Learn the primitives first, then adopt selectively A developer who understands the loop can use a framework well or drop it when it fights them. A developer who only knows the framework is stuck when the abstraction leaks — and it will leak, usually in production. That is why this course put frameworks in lesson 15 rather than lesson 3.

What the abstractions look like

# LangChain, modern style (LCEL): compose runnables with |
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

prompt = ChatPromptTemplate.from_template(
    "Answer using only this context:\n{context}\n\nQuestion: {question}"
)
chain = prompt | llm | StrOutputParser()
answer = chain.invoke({"context": docs, "question": q})
# LlamaIndex: the RAG happy path in four lines
from llama_index.core import VectorStoreIndex, SimpleDirectoryReader

documents = SimpleDirectoryReader("./docs").load_data()
index = VectorStoreIndex.from_documents(documents)
response = index.as_query_engine(similarity_top_k=5).query("What is the leave policy?")
print(response, response.source_nodes)
# LangGraph: a state machine with checkpointing
from langgraph.graph import StateGraph, END

graph = StateGraph(AgentState)
graph.add_node("retrieve", retrieve_node)
graph.add_node("answer", answer_node)
graph.add_node("verify", verify_node)
graph.set_entry_point("retrieve")
graph.add_edge("retrieve", "answer")
graph.add_conditional_edges("answer", needs_more_context, {"yes": "retrieve", "no": "verify"})
graph.add_edge("verify", END)

app = graph.compile(checkpointer=checkpointer)   # resumable, inspectable, interruptible

The LlamaIndex snippet is genuinely four lines against the hundred-odd you wrote in lessons 8–11 — and it is also the least tunable version of that pipeline. That trade is the whole decision.

How to decide

  1. Prototype: use whatever gets you an answer fastest. LlamaIndex for RAG demos is hard to beat.
  2. Production, simple pipeline (one or two calls, one retrieval): plain SDK plus your own thin helpers. You will not miss the framework.
  3. Production, complex stateful agent (resumable, human-in-the-loop, multi-day runs): LangGraph or a managed agent platform. Building durable execution yourself is a real project.
  4. Heavy document variety (dozens of formats and sources): borrow the loaders even if you write the rest yourself — you can import just the pieces.

Nothing stops you mixing: LlamaIndex readers for ingestion, your own retrieval and prompting, the provider SDK for calls. Frameworks are libraries, not religions.

The costs, stated plainly

  • Debugging through layers. When the prompt sent to the model is not what you expected, you are reading framework source to find where it was assembled. Turn on the framework's prompt logging early.
  • Churn. These libraries move fast; tutorials go stale within months, and imports get reorganised between minor versions. Pin versions.
  • Lag behind provider features. A new capability lands in the provider SDK first and in the framework later, sometimes partially.
  • Hidden cost and latency. A convenient one-liner may be making three model calls. Check your usage logs.
  • Weak defaults presented as decisions. A default chunk size and a default k are not a retrieval strategy — the tuning from lesson 12 is still yours to do.

If you do use one, use it well

# 1. keep framework types at the edges, not through your whole codebase
def answer(question: str, tenant: str) -> Answer:   # your own types in and out
    ...                                              # framework used inside

# 2. always be able to see the final prompt
import langchain
langchain.debug = True          # or the framework's tracing/callback hooks

# 3. pin versions
langchain-core==0.3.x
llama-index-core==0.12.x

The wrapper discipline from lesson 4 applies doubly here: if your business logic imports framework classes everywhere, switching or dropping the framework becomes a rewrite. If it imports your own answer(), it is an afternoon.

Managed agent platforms

A newer option sits between "framework" and "infrastructure": platforms where the provider runs the agent loop and hosts the sandbox the tools execute in, with persisted agent configurations, sessions, scheduling and file storage. You supply the configuration and your tools, and skip writing loop code, state files and a scheduler.

Worth evaluating when you need long-running or scheduled agents with a workspace, and you would otherwise be building that infrastructure yourself. The trade is the usual one: less code you own, more platform you depend on.

What to say in an interview

"I use the provider SDK directly for straightforward pipelines because it is easier to debug and stays current with the API. I reach for LlamaIndex when ingestion variety is the problem, and LangGraph when I need durable, resumable agent state with human approval. I keep framework types out of my domain code either way." That answer signals judgement — which is what the question is testing. "I only know LangChain" does not.
