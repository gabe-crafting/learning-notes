Calling an LLM API

The request shape, streaming, errors, retries and cost accounting — the boring layer that decides whether your app survives contact with real traffic.

Setup

uv add anthropic
# key in .env as ANTHROPIC_API_KEY; the SDK reads it from the environment

The basic request

import anthropic

client = anthropic.Anthropic()

response = client.messages.create(
    model="claude-opus-5",
    max_tokens=16000,
    system="You are a concise technical assistant. Prefer bullet points.",
    messages=[
        {"role": "user", "content": "Explain vector embeddings in three sentences."}
    ],
)

for block in response.content:
    if block.type == "text":
        print(block.text)

Three things to notice, because they generalise:

  • The conversation is a list of messages with roles. Every provider works this way.
  • The system prompt is separate from the conversation and frames all of it.
  • The response is a list of content blocks, not a string. A response can contain text, reasoning and tool calls together — always check block.type rather than assuming content[0].text.

What the response carries

response.id            # message id — log it
response.model         # which model actually served the request
response.stop_reason   # end_turn | max_tokens | tool_use | refusal | ...
response.usage.input_tokens
response.usage.output_tokens

stop_reason deserves a check on every path. max_tokens means the answer was cut off mid-thought — if you parse that as JSON it will fail, and the cause will not be obvious.

Multi-turn conversations

messages = []

def ask(user_text: str) -> str:
    messages.append({"role": "user", "content": user_text})
    response = client.messages.create(
        model="claude-opus-5",
        max_tokens=4000,
        system=SYSTEM_PROMPT,
        messages=messages,
    )
    answer = next(b.text for b in response.content if b.type == "text")
    messages.append({"role": "assistant", "content": answer})
    return answer

ask("My name is Ana.")
ask("What is my name?")     # works only because the history is resent

Since you resend everything, a long conversation grows linearly in cost. Strategies when it gets long: keep the last N turns, summarise older ones into a compact note, or use the provider's server-side compaction. Decide this early — retro-fitting it into a chat product is unpleasant.

Streaming

Users judge a chat interface by time-to-first-token, not total time. Stream anything a human is waiting on.

with client.messages.stream(
    model="claude-opus-5",
    max_tokens=64000,
    messages=[{"role": "user", "content": "Write a short guide to RAG."}],
) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)

    final = stream.get_final_message()     # full message once done
    print(final.usage.output_tokens)

Streaming is also how you avoid HTTP timeouts on long generations — a non-streaming request with a very large max_tokens can exceed the client timeout before it produces anything. Lesson 20 covers pushing this stream on to a browser over SSE.

Errors and retries

import anthropic

try:
    response = client.messages.create(...)
except anthropic.BadRequestError as e:          # 400 — your request is wrong; do not retry
    log.error("bad request: %s", e.message)
    raise
except anthropic.AuthenticationError:            # 401 — bad or missing key
    raise
except anthropic.RateLimitError as e:            # 429 — back off
    retry_after = int(e.response.headers.get("retry-after", "60"))
    ...
except anthropic.APIStatusError as e:            # 5xx — transient, retry
    if e.status_code >= 500:
        ...
except anthropic.APIConnectionError:             # network
    ...

The SDK already retries connection errors, 408, 409, 429 and 5xx with exponential backoff (two retries by default); tune it rather than reimplementing it:

client = anthropic.Anthropic(max_retries=4, timeout=30.0)

# or per call
client.with_options(timeout=10.0).messages.create(...)

Two habits worth forming now: set an explicit timeout (the default is minutes, which is not what you want behind a web request), and never retry a 400 — the request is malformed and will fail identically forever.

Counting tokens and estimating cost

count = client.messages.count_tokens(
    model="claude-opus-5",
    system=SYSTEM_PROMPT,
    messages=messages,
)
print(count.input_tokens)

INPUT_PER_TOKEN  = 5.00 / 1_000_000     # claude-opus-5
OUTPUT_PER_TOKEN = 25.00 / 1_000_000

def cost(usage) -> float:
    return usage.input_tokens * INPUT_PER_TOKEN + usage.output_tokens * OUTPUT_PER_TOKEN

Log usage for every call from day one, tagged with the feature that made it. Without that you cannot answer "which feature costs us the most", which is the first question anyone will ask when the bill arrives.

Prompt caching

When many requests share a long identical prefix — a big system prompt, a document, a fixed tool list — you can have the provider cache it. Cached input is dramatically cheaper and faster to process.

response = client.messages.create(
    model="claude-opus-5",
    max_tokens=4000,
    cache_control={"type": "ephemeral"},   # cache the stable prefix
    system=LONG_STABLE_SYSTEM_PROMPT,
    messages=[{"role": "user", "content": question}],
)

print(response.usage.cache_creation_input_tokens)   # written to cache
print(response.usage.cache_read_input_tokens)       # served from cache — the win
Caching is a prefix match One changed byte anywhere in the prefix invalidates everything after it. A timestamp, a UUID, an unsorted json.dumps or a tool list built from a set will silently destroy your hit rate. Keep the stable content first and the volatile content last, and verify with cache_read_input_tokens — if it stays zero across repeated calls, something is invalidating.

Wrapping the client

Do not scatter raw SDK calls across your codebase. One module owns model access, and everything else calls that:

# app/llm.py
import anthropic, logging, time

client = anthropic.Anthropic(max_retries=3, timeout=30.0)
log = logging.getLogger(__name__)

def complete(
    prompt: str,
    *,
    system: str | None = None,
    model: str = "claude-opus-5",
    max_tokens: int = 4000,
    feature: str = "unknown",
) -> str:
    started = time.perf_counter()
    response = client.messages.create(
        model=model,
        max_tokens=max_tokens,
        system=system,
        messages=[{"role": "user", "content": prompt}],
    )
    log.info(
        "llm_call feature=%s model=%s in=%d out=%d stop=%s ms=%d",
        feature, model,
        response.usage.input_tokens, response.usage.output_tokens,
        response.stop_reason, (time.perf_counter() - started) * 1000,
    )
    if response.stop_reason == "max_tokens":
        log.warning("truncated response for feature=%s", feature)
    return "".join(b.text for b in response.content if b.type == "text")

That one function gives you a single place to add tracing, caching, model routing, a circuit breaker, or a swap to another provider. Building it on day one costs ten minutes and saves a refactor later.

What is portable between providers

ConceptPortable?
Roles, message list, system promptYes — universal
StreamingYes, with different event shapes
Tool / function callingConceptually yes; schemas and field names differ
Structured output via JSON schemaConceptually yes; parameter names differ
Token counting, caching, batch endpointsProvider-specific
Reasoning / effort controlsProvider-specific, and changing fast
Model IDs, pricing, limitsNo

This is why the wrapper above matters, and why an abstraction layer (lesson 15) is sometimes worth it — and sometimes just an extra dependency between you and the docs.

Rate limits

Providers limit requests per minute and tokens per minute. Under load you will see 429s. The fixes are ordinary engineering: bound your concurrency with a semaphore, retry with exponential backoff and jitter, queue work that is not interactive, and use a batch endpoint for anything that can wait — batch pricing is typically about half.

Practice
  1. Make your first call, print the text and the usage, and compute the cost of that single call.
  2. Build a command-line chat that keeps history, streams the answer, and prints running total cost after every turn.
  3. Trigger three different errors on purpose: an invalid model id, a missing key, and a max_tokens so small the answer is cut off. Handle each distinctly.
  4. Send the same 5,000-token document twice with caching enabled and compare cache_read_input_tokens on the second call. Then break the cache by adding a timestamp to the system prompt and observe it drop to zero.
  5. Write the complete() wrapper with structured logging and use it for everything from here on.
