Portfolio projects and a plan

Three projects worth building, an eight-week schedule to build them alongside the lessons, and what interviews actually ask.

What makes a project count

Recruiters and engineers look for different things. Engineers — the people who decide — look for evidence you have dealt with the parts that are hard:

It runsOne command, a README, seeded data or a demo mode. If a stranger cannot start it in five minutes, it does not exist.
It is measuredAn eval set and a results table. This is the strongest single signal, and the rarest.
It fails wellRefuses when it should, handles empty results, degrades on errors.
It is honestA README section on limitations and what you would do next.
You can defend itEvery design decision has a reason you can state.

Three good projects beat ten tutorials. A tutorial clone with a different colour scheme is worth nothing; nobody is fooled.

Project 1 — Document Q&A with citations

The canonical AI-engineering project. Pick a corpus you genuinely care about: your country's employment law, a game's rules, the documentation of a library you use, your own notes.

Must have
  ingestion (PDF/HTML/Markdown) with chunking and metadata
  embeddings + vector store (pgvector), incremental re-indexing
  hybrid search (vector + BM25) with RRF fusion
  answers with inline citations that link to the source page
  explicit "not in the documents" refusal
  streaming API + a minimal UI
  an eval set of 30+ questions and a results table

Should have
  a reranker, and the measured before/after numbers
  question rewriting for follow-ups
  cost and latency per question, logged and reported

Stretch
  multi-tenant with permission-filtered retrieval
  contextual chunk prefixes at ingestion
  a comparison table of 3–4 retrieval configurations

What it demonstrates: the entire RAG stack, plus that you measure. Lessons 8–12, 16, 20.

Project 2 — An agent with real tools

Something that does work, not just answers. Good briefs: a GitHub triage assistant (read issues, search the codebase, propose labels and a first response), a personal finance agent over your bank export, a research agent that browses and writes a cited brief, a DevOps assistant that reads logs and metrics.

Must have
  3–6 well-designed tools with real side effects (at least one write)
  a bounded loop: iteration, token and time budgets
  a full trace of every run, persisted
  human approval on irreversible actions
  graceful handling of tool failures
  a task-success eval over 15+ fixed goals

Should have
  a comparison against the equivalent fixed workflow, with numbers
  cost per completed task
  a dry-run mode

Stretch
  MCP integration
  a subagent for a reading-heavy step
  resumable runs (checkpointing) with a pause for approval

What it demonstrates: tool design, loop control, safety judgement. Lessons 7, 13, 14, 18.

Project 3 — Structured extraction at volume

The least glamorous and often the most employable, because it is what companies actually pay for. Invoices, CVs, contracts, scientific abstracts, job adverts, receipts — messy input, structured output, at scale.

Must have
  a Pydantic schema with enums, optionals and validation
  structured output with schema enforcement
  business validation beyond the schema (cross-checks against the source)
  batch processing with bounded concurrency
  an accuracy eval on 50 hand-labelled documents, field by field
  a cost-per-document figure

Should have
  a model comparison: frontier vs cheap vs small open model, accuracy and cost
  a repair loop, with the repair rate reported
  handling of scanned documents (multimodal or OCR)

Stretch
  a small review UI for low-confidence extractions
  a distillation experiment (lesson 19)

What it demonstrates: reliability, evaluation and cost engineering. Lessons 6, 16, 17, 19.

The README that makes a project count

# Docs Assistant

Ask questions about <corpus> and get answers with citations.

## Demo
[30-second GIF or a link]

## Run it
docker compose up
open http://localhost:8000

## How it works
[one diagram: ingest → chunk → embed → hybrid search → rerank → answer]

## Results
| configuration          | recall@5 | accuracy | faithfulness | p95 latency | cost/query |
|------------------------|----------|----------|--------------|-------------|------------|
| vector only, k=5       | 0.61     | 0.68     | 0.85         | 1.9 s       | $0.008     |
| + BM25 hybrid (RRF)    | 0.84     | 0.82     | 0.91         | 2.0 s       | $0.008     |
| + cross-encoder rerank | 0.91     | 0.88     | 0.94         | 2.3 s       | $0.009     |

Eval set: 40 questions (evals/dataset.jsonl), graded by programmatic checks
plus an LLM judge validated against 20 hand-graded cases (85% agreement).

## Design decisions
- 800-token chunks split on headings: 300 fragmented tables, 1500 diluted retrieval.
- pgvector over a dedicated vector DB: one datastore, real joins, transactions.
- Rerank only the top 50: +7 points recall for ~240 ms.

## Limitations
- Scanned PDFs are not OCR'd.
- Single tenant.
- Tables are flattened; numeric questions over tables are unreliable.

That results table is the artifact. It says: this person measures, compares and trades off — which is precisely the job.

An eight-week plan

Assumes roughly 10–15 hours a week alongside a job. Compress it if you have more time; do not skip the evaluation weeks.

If you only have four weeks Weeks 1–5 compressed, then deploy project 1 properly. One finished, measured, deployed RAG project with an honest README beats three half-built repositories every time.

Keeping current without drowning

  • Read the primary docs of the provider you use — the changelog and the migration guides especially.
  • Follow a handful of practitioners rather than the whole timeline. Most "breakthroughs" do not change your work.
  • When a new model lands, run your eval set on it. That is your signal, not a benchmark chart.
  • Re-read your prompts after every model upgrade; instructions written for the old model quietly degrade the new one.
  • Budget an hour a week for this and no more. Building beats reading.

Interview preparation

Questions you should be able to answer cold

  • What is the difference between an AI engineer and an ML engineer?
  • Explain RAG to a non-technical stakeholder. Now explain why it is not always the answer.
  • How do you chunk documents, and how did you choose the size?
  • Your RAG system gives a wrong answer. Walk me through debugging it.
  • How do you know a prompt change made things better?
  • What is prompt injection, and how would you defend an agent that reads customer emails?
  • When would you fine-tune rather than use RAG?
  • How do you control cost in an LLM product?
  • What is the difference between a workflow and an agent, and which have you shipped?
  • How would you evaluate an agent when several paths are valid?

For every one of those, answer with something you actually did, with a number in it. "We measured recall@5 at 0.61, added hybrid search, and got to 0.84" ends the question. "I read that hybrid search helps" invites three more.

The take-home

Common brief: "build a small RAG or extraction service over this data". What separates the top submissions is never cleverness — it is a README, an eval, honest limitations, error handling, and code someone else can read. Ship something modest and complete rather than ambitious and broken, and write down what you would do with another week.

What to have ready

  • Three repositories, each with a README and a results table.
  • A short demo — a GIF or a deployed URL — for at least one.
  • A written story for each project: the problem, three decisions and their trade-offs, what you measured, what you would change.
  • One honest failure you learned from. Interviewers ask, and "nothing went wrong" is not a credible answer.

Where to go after this course

  • Depth in retrieval — information retrieval fundamentals, learned sparse retrieval, evaluation methodology. This is the durable specialism.
  • Depth in evaluation — the skill teams most consistently lack, and the fastest route to being the person who is trusted.
  • Backend fundamentals if they are thin: SQL, queues, Docker, a cloud. The Spring course covers the same ideas from another angle.
  • A little ML literacy — enough to read a model card and a benchmark critically, without pretending to be an ML engineer.
  • Ship something real, to real users, even ten of them. Everything you learn from that is unavailable any other way.
Practice
  1. Pick the corpus for project 1 today. Not tomorrow — indecision here is the most common reason people never start.
  2. Write the README for project 1 before you build it, including the empty results table. Then fill the table in as you go.
  3. Put the eight-week plan in your calendar with two fixed sessions a week.
  4. After each project, write the three-decision story. Rehearse it out loud once.
  5. Send project 1 to one experienced developer and ask for honest criticism. Act on it.
