How LLMs actually behave

Not the maths — the operational model. Enough understanding to predict what a model will do, why it costs what it costs, and why it sometimes invents things.

The one-sentence version

A large language model takes a sequence of tokens and predicts a probability distribution over the next token, over and over, until it decides to stop. Everything else — chat, reasoning, tool calls, JSON — is that mechanism wrapped in structure.

Tokens

Models do not see characters or words. Text is split into tokens: common words are one token, rare words split into pieces, and whitespace and punctuation carry their own.

"AI engineering"        →  ~3 tokens
"unbelievability"       →  ~5 tokens
"def chunk_text(text):" →  ~7 tokens
Romanian, Chinese, code →  more tokens per character than English prose

rule of thumb (English): 1 token ≈ 4 characters ≈ 0.75 words
                         1,000 words ≈ 1,300–1,500 tokens

Tokens are the unit of billing, of the context limit, and of latency. Everything you care about operationally is measured in them.

Do not estimate tokens with another provider's tokenizer Every model family tokenizes differently. Using OpenAI's tiktoken to estimate Claude usage undercounts substantially, and more so on code and non-English text. Use the provider's own counting endpoint — for Claude, client.messages.count_tokens(model=..., messages=...), which is free and exact for that model.

The context window

The context window is the maximum number of tokens the model can consider at once — your system prompt, the whole conversation, retrieved documents, tool definitions, tool results, and the response it is generating, all together.

context window = system prompt
               + conversation history
               + retrieved context / documents
               + tool definitions and tool results
               + the output being generated (max_tokens)

Current frontier models offer very large windows (Claude Opus 5 and Sonnet 5: 1M tokens; Claude Haiku 4.5: 200K). That does not mean you should fill them:

  • You pay per input token, every single call. A stuffed context is a permanent tax on every request in the conversation.
  • More context is slower.
  • Irrelevant context degrades answers. Retrieval that dumps twenty mediocre chunks in usually produces a worse answer than three good ones. This is the single most common RAG failure, and lesson 12 is largely about it.

"Context engineering" — deciding what deserves a place in the window — is a real skill, and a better use of your time than shaving words off a prompt.

The API is stateless

turn 1:  [user: "My name is Ana"]
turn 2:  [user: "My name is Ana"] [assistant: "Hello Ana"] [user: "What is my name?"]

The model remembers nothing between calls. "Memory" in a chat product means you resend the history each time, or store a summary and resend that. This is why long conversations get progressively more expensive, and why lesson 14 covers memory strategies.

Sampling: why answers vary

At each step the model has a probability distribution over next tokens, and sampling decides how to pick from it. Classic knobs, which you will meet across providers:

temperature0 makes the choice near-deterministic; higher values flatten the distribution and increase variety.
top_p (nucleus)Only sample from the smallest set of tokens whose probabilities sum to p.
top_kOnly sample from the k most likely tokens.
A concrete example of API drift On current Claude models (Opus 5, Sonnet 5, the 4.6+ family) these sampling parameters have been removed — sending temperature returns a 400. The knob that replaced them is output_config: {"effort": "low"|"medium"|"high"|"xhigh"|"max"}, which trades thoroughness against token spend. Other providers still expose temperature. The general lesson: learn the concept, then check the reference for the model you are actually calling.

Even with everything pinned, outputs are not guaranteed to be byte-identical across calls — batching and hardware nondeterminism see to that. Design as if every call may differ, because it may.

Reasoning / thinking modes

Modern models can spend tokens on internal reasoning before answering, which materially improves hard tasks — multi-step logic, code, planning, careful extraction. On Claude this is adaptive thinking, and it is on by default on Opus 5:

response = client.messages.create(
    model="claude-opus-5",
    max_tokens=16000,
    thinking={"type": "adaptive", "display": "summarized"},
    output_config={"effort": "high"},   # low | medium | high | xhigh | max
    messages=[{"role": "user", "content": "..."}],
)

Reasoning tokens are billed like output tokens, so this is a quality/cost dial. Use higher effort on hard, low-volume work; use lower effort for classification, routing and high-volume paths where it buys nothing. Measure rather than assume — lesson 16.

Why models hallucinate

The model is producing a plausible continuation, not looking anything up. If it does not know, "plausible" and "true" diverge — and the output is just as fluent either way. Fluency is not evidence.

Practical mitigations, in order of effectiveness:

  1. Give it the facts (retrieval) instead of relying on what it absorbed in training.
  2. Demand citations and verify they exist in the source — a check you can automate.
  3. Give it an exit: "If the context does not contain the answer, say you do not know."
  4. Constrain the output to a schema or an enum, so free invention has nowhere to go.
  5. Validate mechanically — does that order id exist, does that URL resolve, does that number add up.
  6. Keep a human in the loop wherever a wrong answer is expensive.

Also remember the training cutoff: models know nothing about events after it, and asking about recent things is a reliable way to get confident fiction. Use search or retrieval for anything current.

Choosing a model

Providers ship tiers, and the tiering is more useful than the branding. As a current example, the Claude family:

ModelModel IDContextInput $/1MOutput $/1M
Claude Opus 5claude-opus-51M$5.00$25.00
Claude Sonnet 5claude-sonnet-51M$2.00$10.00
Claude Haiku 4.5claude-haiku-4-5200K$1.00$5.00

Output tokens cost several times input tokens — everywhere, not just here. That single fact drives a lot of design: verbose formats are expensive, and asking for JSON with short field names genuinely saves money at volume.

How to choose in practice:

  • Prototype on the most capable model, so you learn whether the task is possible at all.
  • Then try to move high-volume paths down a tier and measure whether quality holds. Often it does.
  • Route by difficulty: a cheap model for classification and routing, the strong one for the hard step.
  • Judge cost per completed task, not per call. A cheap model that needs three attempts is not cheap.

Latency

total latency ≈ queue + prompt processing (input tokens)
                      + generation (output tokens × time per token)

Output length dominates. Consequences: stream the response so the user sees the first token quickly; cap max_tokens to something sane; prefer concise output formats; and do independent calls concurrently rather than in sequence. A perceived-fast product is mostly streaming plus not making the user wait on work that could have happened in parallel.

Multimodality and other capabilities

Current models accept images and PDFs alongside text, which quietly solves a lot of document work — you can hand a scanned invoice to the model directly instead of running OCR first. Providers also offer server-side tools (web search, code execution), batch endpoints at reduced cost for non-urgent work, and prompt caching. Know which of these exist before you build your own version of one.

Practice
  1. Count the tokens in a 2,000-word document with the provider's counting endpoint. Compute what it would cost to send it on every request in a 20-turn conversation.
  2. Ask a model a question about something that happened last month, without giving it search or context. Note how the wrong answer is phrased exactly like a right one.
  3. Run the same prompt five times. Diff the answers. Then decide what that means for testing.
  4. Take one task and run it on a top-tier and a cheap model, ten inputs each. Write down where quality actually differed — you may be surprised how rarely it does.
  5. Write a one-paragraph explanation of hallucination for a non-technical stakeholder who asks "can we just tell it not to make things up?"
