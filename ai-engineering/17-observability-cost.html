Observability, latency and cost

Three properties of the same system. You cannot manage any of them without measuring, and measuring LLM systems needs slightly different plumbing than ordinary services.

What to log for every model call

  "message_id": "msg_01ABC..."
}

The unusual fields compared with normal service logging are the token counts, the cache hit numbers, the prompt version and the retrieved ids. Together they let you answer the four questions you will actually be asked: why is it slow, why is it expensive, why did it answer that, and did last week's change help.

Decide your policy on logging prompt content Prompts and outputs contain user data. Logging them makes debugging possible and creates a privacy liability. Common compromise: log content in development, and in production log hashes, lengths and metadata by default, with full-content capture enabled for a sampled percentage, redacted, with a short retention. Never log secrets or the API key, and make sure your tracing vendor's retention matches your privacy policy.

Tracing

One user request may involve a rewrite call, an embedding, a search, a rerank and a generation. A flat log line per call cannot show you which of those was slow. Traces nest spans under one request.

trace: POST /api/ask  (3,180 ms, $0.0182)
├── span rewrite_query      210 ms   $0.0002   claude-haiku-4-5
├── span embed_query         40 ms   $0.0000
├── span vector_search       28 ms
├── span rerank             240 ms
└── span generate         2,610 ms   $0.0180   claude-opus-5   ttft 480 ms

Tooling: Langfuse (open source, self-hostable), LangSmith, Phoenix/Arize, Braintrust, Helicone, or plain OpenTelemetry into whatever you already run. The specific tool matters less than having one before you need it — the day a customer says "it gave me a wrong answer this morning" you want the trace, not a shrug.

# the pattern, with any tracer
with tracer.span("rag_answer", user=user_id, prompt_version="v2") as span:

        response = client.messages.create(...)

                output_tokens=response.usage.output_tokens,
                cost_usd=cost(response.usage))
    span.set(sources=[s.chunk_id for s in sources], outcome="answered")

Latency

total ≈ your overhead + retrieval + queue + prompt processing + generation
                                                  ↑ input tokens    ↑ output tokens (dominant)
  • Stream. Time to first token is what users perceive. A 3-second streamed answer feels faster than a 1.5-second blocking one.
  • Shorten the output. The most effective real lever. Ask for 100 words instead of 400 and you have halved the time and the output cost.
  • Parallelise independent calls; never await three things in sequence that do not depend on each other.
  • Use a smaller model for the fast paths — routing, rewriting, classification.
  • Lower the effort setting where the extra reasoning is not buying accuracy.
  • Cache — both the prompt prefix and whole answers.
  • Do work ahead of time: pre-compute embeddings, pre-warm caches, precompute summaries at ingestion rather than per query.
  • Show progress for genuinely long agent runs — a visible step list beats a spinner.

Track p50 and p95, per feature. The p95 is where your angriest users live.

Cost

Know where it goes before optimising

SELECT feature, model,
       count(*)                    AS calls,
       sum(input_tokens)           AS in_tokens,
       sum(output_tokens)          AS out_tokens,
       round(sum(cost_usd), 2)     AS usd
FROM llm_calls
WHERE created_at > now() - interval '7 days'
GROUP BY feature, model
ORDER BY usd DESC;

Almost always, one or two features dominate. Optimise those; ignore the rest.

The levers, cheapest first

  1. Prompt caching. Free quality, large saving on any repeated prefix — long system prompts, fixed tool lists, a document you ask many questions about. Verify hits rather than assuming them.
  2. Send less. Trim the system prompt, retrieve fewer chunks, shrink tool results, stop resending history you have already summarised. Input tokens are paid on every turn.
  3. Generate less. Output costs several times input. Set sane max_tokens, ask for concise formats, use short JSON field names at volume.
  4. Batch API for anything not interactive — typically around half price for asynchronous processing.
  5. Answer caching for repeated questions.
  6. Effort tuning: drop routine paths to lower effort and measure whether quality holds.
  7. Model routing: cheap model for easy work, strong model for hard work.

The first five cost you nothing in quality. Only then start trading.

Routing, done honestly

class Difficulty(BaseModel):
    level: Literal["simple", "complex"]

def answer(question: str) -> str:
    level = classify(question, output_format=Difficulty).level      # haiku, ~$0.0001
    model = "claude-haiku-4-5" if level == "simple" else "claude-opus-5"
    return generate(question, model=model)

Two warnings. First, measure the router — a wrong route sends a hard question to a weak model and produces a bad answer plus a retry, which is more expensive than never routing. Second, caches are model-scoped, so a cascade forfeits cache reuse across models; sometimes the strong model at low effort beats routing outright. Measure both.

Semantic answer caching

def cached_answer(question: str, tenant: str) -> str | None:
    vector = embed_query(question)
    hit = cache.nearest(vector, tenant=tenant, min_similarity=0.95, max_age_hours=24)
    return hit.answer if hit else None

Effective on FAQ-shaped traffic where many users ask the same thing differently. Set the threshold high — a similar-but-not-identical question served a cached answer is a bug users notice — scope by tenant and permissions, and expire aggressively when the underlying documents change.

Budgets and guardrails

MAX_COST_PER_REQUEST = 0.50
MAX_COST_PER_USER_PER_DAY = 5.00

def check_budget(user_id: str, projected: float) -> None:
    spent = usage.today(user_id)
    if spent + projected > MAX_COST_PER_USER_PER_DAY:
        raise BudgetExceeded(f"daily limit reached ({spent:.2f} USD)")

Also worth having: a global kill switch, alerts on daily spend, alerts on a sudden change in average tokens per request (usually a prompt bug or a retrieval bug), and per-tenant quotas if you are multi-tenant. A runaway agent loop at 3am is a real way to lose a lot of money quickly.

Also: bound concurrency to stay inside rate limits, put non-interactive work in a queue, and make anything the user is not waiting on a background job. Standard backend engineering — which is exactly why your existing experience transfers.

Practice
  1. Add structured logging of every model call in your project, including tokens, cost and latency.
  2. Wire up Langfuse (or any tracer) and inspect a full trace of one RAG request. Find the slowest span.
  3. Build the weekly cost query and identify your most expensive feature.
  4. Enable prompt caching on your largest stable prefix and measure the cost difference over 20 requests.
  5. Implement routing between a cheap and a strong model, then measure quality on your eval set to check you did not silently lose accuracy.
  6. Add a per-user daily budget and a global kill switch, and test that both actually stop requests.
