Calling other services

Your service will consume other HTTP APIs. Doing it well is mostly about what happens when the other side is slow, broken or lying.

Which client

RestClientSpring 6.1+, synchronous, fluent. The default choice today.
RestTemplateThe old synchronous client. Maintained, not deprecated, everywhere in existing code.
WebClientReactive and non-blocking. Use in WebFlux applications, or when you need true concurrency.
HTTP interfaceDeclarative: an annotated interface, implementation generated by Spring.

RestClient

@Configuration
public class ClientConfig {

    @Bean
    RestClient weatherClient(RestClient.Builder builder,
                             @Value("${weather.base-url}") String baseUrl,
                             @Value("${weather.api-key}") String apiKey) {

        var factory = new SimpleClientHttpRequestFactory();
        factory.setConnectTimeout(Duration.ofSeconds(2));
        factory.setReadTimeout(Duration.ofSeconds(5));

        return builder
                .baseUrl(baseUrl)
                .defaultHeader("X-Api-Key", apiKey)
                .requestFactory(factory)
                .build();
    }
}
@Service
public class WeatherService {

    private final RestClient client;

    public WeatherService(RestClient weatherClient) { this.client = weatherClient; }

    public Forecast forecastFor(String city) {
        return client.get()
                .uri("/forecast?city={city}", city)        // template variables are URL-encoded
                .retrieve()
                .body(Forecast.class);
    }

    public CreatedOrder createOrder(OrderRequest request) {
        return client.post()
                .uri("/orders")
                .contentType(MediaType.APPLICATION_JSON)
                .body(request)
                .retrieve()
                .body(CreatedOrder.class);
    }

    public List<City> cities() {
        return client.get().uri("/cities")
                .retrieve()
                .body(new ParameterizedTypeReference<List<City>>() {});
    }
}
Always set timeouts The defaults are effectively infinite. One slow dependency then holds your request threads until the whole service stops responding — a failure that spreads instead of staying contained.

Handling failure

Forecast forecast = client.get()
        .uri("/forecast?city={city}", city)
        .retrieve()
        .onStatus(HttpStatusCode::is4xxClientError, (req, res) -> {
            if (res.getStatusCode() == HttpStatus.NOT_FOUND) {
                throw new CityNotFoundException(city);
            }
            throw new WeatherClientException("Bad request: " + res.getStatusCode());
        })
        .onStatus(HttpStatusCode::is5xxServerError, (req, res) -> {
            throw new WeatherUnavailableException("Upstream error: " + res.getStatusCode());
        })
        .body(Forecast.class);

Without onStatus, retrieve() throws HttpClientErrorException/HttpServerErrorException — fine, but translating into your own exceptions keeps the upstream API out of your service layer, and lets your @RestControllerAdvice decide what the caller sees. A 404 from a dependency is usually not a 500 for your client — decide deliberately.

Declarative HTTP interfaces

public interface WeatherApi {

    @GetExchange("/forecast")
    Forecast forecast(@RequestParam String city);

    @PostExchange("/subscriptions")
    Subscription subscribe(@RequestBody SubscriptionRequest request);
}

@Bean
WeatherApi weatherApi(RestClient weatherClient) {
    return HttpServiceProxyFactory
            .builderFor(RestClientAdapter.create(weatherClient))
            .build()
            .createClient(WeatherApi.class);
}

The same annotations you know from controllers, on the client side. Readable, and easy to mock in tests because it is just an interface.

Retries and circuit breakers

<dependency>
    <groupId>io.github.resilience4j</groupId>
    <artifactId>resilience4j-spring-boot3</artifactId>
</dependency>
@Retry(name = "weather")
@CircuitBreaker(name = "weather", fallbackMethod = "cachedForecast")
public Forecast forecastFor(String city) { ... }

private Forecast cachedForecast(String city, Throwable cause) {
    log.warn("Weather API unavailable, serving cached data", cause);
    return cache.get(city);
}
resilience4j:
  retry:
    instances:
      weather:
        max-attempts: 3
        wait-duration: 200ms
        exponential-backoff-multiplier: 2
  circuitbreaker:
    instances:
      weather:
        failure-rate-threshold: 50
        wait-duration-in-open-state: 30s

Retry only idempotent operations — GET, PUT, DELETE. Retrying a POST that creates an order can charge a customer twice. If you must retry a create, make it idempotent with a client-supplied key.

A circuit breaker stops hammering a service that is already failing: after enough failures it "opens" and fails fast for a while, giving the other side room to recover.

Testing a client

@RestClientTest(WeatherService.class)
class WeatherServiceTest {

    @Autowired WeatherService service;
    @Autowired MockRestServiceServer server;

    @Test
    void parsesTheForecast() {
        server.expect(requestTo("/forecast?city=Berlin"))
              .andRespond(withSuccess("""
                  {"city":"Berlin","temperature":21}
                  """, MediaType.APPLICATION_JSON));

        assertThat(service.forecastFor("Berlin").temperature()).isEqualTo(21);
    }

    @Test
    void translatesA404() {
        server.expect(requestTo("/forecast?city=Nowhere"))
              .andRespond(withStatus(HttpStatus.NOT_FOUND));

        assertThatThrownBy(() -> service.forecastFor("Nowhere"))
                .isInstanceOf(CityNotFoundException.class);
    }
}

WireMock is the other common option, and can simulate delays and flaky responses — useful for testing timeouts and retries.

Practical rules

  • Never call another service inside a database transaction (lesson 9).
  • Log the correlation id you send and receive, so a trace spans both services.
  • Do not leak upstream errors verbatim to your clients — translate them.
  • Cache what is stable. @Cacheable on a lookup that changes daily removes most of the traffic.
  • Treat responses as untrusted input — validate what you receive.
  • Configure the base URL per environment; never hard-code a hostname.
  • Watch for N+1 over HTTP — a call per row in a loop is the same bug as the JPA one, only slower. Use a batch endpoint.

Parallel calls

// Java 21 virtual threads make this cheap
try (var scope = Executors.newVirtualThreadPerTaskExecutor()) {
    Future<Profile> profile = scope.submit(() -> profileClient.get(userId));
    Future<List<Order>> orders = scope.submit(() -> orderClient.forUser(userId));

    return new Dashboard(profile.get(), orders.get());   // ~max(a,b) instead of a+b
}
spring:
  threads:
    virtual:
      enabled: true      # Boot 3.2+: serve requests on virtual threads
Practice
  1. Call a public API (for example https://api.github.com/users/{name}) with RestClient and map the response to a record.
  2. Configure connect and read timeouts, then point the client at a URL that hangs and observe the behaviour.
  3. Translate 404 and 5xx into your own exceptions and map them to sensible status codes for your own API.
  4. Rewrite the client as a declarative HTTP interface.
  5. Write a @RestClientTest for the success case and one failure case.
  6. Add a retry with backoff and prove with a mock server that it retries exactly three times.
