Testing Spring applications

Fast unit tests for logic, narrow slices for the web and data layers, and a few full-stack tests with a real database.

What the starter gives you

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-test</artifactId>
    <scope>test</scope>
</dependency>

JUnit 5, AssertJ, Mockito, Hamcrest, JSONassert, and Spring's own test support — all in one dependency.

Level 1: plain unit tests

Most of your tests should not start Spring at all. If a service takes its dependencies through the constructor, you can build it yourself:

class TaskServiceTest {

    private final TaskRepository repository = mock(TaskRepository.class);
    private final Clock clock = Clock.fixed(Instant.parse("2026-01-01T10:00:00Z"), ZoneOffset.UTC);
    private final TaskService service = new TaskService(repository, clock);

    @Test
    void completingAnOpenTaskSetsTheTimestamp() {
        Task task = new Task("write tests", null);
        when(repository.findById(1L)).thenReturn(Optional.of(task));

        TaskResponse response = service.complete(1L);

        assertThat(response.done()).isTrue();
        assertThat(task.getCompletedAt()).isEqualTo(Instant.parse("2026-01-01T10:00:00Z"));
    }

    @Test
    void completingATwiceCompletedTaskFails() {
        Task task = new Task("done already", null);
        task.setDone(true);
        when(repository.findById(1L)).thenReturn(Optional.of(task));

        assertThatThrownBy(() -> service.complete(1L))
                .isInstanceOf(TaskAlreadyCompletedException.class);
    }
}

Milliseconds per test, no context to start. Note the injected Clock — that is why lesson 3 suggested it; testing "now" is otherwise miserable.

Level 2: slices

A slice starts only the part of Spring you are testing.

@WebMvcTest — the controller and its JSON

@WebMvcTest(TaskController.class)
class TaskControllerTest {

    @Autowired MockMvc mvc;
    @Autowired ObjectMapper json;

    @MockitoBean TaskService service;        // @MockBean in Boot < 3.4

    @Test
    void returnsTheTaskList() throws Exception {
        when(service.findAll(null)).thenReturn(List.of(
                new TaskResponse(1L, "write tests", null, false, null, Instant.EPOCH)));

        mvc.perform(get("/api/tasks"))
           .andExpect(status().isOk())
           .andExpect(jsonPath("$", hasSize(1)))
           .andExpect(jsonPath("$[0].title").value("write tests"));
    }

    @Test
    void rejectsABlankTitle() throws Exception {
        var request = new CreateTaskRequest("  ", null, null);

        mvc.perform(post("/api/tasks")
                .contentType(MediaType.APPLICATION_JSON)
                .content(json.writeValueAsString(request)))
           .andExpect(status().isBadRequest())
           .andExpect(jsonPath("$.fieldErrors.title").exists());
    }

    @Test
    void returns404WhenMissing() throws Exception {
        when(service.findById(99L)).thenThrow(new TaskNotFoundException(99L));

        mvc.perform(get("/api/tasks/99")).andExpect(status().isNotFound());
    }
}

No server, no database — but real routing, real JSON serialisation, real validation and your real exception handler. This is the sweet spot for testing the web layer.

@DataJpaTest — repositories

@DataJpaTest
class TaskRepositoryTest {

    @Autowired TaskRepository repository;
    @Autowired TestEntityManager em;

    @Test
    void findsOverdueTasks() {
        em.persist(new Task("late", LocalDate.now().minusDays(1)));
        em.persist(new Task("soon", LocalDate.now().plusDays(1)));
        em.flush();

        assertThat(repository.findByDueDateBefore(LocalDate.now()))
                .extracting(Task::getTitle)
                .containsExactly("late");
    }
}

Each test runs in a transaction that is rolled back afterwards, so tests do not pollute each other.

Level 3: the whole application

@SpringBootTest(webEnvironment = WebEnvironment.RANDOM_PORT)
@AutoConfigureMockMvc
class TaskApiIntegrationTest {

    @Autowired TestRestTemplate rest;      // or MockMvc
    @Autowired TaskRepository repository;

    @Test
    void createsAndThenReadsATask() {
        var created = rest.postForEntity("/api/tasks",
                new CreateTaskRequest("integration", null, null), TaskResponse.class);

        assertThat(created.getStatusCode()).isEqualTo(HttpStatus.CREATED);

        var fetched = rest.getForObject("/api/tasks/" + created.getBody().id(), TaskResponse.class);
        assertThat(fetched.title()).isEqualTo("integration");
    }
}

These are slow (seconds each), so keep them few and reserve them for the paths that matter most: the main happy path of each feature, and anything security-related.

Testcontainers: a real database in tests

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-testcontainers</artifactId>
    <scope>test</scope>
</dependency>
<dependency>
    <groupId>org.testcontainers</groupId>
    <artifactId>postgresql</artifactId>
    <scope>test</scope>
</dependency>
@SpringBootTest
@Testcontainers
class TaskIntegrationTest {

    @Container
    @ServiceConnection                       // Boot wires the datasource automatically
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16");

    @Test
    void runsAgainstRealPostgres() { ... }
}

Docker starts a throwaway Postgres for the test run. Your migrations run against it, and dialect differences between H2 and Postgres stop hiding bugs. Declare the container static so it is reused across tests in the class.

Mocking a bean inside a context test

@SpringBootTest
class CheckoutFlowTest {

    @MockitoBean PaymentGateway gateway;      // replaces the real bean in the context

    @Test
    void doesNotCallTheRealPaymentProvider() { ... }
}

Use it for external systems. Every distinct combination of mocked beans creates a new application context, and contexts are cached per configuration — a suite with many different combinations gets slow, so keep them few.

Test data

// a builder or factory keeps tests readable
static Task aTask() {
    return new Task("default title", LocalDate.now().plusDays(1));
}

@Sql("/test-data/tasks.sql")           // run SQL before the test
@Sql(scripts = "/cleanup.sql", executionPhase = AFTER_TEST_METHOD)

Each test should create the data it needs and not depend on what another test left behind. Order-dependent tests are a maintenance disaster.

What to test at each level

LevelTestDo not test
UnitBusiness rules, calculations, edge casesFramework wiring
@WebMvcTestStatus codes, JSON shape, validation, error mappingBusiness logic (mock the service)
@DataJpaTestCustom queries, constraints, mappingsSpring Data's own methods
@SpringBootTestOne end-to-end path per feature, securityEvery permutation

Habits worth forming

  • Name tests after behaviour: rejectsBlankTitle, not test2.
  • One reason to fail per test.
  • Assert on what the user of the code observes, not on internal calls, unless the call is the behaviour (an email being sent, for instance).
  • Fix flaky tests immediately; a suite people ignore is worse than none.
  • When you fix a bug, add the test that would have caught it — first.
  • Keep the whole suite fast enough that you run it before every commit.
Practice
  1. Write plain unit tests for your service with mocked repository and a fixed Clock.
  2. Write a @WebMvcTest covering 200, 400 (validation) and 404 for one controller.
  3. Write a @DataJpaTest for your custom queries.
  4. Add Testcontainers and run one full integration test against real Postgres.
  5. Add security tests: anonymous → 401, wrong role → 403, right role → 200.
  6. Time the suite. If it is over a minute, work out which tests are responsible and whether they need to be that heavy.
