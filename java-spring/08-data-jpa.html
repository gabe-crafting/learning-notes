Persistence with Spring Data JPA

Java objects in, rows out. JPA saves an enormous amount of boilerplate — and hides enough that you must know what it is doing.

The vocabulary

JPAThe specification: annotations and an API for object-relational mapping
HibernateThe implementation Spring Boot uses
Spring Data JPAA layer that generates repository implementations for you
EntityManagerHibernate's session: tracks loaded entities and flushes changes

Setup

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-jpa</artifactId>
</dependency>
<dependency>
    <groupId>org.postgresql</groupId>
    <artifactId>postgresql</artifactId>
    <scope>runtime</scope>
</dependency>
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/tasks
    username: ${DB_USER}
    password: ${DB_PASSWORD}
  jpa:
    hibernate:
      ddl-auto: validate        # see the warning below
    open-in-view: false         # turn this off — see lesson 9
    properties:
      hibernate:
        format_sql: true
logging:
  level:
    org.hibernate.SQL: DEBUG
ddl-auto update is convenient and dangerous: it silently alters your schema and never removes anything. Use validate with real migrations (lesson 10). create-drop is for tests only. Never point create or update at a production database.

An entity

@Entity
@Table(name = "tasks")
public class Task {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 200)
    private String title;

    @Column(columnDefinition = "text")
    private String description;

    @Enumerated(EnumType.STRING)               // never ORDINAL — reordering the enum corrupts data
    @Column(nullable = false)
    private TaskStatus status = TaskStatus.TODO;

    private LocalDate dueDate;

    @Column(nullable = false, updatable = false)
    private Instant createdAt;

    @Version                                    // optimistic locking
    private Long version;

    protected Task() { }                        // JPA needs a no-arg constructor

    public Task(String title, LocalDate dueDate) {
        this.title = title;
        this.dueDate = dueDate;
        this.createdAt = Instant.now();
    }

    // getters, and setters only for what may actually change
}

Rules that save pain later:

  • Entities are mutable classes, not records — JPA needs a no-arg constructor and proxies.
  • Use wrapper types (Long, not long) for ids so "not yet saved" is null.
  • Do not put @Data (Lombok) on an entity: the generated equals, hashCode and toString touch lazy associations and cause real bugs.
  • If you need equals, base it on a business key or the id with a null-safe check.

Auditing timestamps automatically

@EnableJpaAuditing            // on a @Configuration class

@EntityListeners(AuditingEntityListener.class)
@Entity
public class Task {
    @CreatedDate  private Instant createdAt;
    @LastModifiedDate private Instant updatedAt;
}

The repository

public interface TaskRepository extends JpaRepository<Task, Long> { }

That is the whole implementation. You now have:

save(entity)            saveAll(entities)
findById(id) → Optional findAll()          findAllById(ids)
existsById(id)          count()
deleteById(id)          delete(entity)     deleteAll()
findAll(Pageable)       findAll(Sort)

Derived query methods

Spring parses the method name and writes the query:

public interface TaskRepository extends JpaRepository<Task, Long> {

    List<Task> findByStatus(TaskStatus status);
    List<Task> findByStatusAndDueDateBefore(TaskStatus status, LocalDate date);
    List<Task> findByTitleContainingIgnoreCase(String fragment);
    Optional<Task> findFirstByOrderByCreatedAtDesc();
    List<Task> findByDueDateBetween(LocalDate from, LocalDate to);
    List<Task> findByStatusIn(Collection<TaskStatus> statuses);
    boolean existsByTitle(String title);
    long countByStatus(TaskStatus status);
    void deleteByStatus(TaskStatus status);
    Page<Task> findByStatus(TaskStatus status, Pageable pageable);
}

Keywords: And Or Between LessThan GreaterThan After Before IsNull IsNotNull Like Containing StartingWith In NotIn True False IgnoreCase OrderBy Distinct Top10 First.

A typo in a property name fails at startup, not at runtime — that is a feature. When a method name grows past about four conditions, switch to @Query.

@Query

// JPQL — operates on entities and fields, not tables and columns
@Query("select t from Task t where t.status = :status and t.dueDate < :date")
List<Task> findOverdue(@Param("status") TaskStatus status, @Param("date") LocalDate date);

// projection straight into a DTO
@Query("""
       select new com.example.tasks.dto.TaskSummary(t.status, count(t))
       from Task t group by t.status
       """)
List<TaskSummary> summariseByStatus();

// native SQL when you need database-specific features
@Query(value = "select * from tasks where title % :term", nativeQuery = true)
List<Task> fuzzySearch(@Param("term") String term);

@Modifying
@Transactional
@Query("update Task t set t.status = :status where t.id = :id")
int updateStatus(@Param("id") Long id, @Param("status") TaskStatus status);

Projections

// interface projection — Spring selects only these columns
public interface TaskTitleView {
    Long getId();
    String getTitle();
}
List<TaskTitleView> findByStatus(TaskStatus status);

// record projection
public record TaskSummary(TaskStatus status, long count) { }

Selecting whole entities when you need two fields is a common and avoidable waste.

Paging and sorting

Page<Task> page = repository.findAll(PageRequest.of(0, 20, Sort.by("dueDate").ascending()));

page.getContent();        // List<Task>
page.getTotalElements();  // total rows (costs an extra count query)
page.getTotalPages();
page.hasNext();

Slice<Task> slice = repository.findByStatus(status, pageable);   // no count query — cheaper

How save actually behaves

@Transactional
public void rename(Long id, String newTitle) {
    Task task = repository.findById(id).orElseThrow();
    task.setTitle(newTitle);
    // no save() call — the entity is "managed", and Hibernate flushes the change on commit
}

Inside a transaction, entities loaded from the repository are tracked; changing a field schedules an UPDATE. This is dirty checking, and it surprises people in both directions: forgetting that changes persist, and expecting them to persist outside a transaction, where they do not.

save() inserts when the id is null and merges otherwise. It returns the managed instance — always use the returned object.

Testing the repository

@DataJpaTest                          // only the JPA slice, with a test database, rolled back after each test
class TaskRepositoryTest {

    @Autowired TaskRepository repository;

    @Test
    void findsOverdueTasks() {
        repository.save(new Task("late", LocalDate.now().minusDays(1)));
        repository.save(new Task("future", LocalDate.now().plusDays(5)));

        List<Task> overdue = repository.findByDueDateBefore(LocalDate.now());

        assertThat(overdue).hasSize(1).extracting(Task::getTitle).containsExactly("late");
    }
}

Things that bite juniors

  • Every derived query returns a list you did not page. Page anything unbounded.
  • findAll() on a large table loads it all into memory.
  • Calling the repository in a loop instead of findAllById — one query beats a thousand.
  • Not looking at the SQL. Turn on org.hibernate.SQL logging and read what your code actually executes. Almost every performance problem is visible there.
Practice
  1. Turn your in-memory task store into a real @Entity + JpaRepository, running against H2 first.
  2. Add five derived queries, including one with paging and one with Containing.
  3. Write a @Query that returns a DTO projection of status counts.
  4. Turn on SQL logging and count the queries your list endpoint issues.
  5. Write a @DataJpaTest for two repository methods.
  6. Modify an entity inside a transactional service method without calling save, and confirm the change is persisted.
