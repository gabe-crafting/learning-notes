Dependency injection and beans

The mechanics of the container: how objects get into it, how they get wired together, and what to do when Spring cannot decide.

Declaring a bean

By annotation (component scanning)

@Component      // generic
@Service        // business logic          ─┐
@Repository     // data access              ├─ all are @Component with a clearer name
@Controller     // web layer (MVC views)    │
@RestController // web layer (JSON)        ─┘
@Service
public class TaskService {
    ...
}

They behave identically to the container, with two exceptions: @Repository translates persistence exceptions into Spring's DataAccessException hierarchy, and @RestController implies @ResponseBody. Use the specific one anyway — it tells a reader what the class is for.

By configuration method

@Configuration
public class AppConfig {

    @Bean
    public RestClient restClient() {
        return RestClient.builder()
                .baseUrl("https://api.example.com")
                .build();
    }

    @Bean
    public Clock clock() {
        return Clock.systemUTC();
    }
}

Use @Bean when you cannot annotate the class — third-party types, or when construction needs logic. The method name becomes the bean name.

Injecting dependencies

Constructor injection — the only one you should use

@Service
public class TaskService {

    private final TaskRepository repository;
    private final Clock clock;

    public TaskService(TaskRepository repository, Clock clock) {   // no @Autowired needed
        this.repository = repository;
        this.clock = clock;
    }
}

Since Spring 4.3, a class with a single constructor gets it autowired automatically.

Why constructor injection wins:

  • Fields can be final — the object is fully built and immutable.
  • The object cannot exist in a half-initialised state.
  • Tests can construct it with new TaskService(mockRepo, fixedClock) — no Spring at all.
  • A constructor with eight parameters is visibly wrong, which is useful feedback about the design.

The alternatives, and why not

@Autowired
private TaskRepository repository;      // field injection: cannot be final, untestable
                                        // without reflection, hides how many dependencies exist

@Autowired
public void setRepository(TaskRepository r) { ... }   // setter: for genuinely optional deps only

Field injection is common in older tutorials and IntelliJ will warn about it. Do not write new code with it.

Lombok, if the project uses it

@Service
@RequiredArgsConstructor            // generates a constructor for all final fields
public class TaskService {
    private final TaskRepository repository;
    private final Clock clock;
}

When there is more than one candidate

public interface NotificationSender { void send(String to, String message); }

@Component class EmailSender implements NotificationSender { ... }
@Component class SmsSender   implements NotificationSender { ... }

@Service
public class AlertService {
    public AlertService(NotificationSender sender) { ... }   // which one?!
}
// NoUniqueBeanDefinitionException: expected single matching bean but found 2

Four ways out:

// 1. mark a default
@Component @Primary class EmailSender implements NotificationSender { ... }

// 2. name the one you want
public AlertService(@Qualifier("smsSender") NotificationSender sender) { ... }

// 3. choose by configuration
@Component
@ConditionalOnProperty(name = "notifications.channel", havingValue = "sms")
class SmsSender implements NotificationSender { ... }

// 4. inject them all
public AlertService(List<NotificationSender> senders) { ... }        // send to every channel
public AlertService(Map<String, NotificationSender> byName) { ... }  // keyed by bean name

That last one is a genuinely nice pattern for strategies: add a new implementation and it joins the list without touching existing code.

Bean scopes

singleton (default)One instance for the whole application
prototypeA new instance every time it is injected or requested
requestOne per HTTP request (web apps)
sessionOne per HTTP session
@Service
@Scope("prototype")
public class ReportBuilder { ... }
Singletons are shared across threads Every request uses the same @Service instance. Never put per-request state in a field. Dependencies in final fields, everything else as method parameters and local variables.

Lifecycle

@Component
public class CacheWarmer {

    @PostConstruct                 // after construction and injection
    void warmUp() { ... }

    @PreDestroy                    // on graceful shutdown
    void flush() { ... }
}

@Component
public class Startup implements ApplicationRunner {
    @Override
    public void run(ApplicationArguments args) {   // after the context is fully ready
        ...
    }
}

Do not do real work in a constructor — the object may not be fully wired yet, and failures there produce confusing startup errors.

Circular dependencies

A needs B, B needs A
→ BeanCurrentlyInCreationException (Boot 2.6+ rejects this by default)

The fix is not spring.main.allow-circular-references=true. A cycle means the responsibilities are wrong: extract the shared logic into a third bean, or use an event so one side no longer depends on the other.

Seeing what is in the container

@Component
class BeanPrinter implements ApplicationRunner {
    private final ApplicationContext ctx;
    BeanPrinter(ApplicationContext ctx) { this.ctx = ctx; }

    @Override public void run(ApplicationArguments args) {
        Arrays.stream(ctx.getBeanDefinitionNames()).sorted().forEach(System.out::println);
    }
}
# or ask Boot why it configured something
./mvnw spring-boot:run -Ddebug
# prints the auto-configuration report: what matched, what did not, and why

The errors you will actually see

MessageUsual cause
NoSuchBeanDefinitionExceptionMissing @Component/@Bean, or the class is outside the scanned packages
NoUniqueBeanDefinitionExceptionTwo implementations — use @Primary or @Qualifier
BeanCurrentlyInCreationExceptionCircular dependency
NullPointerException on an injected fieldThe object was created with new instead of coming from the container

That last one is worth internalising: injection only happens for beans Spring created. If you write new TaskService() yourself, nothing is injected.

Practice
  1. Build TaskController → TaskService → InMemoryTaskRepository with constructor injection, all three as beans.
  2. Add a second TaskRepository implementation, watch the startup fail, then fix it with @Primary and again with @Qualifier.
  3. Define a Clock bean and inject it instead of calling LocalDate.now(). Explain why this makes the service testable.
  4. Inject List<NotificationSender> and have a service call every implementation.
  5. Print every bean name at startup and find three you never declared.
  6. Create a deliberate circular dependency, read the error, then break the cycle properly.
