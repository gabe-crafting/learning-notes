Packaging and deployment

From source on your laptop to a container running somewhere else, configured by the environment rather than by edits.

The jar

./mvnw clean package
java -jar target/tasks-0.0.1-SNAPSHOT.jar

spring-boot-maven-plugin produces an executable jar containing your classes, every dependency and an embedded Tomcat. One file, one command, no application server to install.

java -jar app.jar --server.port=9090
java -jar app.jar --spring.profiles.active=prod
java -Xmx512m -jar app.jar

Dockerfile

# ---- build stage ----
FROM eclipse-temurin:21-jdk-alpine AS build
WORKDIR /app

COPY .mvn/ .mvn/
COPY mvnw pom.xml ./
RUN ./mvnw dependency:go-offline -B          # cached unless pom.xml changes

COPY src/ src/
RUN ./mvnw clean package -DskipTests

# ---- runtime stage ----
FROM eclipse-temurin:21-jre-alpine
WORKDIR /app

RUN addgroup -S app && adduser -S app -G app
USER app                                      # never run as root

COPY --from=build /app/target/*.jar app.jar

EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
docker build -t tasks:1.0 .
docker run -p 8080:8080 -e SPRING_PROFILES_ACTIVE=prod -e DB_PASSWORD=... tasks:1.0

The two stages matter: the final image contains a JRE and your jar, not a JDK, Maven and the whole build cache — roughly 200 MB instead of 800 MB, with a much smaller attack surface.

Or skip the Dockerfile

./mvnw spring-boot:build-image -Dspring-boot.build-image.imageName=tasks:1.0

Boot builds an optimised image with Cloud Native Buildpacks — layered, non-root, sensible JVM defaults, no Dockerfile to maintain.

Compose for local end-to-end

services:
  db:
    image: postgres:16
    environment:
      POSTGRES_DB: tasks
      POSTGRES_USER: tasks
      POSTGRES_PASSWORD: tasks
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U tasks"]
      interval: 5s
      retries: 5

  app:
    build: .
    depends_on:
      db:
        condition: service_healthy
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://db:5432/tasks
      SPRING_DATASOURCE_USERNAME: tasks
      SPRING_DATASOURCE_PASSWORD: tasks
      SPRING_PROFILES_ACTIVE: docker
    ports:
      - "8080:8080"

Note the hostname db: inside the compose network, service names resolve. localhost from the app container means the container itself, which is the classic first mistake.

Configuration in production

SPRING_DATASOURCE_URL=jdbc:postgresql://prod-host:5432/tasks
SPRING_DATASOURCE_USERNAME=tasks
SPRING_DATASOURCE_PASSWORD=***          # from the platform's secret store
SPRING_PROFILES_ACTIVE=prod
APP_JWT_SECRET=***

Every property has an environment-variable form: uppercase, dots and hyphens to underscores. The same image runs in every environment, differing only by the variables passed to it. That is the property you are protecting — an image that has to be rebuilt to change an environment is not deployable.

JVM settings in a container

ENV JAVA_OPTS="-XX:MaxRAMPercentage=75 -XX:+ExitOnOutOfMemoryError"
ENTRYPOINT ["sh", "-c", "java $JAVA_OPTS -jar app.jar"]

Modern JVMs are container-aware, but sizing the heap as a percentage of the container limit rather than a fixed -Xmx keeps it correct when the limit changes.

A production checklist

  • ddl-auto: validate, schema owned by Flyway.
  • No secrets in the image or the repository.
  • Actuator: only health and info exposed publicly.
  • Graceful shutdown enabled.
  • Connection pool sized deliberately (spring.datasource.hikari.maximum-pool-size) — bigger is not better; the database has limits.
  • Timeouts on every outbound call.
  • Logs to stdout, structured, no personal data.
  • Health and readiness probes wired to the orchestrator.
  • Resource limits set on the container.
  • A rollback plan — know how to deploy the previous image.

Continuous integration

# .github/workflows/build.yml
name: build
on:
  push:
    branches: [main]
  pull_request:

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          java-version: '21'
          distribution: 'temurin'
          cache: maven
      - run: ./mvnw -B verify
      - uses: actions/upload-artifact@v4
        with:
          name: jar
          path: target/*.jar

The bar for a pull request: it compiles, the tests pass, and the artifact builds. Testcontainers works on GitHub Actions runners, so integration tests can run here too.

Deployment strategies, briefly

RollingReplace instances gradually. The default in Kubernetes. Requires that two versions can run at once — which is why migrations must be backwards compatible.
Blue-greenTwo environments, switch traffic at once. Instant rollback, double the resources.
CanarySend a small percentage of traffic to the new version first.

Where a small service can run

  • A single VM with Docker Compose and a reverse proxy — perfectly respectable, and the cheapest way to learn.
  • Managed container platforms — Railway, Render, Fly.io, Google Cloud Run: push an image, get a URL.
  • Kubernetes — what most companies with several services use. Learn Docker thoroughly first.

Common first-deployment failures

SymptomUsual cause
Works locally, cannot reach the database in DockerUsing localhost instead of the service name
Container exits immediatelyRead the logs — usually a missing required property
OOMKilledHeap larger than the container memory limit
Migration fails on startupAn edited migration, or a schema that drifted
Requests dropped during deployNo graceful shutdown, or no readiness probe
Frontend gets CORS errorsProduction origin not in the allowed list
Practice
  1. Build the jar and run it with three different profiles from the command line.
  2. Write the multi-stage Dockerfile and compare the image size against a single-stage one.
  3. Run the app and Postgres together with Docker Compose, configured entirely by environment variables.
  4. Try spring-boot:build-image and compare with your Dockerfile.
  5. Set up a GitHub Actions workflow that builds and tests on every push.
  6. Deploy to a free container platform and hit the health endpoint over the internet.
