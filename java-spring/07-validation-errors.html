Validation and error handling

Reject bad input at the door, and make every failure produce a response a client can actually use.

A custom constraint

@Target({ElementType.FIELD, ElementType.RECORD_COMPONENT})
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = UniqueEmailValidator.class)
public @interface UniqueEmail {
    String message() default "Email is already registered";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

@Component
public class UniqueEmailValidator implements ConstraintValidator<UniqueEmail, String> {

    private final UserRepository repository;
    public UniqueEmailValidator(UserRepository repository) { this.repository = repository; }

    @Override
    public boolean isValid(String email, ConstraintValidatorContext context) {
        return email == null || !repository.existsByEmail(email);
    }
}

What happens without a handler

{
  "timestamp": "2026-09-05T10:12:31.123+00:00",
  "status": 400,
  "error": "Bad Request",
  "path": "/api/users"
}

Correct status, useless body: the client cannot tell which field was wrong. Fix that once, globally.

A global exception handler

public record ApiError(
        Instant timestamp,
        int status,
        String error,
        String message,
        String path,
        Map<String, String> fieldErrors) { }
@RestControllerAdvice
public class GlobalExceptionHandler {

    private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);

    @ExceptionHandler(MethodArgumentNotValidException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public ApiError handleValidation(MethodArgumentNotValidException ex, HttpServletRequest req) {
        Map<String, String> fields = new LinkedHashMap<>();
        for (FieldError fe : ex.getBindingResult().getFieldErrors()) {
            fields.put(fe.getField(), fe.getDefaultMessage());
        }
        return new ApiError(Instant.now(), 400, "Bad Request",
                            "Validation failed", req.getRequestURI(), fields);
    }

    @ExceptionHandler(TaskNotFoundException.class)
    @ResponseStatus(HttpStatus.NOT_FOUND)
    public ApiError handleNotFound(TaskNotFoundException ex, HttpServletRequest req) {
        return new ApiError(Instant.now(), 404, "Not Found",
                            ex.getMessage(), req.getRequestURI(), Map.of());
    }

    @ExceptionHandler(IllegalStateException.class)
    @ResponseStatus(HttpStatus.CONFLICT)
    public ApiError handleConflict(IllegalStateException ex, HttpServletRequest req) {
        return new ApiError(Instant.now(), 409, "Conflict",
                            ex.getMessage(), req.getRequestURI(), Map.of());
    }

    @ExceptionHandler(Exception.class)
    @ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)
    public ApiError handleEverythingElse(Exception ex, HttpServletRequest req) {
        log.error("Unhandled exception on {}", req.getRequestURI(), ex);   // log the detail...
        return new ApiError(Instant.now(), 500, "Internal Server Error",
                            "Something went wrong", req.getRequestURI(), Map.of());
        // ...but do not leak stack traces or SQL to the client
    }
}

Domain exceptions

public class TaskNotFoundException extends RuntimeException {
    public TaskNotFoundException(Long id) {
        super("Task not found: " + id);
    }
}

public class TaskAlreadyCompletedException extends RuntimeException { ... }

The service throws them; the handler decides the HTTP status. That keeps the service free of web concerns while still producing correct responses.

A shortcut for small applications:

@ResponseStatus(HttpStatus.NOT_FOUND)
public class TaskNotFoundException extends RuntimeException { ... }

It works, but it couples a domain class to HTTP. Fine early, worth removing later.

Problem Detail (RFC 7807)

Spring 6 supports the standard error format, which is a good default for new APIs:

@ExceptionHandler(TaskNotFoundException.class)
public ProblemDetail handle(TaskNotFoundException ex) {
    ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
    problem.setTitle("Task not found");
    problem.setType(URI.create("https://api.example.com/errors/task-not-found"));
    problem.setProperty("taskId", ex.getId());
    return problem;
}
spring:
  mvc:
    problemdetails:
      enabled: true       # makes Spring's built-in errors use this format too

Exceptions worth handling explicitly

MethodArgumentNotValidExceptionInvalid @RequestBody → 400
ConstraintViolationExceptionInvalid path/query parameter → 400
HttpMessageNotReadableExceptionMalformed JSON → 400
MethodArgumentTypeMismatchException/tasks/abc where a Long was expected → 400
MissingServletRequestParameterExceptionRequired parameter absent → 400
DataIntegrityViolationExceptionUnique or FK constraint hit → 409
AccessDeniedExceptionNot permitted → 403

Rules that keep errors useful

  • Log the detail, return the summary. Stack traces belong in the log, never in the response.
  • Never echo internals — SQL, class names, file paths, library versions. They are a gift to an attacker.
  • Be consistent. One error shape for the whole API, so clients can parse it once.
  • Say what to do. "Validation failed" plus the field errors beats "Bad request".
  • Do not leak whether an account exists on login or password reset — the same generic message either way.
  • Include a correlation id in both the log line and the response so a support ticket maps to a log entry.
Practice
  1. Add validation annotations to your create and update DTOs and confirm a bad request returns 400.
  2. Write a @RestControllerAdvice returning a consistent ApiError, including field errors.
  3. Create TaskNotFoundException and map it to 404; verify with curl -i.
  4. Write a custom @UniqueEmail constraint backed by the repository.
  5. Post malformed JSON and a wrong-typed path variable; handle both explicitly.
  6. Convert your handler to return ProblemDetail and compare the two response formats.
