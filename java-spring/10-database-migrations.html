Databases and migrations

Running a real database locally, and changing its schema in a way that works for the whole team and for production.

Postgres with Docker Compose

# compose.yaml at the project root
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_DB: tasks
      POSTGRES_USER: tasks
      POSTGRES_PASSWORD: tasks
    ports:
      - "5432:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data

volumes:
  pgdata:
docker compose up -d          # start
docker compose logs -f db     # watch
docker compose down           # stop
docker compose down -v        # stop and delete the data volume

Spring Boot 3.1+ can even start it for you: add spring-boot-docker-compose and the app boots the compose file and wires the datasource automatically during development.

Connecting

spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/tasks
    username: tasks
    password: tasks
  jpa:
    hibernate:
      ddl-auto: validate
    open-in-view: false

H2 for quick experiments

spring:
  datasource:
    url: jdbc:h2:mem:testdb
  h2:
    console:
      enabled: true       # browse at /h2-console

Fine for a first afternoon and for some tests, but H2 is not Postgres: different types, different SQL dialect, different constraint behaviour. Develop against the database you deploy against — Testcontainers (lesson 12) makes that easy.

Why migrations

ddl-auto: update looks convenient and then:

  • It never drops or renames anything — your schema silently accumulates dead columns.
  • It cannot express a data change ("split name into first and last").
  • It is not reviewable: nobody can see in a pull request what will happen to the production schema.
  • It is not reproducible — the result depends on what the schema happened to be already.

Migrations put the schema in version control as ordered, immutable SQL scripts, applied exactly once, in order, on every environment.

Flyway

<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-database-postgresql</artifactId>
</dependency>
src/main/resources/db/migration/
├── V1__create_tasks_table.sql
├── V2__add_project_table.sql
├── V3__add_due_date_index.sql
└── V4__backfill_status.sql

Naming: V + version + __ (two underscores) + description. Flyway runs pending scripts at startup, in order, and records each one in a flyway_schema_history table.

-- V1__create_tasks_table.sql
create table tasks (
    id          bigserial primary key,
    title       varchar(200) not null,
    description text,
    status      varchar(20)  not null default 'TODO',
    due_date    date,
    created_at  timestamptz  not null default now(),
    version     bigint       not null default 0
);

create index idx_tasks_status on tasks (status);
create index idx_tasks_due_date on tasks (due_date) where due_date is not null;
-- V2__add_project_table.sql
create table projects (
    id   bigserial primary key,
    name varchar(200) not null unique
);

alter table tasks add column project_id bigint references projects (id);
create index idx_tasks_project_id on tasks (project_id);
Never edit an applied migration Flyway stores a checksum. Changing V1 after it has run anywhere fails the next startup with a validation error. Fix mistakes by adding V5.

Configuration

spring:
  flyway:
    enabled: true
    baseline-on-migrate: true      # for an existing database that predates Flyway
    locations: classpath:db/migration
  jpa:
    hibernate:
      ddl-auto: validate           # Hibernate checks the schema matches the entities, changes nothing

That pairing — Flyway owns the schema, Hibernate validates it — is the standard production setup. If an entity and the schema disagree, the application refuses to start, which is exactly when you want to find out.

Liquibase

The main alternative, using XML/YAML changesets instead of raw SQL, with built-in rollback support. Same idea; pick whichever the team uses. Flyway is simpler and more common in Boot projects.

Writing migrations safely

ChangeSafe approach
Add a columnAdd it nullable, or with a default. Adding not null without a default to a populated table fails.
Rename a columnAdd new → backfill → switch the code → drop old, across several releases.
Drop a columnOnly after no deployed version still reads it.
Add an indexOn a big table use create index concurrently (outside a transaction).
Change a typeNew column, backfill, swap. In-place changes lock the table.

The principle: a migration must be compatible with both the old and the new version of the application, because during a rolling deploy both are running.

Seed and reference data

-- V5__seed_default_tags.sql
insert into tags (name) values ('home'), ('work'), ('urgent')
on conflict (name) do nothing;         -- idempotent

Reference data belongs in migrations. Demo data belongs in a dev-profile CommandLineRunner or a separate script — never in a migration that also runs in production.

Indexes, briefly

  • Index every foreign key you query by, and every column used in a where or order by on a large table.
  • A composite index (status, due_date) serves queries filtering on status alone, but not on due_date alone — leading columns matter.
  • Indexes cost write throughput and disk. Do not index everything.
  • Measure with explain analyze select ... in psql before and after.

Useful psql

docker compose exec db psql -U tasks -d tasks

\dt                      list tables
\d tasks                 describe a table, with indexes and constraints
\di                      list indexes
select * from flyway_schema_history;
explain analyze select * from tasks where status = 'TODO';
\q
Practice
  1. Start Postgres with Docker Compose and point your app at it.
  2. Add Flyway, write V1 creating your tables, and set ddl-auto: validate.
  3. Add a column via V2, restart, and inspect flyway_schema_history.
  4. Deliberately edit V1 after it ran, read the checksum error, then revert it.
  5. Make an entity field disagree with the schema and watch startup validation fail.
  6. Write a migration that renames a column safely across three steps, and describe which release each step goes in.
  7. Add an index for your most common query and compare explain analyze before and after.
