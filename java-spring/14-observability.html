Logging, Actuator and metrics

When something breaks in production you cannot attach a debugger. What you have is logs, health checks and metrics — so make them good before you need them.

Logging

Boot ships SLF4J as the API and Logback as the implementation. Always code against SLF4J.

public class TaskService {

    private static final Logger log = LoggerFactory.getLogger(TaskService.class);

    public void complete(Long id) {
        log.info("Completing task {}", id);                  // placeholders, not concatenation
        try {
            ...
        } catch (Exception e) {
            log.error("Failed to complete task {}", id, e);   // exception LAST, no placeholder
        }
    }
}
@Slf4j                       // Lombok, if the project uses it
public class TaskService { }

Why {} matters: with concatenation the string is built even when the level is disabled. With placeholders it is not, and structured log processors can parse the parameters separately.

Levels

ERRORSomething failed and needs attention. Someone may be paged.
WARNUnexpected but handled — a retry, a fallback, a deprecated call.
INFONotable business events: started, order placed, user registered.
DEBUGDetail for diagnosing, off in production by default.
TRACEVery fine-grained; rarely enabled.
logging:
  level:
    root: INFO
    com.example.tasks: DEBUG
    org.hibernate.SQL: DEBUG
  file:
    name: logs/app.log
  logback:
    rollingpolicy:
      max-file-size: 10MB
      max-history: 7

What to log, and what never to

  • Do log the start and outcome of significant operations, with identifiers you can search (order id, user id, correlation id).
  • Do log the full exception object — not e.getMessage(), which throws away the stack trace.
  • Do not log passwords, tokens, card numbers, or personal data beyond an id. GDPR applies to log files.
  • Do not log inside tight loops, or at INFO for every request detail — noise makes the useful lines invisible and costs real money in log storage.
  • Do not use System.out.println. It bypasses levels, formatting and appenders.

Correlation ids (MDC)

@Component
public class CorrelationIdFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {

        String id = Optional.ofNullable(req.getHeader("X-Correlation-Id"))
                            .orElse(UUID.randomUUID().toString());
        MDC.put("correlationId", id);
        res.setHeader("X-Correlation-Id", id);
        try {
            chain.doFilter(req, res);
        } finally {
            MDC.clear();                    // essential: threads are reused
        }
    }
}
logging:
  pattern:
    console: "%d{HH:mm:ss} [%X{correlationId}] %-5level %logger{36} - %msg%n"

Now every log line from one request shares an id, and the client has it too — so a support ticket maps directly to the exact lines. Spring's Micrometer Tracing does this and more (span ids across services) if you add it.

Structured logging

logging:
  structured:
    format:
      console: ecs        # Boot 3.4+: JSON output for log aggregators

In containerised environments log JSON to stdout and let the platform collect it. Do not write log files inside a container.

Actuator

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,prometheus     # expose deliberately, never "*" in production
  endpoint:
    health:
      show-details: when-authorized
      probes:
        enabled: true
  info:
    env:
      enabled: true
/actuator/healthUP/DOWN, aggregating database, disk and custom checks
/actuator/health/liveness, /readinessKubernetes probes
/actuator/infoBuild version, git commit
/actuator/metricsJVM, HTTP, datasource metrics
/actuator/prometheusMetrics in Prometheus format
/actuator/loggersRead and change log levels at runtime
/actuator/env, /heapdump, /threaddumpPowerful and sensitive — never expose publicly
Actuator endpoints are an attack surface /env can reveal configuration, /heapdump can reveal everything in memory. Expose only health and info publicly, secure the rest behind authentication or bind them to an internal management port (management.server.port).

A custom health check

@Component
public class WeatherApiHealthIndicator implements HealthIndicator {

    private final WeatherClient client;

    @Override
    public Health health() {
        try {
            client.ping();
            return Health.up().withDetail("provider", "weather-api").build();
        } catch (Exception e) {
            return Health.down(e).build();
        }
    }
}

Keep health checks fast and shallow. A check that calls three downstream services turns their outage into yours, because your orchestrator will restart a perfectly healthy pod.

Metrics with Micrometer

@Service
public class TaskService {

    private final Counter completed;
    private final Timer processing;

    public TaskService(MeterRegistry registry) {
        this.completed = Counter.builder("tasks.completed")
                                .description("Tasks marked done")
                                .register(registry);
        this.processing = registry.timer("tasks.processing");
    }

    public void complete(Long id) {
        processing.record(() -> {
            ...
            completed.increment();
        });
    }
}
@Timed(value = "orders.place", percentiles = {0.5, 0.95, 0.99})
public void placeOrder(...) { }

Boot already records HTTP request counts and latencies per endpoint and status, JVM memory, GC, thread counts and connection-pool usage. Add your own only for business events worth graphing.

Cardinality warning: never use a user id, order id or free-text value as a metric tag. Each distinct value creates a separate time series and will exhaust your monitoring system.

The four questions a service should answer

  1. Is it up? — health endpoint, uptime.
  2. Is it fast? — latency percentiles (p95, p99, not averages).
  3. Is it failing? — error rate by endpoint and status.
  4. Why? — logs with correlation ids, and traces if you have them.

Graceful shutdown

server:
  shutdown: graceful
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s

On SIGTERM the server stops accepting new requests and finishes in-flight ones. Without this, a deployment drops requests every time.

Practice
  1. Replace every System.out.println in your project with a properly levelled logger.
  2. Add the correlation-id filter and confirm the id appears in every line of one request and in the response header.
  3. Enable Actuator, expose health and info, and add build info to /actuator/info.
  4. Write a custom HealthIndicator and make it report DOWN on purpose.
  5. Add a counter and a timer for a business operation and read them from /actuator/metrics.
  6. Change a log level at runtime through /actuator/loggers without restarting.
