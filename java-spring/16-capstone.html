Capstone project

Build one complete service that uses everything in this course. Finished and deployed beats perfect and abandoned — this is the project you put on your CV.

The brief: a task manager API

Users register and log in. Each user owns projects; each project holds tasks. Tasks have a status, a due date, tags, and can be assigned to a user. The API is JSON over HTTP, authenticated with JWT, backed by Postgres, tested, containerised and deployed.

The domain

User        id, email (unique), passwordHash, displayName, roles, createdAt
Project     id, name, description, owner → User, createdAt, archived
Task        id, title, description, status, priority, dueDate,
            project → Project, assignee → User (nullable), tags, createdAt, completedAt
Tag         id, name (unique)

TaskStatus  TODO, IN_PROGRESS, DONE, CANCELLED
Priority    LOW, MEDIUM, HIGH

Build it in these steps

1 — Skeleton (lesson 2)

  • Generate with web, validation, JPA, security, Flyway, Postgres driver, devtools, test.
  • Package by feature: auth, user, project, task, common.
  • Commit. Then commit after every step below.

2 — Database (lesson 10)

  • compose.yaml with Postgres; docker compose up -d.
  • Flyway V1__initial_schema.sql creating all five tables with constraints and indexes.
  • ddl-auto: validate, open-in-view: false.

3 — Entities and repositories (lessons 8–9)

  • Entities matching the schema; every association LAZY.
  • Repositories with the derived queries you need; page anything that returns a collection.
  • @DataJpaTest for each custom query.

4 — The task feature end to end (lessons 5–7)

  • Request and response records with validation annotations.
  • Service holding the rules; controller thin.
  • @RestControllerAdvice returning a consistent error body.
  • Rules worth enforcing: cannot complete an already-completed task (409), cannot create a task in an archived project (409), due date not in the past (400).

5 — Authentication (lesson 11)

  • Register with BCrypt hashing; reject duplicate emails with 409.
  • Login returning a JWT; a filter that authenticates from the header.
  • Everything except /api/auth/** and /actuator/health requires authentication.
  • Ownership checks: a user may only see and modify their own projects and tasks. Test the negative case — this is where real APIs leak data.

6 — Tests (lesson 12)

  • Unit tests for every business rule, with a fixed Clock.
  • @WebMvcTest per controller: happy path, validation failure, 404, 403.
  • One @SpringBootTest with Testcontainers covering register → login → create project → create task → complete.

7 — Production readiness (lessons 14–15)

  • Logging with correlation ids; no secrets in logs.
  • Actuator health and info only.
  • Dockerfile, Compose, GitHub Actions, deployed somewhere with a public URL.
  • A README: what it is, how to run it, example requests.

Sketches to get you moving

-- V1__initial_schema.sql (extract)
create table users (
    id            bigserial primary key,
    email         varchar(255) not null unique,
    password_hash varchar(100) not null,
    display_name  varchar(100) not null,
    created_at    timestamptz  not null default now()
);

create table projects (
    id          bigserial primary key,
    name        varchar(200) not null,
    description text,
    owner_id    bigint       not null references users (id),
    archived    boolean      not null default false,
    created_at  timestamptz  not null default now()
);
create index idx_projects_owner on projects (owner_id);

create table tasks (
    id           bigserial primary key,
    title        varchar(200) not null,
    description  text,
    status       varchar(20)  not null default 'TODO',
    priority     varchar(10)  not null default 'MEDIUM',
    due_date     date,
    project_id   bigint       not null references projects (id) on delete cascade,
    assignee_id  bigint       references users (id),
    created_at   timestamptz  not null default now(),
    completed_at timestamptz,
    version      bigint       not null default 0
);
create index idx_tasks_project on tasks (project_id);
create index idx_tasks_status  on tasks (status);
@Service
@Transactional(readOnly = true)
public class TaskService {

    private final TaskRepository tasks;
    private final ProjectRepository projects;
    private final Clock clock;

    @Transactional
    public TaskResponse create(Long projectId, CreateTaskRequest request, String userEmail) {
        Project project = projects.findById(projectId)
                .orElseThrow(() -> new ProjectNotFoundException(projectId));

        if (!project.getOwner().getEmail().equals(userEmail)) {
            throw new AccessDeniedException("Not your project");        // → 403
        }
        if (project.isArchived()) {
            throw new ProjectArchivedException(projectId);              // → 409
        }

        Task task = new Task(request.title(), project);
        task.setDueDate(request.dueDate());
        task.setPriority(request.priority());

        return TaskResponse.from(tasks.save(task));
    }

    @Transactional
    public TaskResponse complete(Long id, String userEmail) {
        Task task = tasks.findById(id).orElseThrow(() -> new TaskNotFoundException(id));
        requireOwner(task, userEmail);

        if (task.getStatus() == TaskStatus.DONE) {
            throw new TaskAlreadyCompletedException(id);                // → 409
        }
        task.setStatus(TaskStatus.DONE);
        task.setCompletedAt(Instant.now(clock));
        return TaskResponse.from(task);
    }
}

Stretch goals, in order of value

  1. OpenAPI docs — add springdoc-openapi-starter-webmvc-ui and get interactive documentation at /swagger-ui.html. Reviewers love this.
  2. Search and filtering with Specification for dynamic queries.
  3. Refresh tokens and logout.
  4. Email notifications for tasks due tomorrow, via @Scheduled.
  5. Caching with @Cacheable on the stats endpoint.
  6. Rate limiting on the login endpoint.
  7. A small frontend — even a single HTML page — so it is demonstrable.

Then what

You have finished both courses. The useful next moves, roughly in order:

  • SQL properly — joins, indexes, execution plans, transactions and isolation levels. It pays off forever.
  • Read Spring's own documentation. It is genuinely good, and being able to read reference docs instead of blog posts is a professional skill.
  • Build a second project in a domain you find interesting, without a tutorial.
  • Contribute a small fix to an open-source Spring project to practise working in someone else's codebase.
  • Explain your capstone out loud — the design decisions and the trade-offs. That is what a job interview actually asks.
Practice

The whole page is the practice. Do it in the seven steps, commit after each, and do not skip the tests — the point of the capstone is to prove to yourself that you can finish something complete.
