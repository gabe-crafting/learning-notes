Configuration and profiles

The same jar has to run on your laptop, in the test environment and in production. Configuration is what makes that possible — and secrets are what make it dangerous.

application.yml

spring:
  application:
    name: tasks
  datasource:
    url: jdbc:postgresql://localhost:5432/tasks
    username: tasks
    password: dev-only
  jpa:
    hibernate:
      ddl-auto: validate
    show-sql: false

server:
  port: 8080
  servlet:
    context-path: /api

logging:
  level:
    root: INFO
    com.example.tasks: DEBUG
    org.hibernate.SQL: DEBUG

app:                        # your own properties live under your own prefix
  max-tasks-per-user: 100
  cleanup-after: 30d
  features:
    notifications: true

The equivalent .properties syntax flattens the tree: spring.datasource.url=.... Both work; YAML is easier to read once there are more than a dozen entries.

Reading a property

@Value for one-offs

@Service
public class TaskService {

    private final int maxTasks;

    public TaskService(@Value("${app.max-tasks-per-user:50}") int maxTasks) {
        this.maxTasks = maxTasks;      // :50 is the default when the property is absent
    }
}

@ConfigurationProperties for groups — prefer this

@ConfigurationProperties(prefix = "app")
public record AppProperties(
        int maxTasksPerUser,
        Duration cleanupAfter,
        Features features) {

    public record Features(boolean notifications) { }
}
@SpringBootApplication
@EnableConfigurationProperties(AppProperties.class)
public class TasksApplication { ... }
@Service
public class TaskService {
    private final AppProperties props;

    public TaskService(AppProperties props) { this.props = props; }

    void check(int count) {
        if (count >= props.maxTasksPerUser()) throw new TooManyTasksException();
    }
}

Advantages over @Value: typed (a Duration parses 30d for you), grouped, validated, discoverable, and IDE-completable. Note the relaxed binding — max-tasks-per-user in YAML maps to maxTasksPerUser in Java.

Validating configuration at startup

@Validated
@ConfigurationProperties(prefix = "app")
public record AppProperties(
        @Min(1) @Max(1000) int maxTasksPerUser,
        @NotNull Duration cleanupAfter) { }

A bad value now fails the application at startup with a clear message, instead of at 3am with a NumberFormatException.

Profiles

A profile is a named set of configuration. Files are picked up by convention:

application.yml            always loaded
application-dev.yml        loaded when the "dev" profile is active
application-test.yml
application-prod.yml
# application.yml
spring:
  profiles:
    default: dev

---
# a profile-specific block in the same file also works
spring:
  config:
    activate:
      on-profile: prod
  jpa:
    show-sql: false
logging:
  level:
    root: WARN

Activating one:

java -jar app.jar --spring.profiles.active=prod
SPRING_PROFILES_ACTIVE=prod java -jar app.jar
./mvnw spring-boot:run -Dspring-boot.run.profiles=dev

Profile-specific beans

@Component
@Profile("dev")
public class LoggingEmailSender implements EmailSender {      // just logs
    public void send(...) { log.info("would send: {}", message); }
}

@Component
@Profile("prod")
public class SmtpEmailSender implements EmailSender { ... }

@Profile("!prod")     // everything except prod
@Profile({"dev", "test"})

Use profiles for environment differences. Do not use them for feature toggles that change per customer or per request — those belong in properties or a feature-flag service.

Where configuration comes from, and who wins

Spring merges many sources. Later in this list overrides earlier:

  1. application.yml packaged inside the jar
  2. application-{profile}.yml inside the jar
  3. application.yml in the working directory or ./config/
  4. OS environment variables
  5. JVM system properties (-Dserver.port=9090)
  6. Command-line arguments (--server.port=9090)

Environment variables use a relaxed spelling: SPRING_DATASOURCE_URL sets spring.datasource.url. That is how containers and cloud platforms configure your app without touching the jar.

Secrets

Never commit a password, key or token Not in application.yml, not "temporarily", not in a test. Git remembers forever, and repository scanners find them within minutes of a push. 
# application.yml — reference, do not embed
spring:
  datasource:
    url: ${DATABASE_URL}
    username: ${DATABASE_USER}
    password: ${DATABASE_PASSWORD}       # fails fast at startup if unset

app:
  api-key: ${API_KEY:}                    # empty default, for local runs

Locally, set them in your IDE run configuration or a .env file that is git-ignored. In production the platform injects them (Kubernetes secrets, AWS Parameter Store, Vault). If a secret does leak, rotate it — removing the commit is not enough.

Configuration in tests

@SpringBootTest
@ActiveProfiles("test")
@TestPropertySource(properties = "app.max-tasks-per-user=5")
class TaskServiceTest { ... }

src/test/resources/application-test.yml is the natural home for test settings — an in-memory database, verbose logging, short timeouts.

Logging configuration

logging:
  level:
    root: INFO
    com.example.tasks: DEBUG
    org.springframework.web: DEBUG        # see request mapping decisions
    org.hibernate.SQL: DEBUG              # see the generated SQL
    org.hibernate.orm.jdbc.bind: TRACE    # ...and the bound parameters
  pattern:
    console: "%d{HH:mm:ss} %-5level %logger{36} - %msg%n"
  file:
    name: logs/app.log

Those Hibernate lines are the single most useful debugging tool in the next few lessons.

Common mistakes

  • Tabs in YAML — the file will not parse. Spaces only.
  • Hard-coding localhost or a port in Java code instead of a property.
  • Using @Value in a field rather than a constructor parameter, then wondering why it is null in a unit test.
  • Defining the same key in application.properties and application.yml — properties wins, silently.
  • Putting production credentials in a profile "just for now".
Practice
  1. Move every hard-coded value in your app into application.yml.
  2. Create an AppProperties record with @ConfigurationProperties and validation, and inject it into a service.
  3. Add dev and prod profiles with different log levels and a different EmailSender bean; run with each and confirm which one is used.
  4. Override the port three ways: YAML, environment variable, command-line argument. Confirm the precedence order.
  5. Make a required property missing and read the failure message Boot produces.
  6. Turn on org.hibernate.SQL logging — you will need it in lesson 8.
