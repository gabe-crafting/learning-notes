DTOs, layers and mapping

Where code goes, and why exposing your database entities over HTTP is a mistake you only make once.

The three layers

HTTP request
    ↓
@RestController      web concerns: routing, status codes, DTOs, validation
    ↓
@Service             business rules, orchestration, transactions
    ↓
@Repository          persistence only: queries, saves
    ↓
database

Dependencies point downward only. A repository must never call a service; a service must never know about HttpServletRequest. That one rule keeps the business logic testable without a web server or a database.

What belongs where

LayerYesNo
ControllerMap request → DTO, call one service method, choose the status code Business rules, entity objects, SQL, @Transactional
ServiceRules, validation beyond format, coordinating repositories, transactions, events HTTP types, JSON annotations
RepositoryQueries and persistenceBusiness decisions

Why DTOs

@Entity
public class User {
    @Id private Long id;
    private String email;
    private String passwordHash;        // ← would you like this in your API response?
    private String internalNotes;
    private boolean fraudFlag;
    @OneToMany private List<Order> orders;   // ← and every order, recursively?
}

@GetMapping("/{id}")
public User get(@PathVariable Long id) { return repository.findById(id).orElseThrow(); }

Four problems with returning the entity directly:

  1. Leaks data — password hashes, internal flags, other people's information.
  2. Leaks structure — renaming a column now breaks every client.
  3. Serialisation surprises — lazy associations trigger extra queries or blow up with LazyInitializationException; bidirectional relations recurse forever.
  4. Accepts too much — binding a request body straight onto an entity lets a caller set id, role or createdAt.

The shape to use instead

// what the client may send
public record CreateTaskRequest(
        @NotBlank @Size(max = 200) String title,
        @Size(max = 2000) String description,
        @FutureOrPresent LocalDate dueDate) { }

// what the client gets back
public record TaskResponse(
        Long id,
        String title,
        String description,
        boolean done,
        LocalDate dueDate,
        Instant createdAt) {

    public static TaskResponse from(Task task) {
        return new TaskResponse(task.getId(), task.getTitle(), task.getDescription(),
                                task.isDone(), task.getDueDate(), task.getCreatedAt());
    }
}

Records are ideal here: immutable, concise, and Jackson handles them natively.

Keep separate request and response types. They diverge quickly — the request has no id, the response has no password — and merging them produces a type full of fields that are meaningless half the time.

Mapping

By hand (start here)

@Service
public class TaskService {

    public TaskResponse create(CreateTaskRequest request) {
        Task task = new Task();
        task.setTitle(request.title());
        task.setDescription(request.description());
        task.setDueDate(request.dueDate());
        task.setCreatedAt(Instant.now(clock));

        return TaskResponse.from(repository.save(task));
    }
}

Explicit, debuggable, no magic. For a handful of entities this is genuinely fine, and it is what you should do while learning.

MapStruct, when there are many

@Mapper(componentModel = "spring")
public interface TaskMapper {
    TaskResponse toResponse(Task task);
    Task toEntity(CreateTaskRequest request);

    @Mapping(target = "id", ignore = true)
    void update(@MappingTarget Task task, UpdateTaskRequest request);
}

MapStruct generates the implementation at compile time — no reflection, and mistakes are compile errors. Prefer it to runtime mappers like ModelMapper, which fail silently and at the worst moment.

A service worth reading

@Service
@Transactional(readOnly = true)
public class TaskService {

    private final TaskRepository repository;
    private final Clock clock;

    public TaskService(TaskRepository repository, Clock clock) {
        this.repository = repository;
        this.clock = clock;
    }

    public List<TaskResponse> findAll(Boolean done) {
        List<Task> tasks = (done == null) ? repository.findAll() : repository.findByDone(done);
        return tasks.stream().map(TaskResponse::from).toList();
    }

    public TaskResponse findById(Long id) {
        return repository.findById(id)
                .map(TaskResponse::from)
                .orElseThrow(() -> new TaskNotFoundException(id));
    }

    @Transactional
    public TaskResponse complete(Long id) {
        Task task = repository.findById(id).orElseThrow(() -> new TaskNotFoundException(id));

        if (task.isDone()) {
            throw new TaskAlreadyCompletedException(id);      // a business rule, in the service
        }
        task.setDone(true);
        task.setCompletedAt(Instant.now(clock));

        return TaskResponse.from(task);       // no explicit save needed inside a transaction
    }
}

Notice: the service speaks DTOs outward and entities inward, owns the rules, and never mentions HTTP.

Where should validation live?

  • Format and shape — @NotBlank, @Email, @Size — on the request DTO, checked by @Valid in the controller. Cheap, declarative, returns 400.
  • Business rules — "the due date must be after the project start", "a completed task cannot be reopened" — in the service, as exceptions. These need other data to decide, so they cannot be annotations.
  • Invariants — "an amount is never negative" — in the domain object's constructor, so the object cannot exist in a broken state.

Package by feature

com.example.tasks
├── task
│   ├── TaskController.java
│   ├── TaskService.java
│   ├── TaskRepository.java
│   ├── Task.java                 entity
│   └── dto/
│       ├── CreateTaskRequest.java
│       └── TaskResponse.java
├── user
└── common
    ├── GlobalExceptionHandler.java
    └── config/

Everything about tasks lives together, so a change touches one folder. This scales better than controller/, service/, repository/ packages, where every feature is smeared across the tree. Either way, be consistent with whatever the codebase already does.

Anti-patterns to avoid

  • Anaemic controllers with fat everything else is fine; fat controllers are not.
  • Service calling service calling service in a deep chain — it usually means the boundaries are wrong.
  • Repository injected into a controller to "save a layer". The day you need a rule, it is in the wrong place.
  • One TaskDto reused for create, update and response, full of nulls.
  • Static utility classes holding business logic — untestable and un-injectable.
Practice
  1. Take the controller from lesson 5 and introduce CreateTaskRequest, UpdateTaskRequest and TaskResponse.
  2. Move every rule out of the controller into a service, leaving the controller three lines per method.
  3. Add a field to your entity that must never be exposed and confirm it does not appear in the JSON.
  4. Write a from(Task) factory on the response record, then try MapStruct and compare.
  5. Reorganise the project by feature and note how many folders a "add a field to Task" change now touches.
