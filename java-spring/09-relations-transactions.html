Relations and transactions

Where JPA gets subtle: associations between entities, the N+1 problem, and what @Transactional really does.

Many-to-one and one-to-many

@Entity
public class Task {

    @Id @GeneratedValue private Long id;
    private String title;

    @ManyToOne(fetch = FetchType.LAZY)          // ALWAYS lazy on @ManyToOne
    @JoinColumn(name = "project_id", nullable = false)
    private Project project;                     // the foreign key lives here — the owning side
}

@Entity
public class Project {

    @Id @GeneratedValue private Long id;
    private String name;

    @OneToMany(mappedBy = "project", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Task> tasks = new ArrayList<>();   // the inverse side

    public void addTask(Task task) {             // keep both sides in sync yourself
        tasks.add(task);
        task.setProject(this);
    }

    public void removeTask(Task task) {
        tasks.remove(task);
        task.setProject(null);
    }
}

mappedBy says "the other side owns this relationship". Only the owning side's column is written; if you set only the inverse side, nothing is saved. That is why the helper methods above exist.

Fetch types

LAZYLoad on first access. Default for collections; set it explicitly on @ManyToOne and @OneToOne, whose default is EAGER.
EAGERLoad immediately, always, whether you need it or not. It quietly turns one query into several and is very hard to undo later.

Rule: everything lazy, then fetch what you need explicitly per query.

Many-to-many

@ManyToMany
@JoinTable(name = "task_tags",
           joinColumns = @JoinColumn(name = "task_id"),
           inverseJoinColumns = @JoinColumn(name = "tag_id"))
private Set<Tag> tags = new HashSet<>();

Use a Set, not a List. And the moment the relationship needs an attribute of its own — a date added, a role, a quantity — replace it with an explicit join entity and two @ManyToOnes. That happens more often than not.

The N+1 problem

List<Task> tasks = repository.findAll();          // 1 query
for (Task t : tasks) {
    System.out.println(t.getProject().getName());  // 1 query per task → 101 queries for 100 tasks
}

This is the single most common performance bug in Spring applications, and it is invisible until you look at the SQL log. Fixes:

// 1. join fetch in a query
@Query("select t from Task t join fetch t.project where t.status = :status")
List<Task> findByStatusWithProject(@Param("status") TaskStatus status);

// 2. an entity graph
@EntityGraph(attributePaths = {"project", "tags"})
List<Task> findByStatus(TaskStatus status);

// 3. batch fetching, globally
spring.jpa.properties.hibernate.default_batch_fetch_size: 50

// 4. do not load the association at all — project into a DTO with just the fields you need
How to catch it Turn on org.hibernate.SQL: DEBUG, call the endpoint once, and count the queries in the log. If the number grows with the number of rows, you have an N+1.

LazyInitializationException

// service returns the entity, transaction ends
// then Jackson serialises it and touches task.getProject()
// → LazyInitializationException: could not initialize proxy - no Session

The clean fix is the one from lesson 6: never return entities from a controller. Map to a DTO inside the transaction, where the data is still reachable.

spring:
  jpa:
    open-in-view: false      # set this. It is true by default and hides the problem

open-in-view=true keeps the persistence session open for the whole request, so lazy loading "works" — from the view layer, one query at a time, outside any transaction. Turning it off makes the problem visible where it belongs.

Transactions

@Service
@Transactional(readOnly = true)              // sensible class-level default
public class TransferService {

    @Transactional                            // read-write for this method
    public void transfer(Long fromId, Long toId, BigDecimal amount) {
        Account from = accounts.findById(fromId).orElseThrow();
        Account to   = accounts.findById(toId).orElseThrow();

        from.withdraw(amount);
        to.deposit(amount);
        // both succeed or both are rolled back
    }
}

A transaction is atomic: every write inside it commits together, or none does. Spring starts one when a @Transactional method is entered from outside the bean, commits on normal return, and rolls back on an unchecked exception.

Rollback rules

@Transactional                                   // rolls back on RuntimeException and Error
@Transactional(rollbackFor = Exception.class)     // ...also on checked exceptions
@Transactional(noRollbackFor = NotFoundException.class)

By default a checked exception does not roll back. That default surprises everyone exactly once.

Propagation

REQUIRED (default)Join the caller's transaction, or start one
REQUIRES_NEWSuspend the caller's and run in a fresh one — useful for audit rows that must survive a rollback
SUPPORTS, MANDATORY, NEVER, NESTEDRarer; look them up when you meet one
Self-invocation does nothing 
@Service
public class TaskService {
    public void a() { b(); }                 // b() runs with NO transaction
    @Transactional public void b() { ... }
}
The annotation is implemented by a proxy around the bean. An internal call never leaves the object, so the proxy is not involved. Move the method to another bean, or inject the bean into itself (ugly). The same applies to @Async, @Cacheable and @PreAuthorize.

Where to put it

On the service — the layer that defines a unit of business work. Not on the controller (which would hold a transaction open across serialisation), and not on the repository (which would make every save its own transaction, defeating atomicity).

Keep them short

@Transactional
public void placeOrder(OrderRequest request) {
    Order order = repository.save(new Order(request));
    paymentGateway.charge(order);          // ✗ an HTTP call inside a transaction:
                                           //   the database connection is held for its full duration
}

Do the external call outside the transaction, or record intent and process it afterwards. A connection pool is small; a slow third party can exhaust it and take the whole service down.

Concurrent updates

@Entity
public class Account {
    @Version private Long version;        // optimistic locking
}
// two users update the same row → the second gets OptimisticLockingFailureException
// catch it and either retry or tell the user the data changed
@Lock(LockModeType.PESSIMISTIC_WRITE)     // a real database lock; use sparingly
@Query("select a from Account a where a.id = :id")
Optional<Account> findByIdForUpdate(@Param("id") Long id);

Optimistic locking is the right default for web applications: no locks held between requests, and conflicts are rare and detectable.

Cascades

cascade = CascadeType.ALL        // PERSIST, MERGE, REMOVE, REFRESH, DETACH
orphanRemoval = true            // removing a child from the collection deletes the row

Cascade from parent to genuinely owned children (a project owns its tasks). Never cascade REMOVE to something shared — deleting a task should not delete the tag.

Practice
  1. Add Project with a one-to-many to Task, including the sync helper methods.
  2. Reproduce an N+1: list tasks with their project name, count the queries, then fix it with join fetch and confirm the count drops.
  3. Set open-in-view: false, trigger a LazyInitializationException, and fix it by mapping to a DTO inside the service.
  4. Write a transfer method across two entities and prove atomicity by throwing halfway through.
  5. Throw a checked exception in a transactional method and observe that the change is committed. Then fix it with rollbackFor.
  6. Add @Version and simulate a concurrent update from two threads.
