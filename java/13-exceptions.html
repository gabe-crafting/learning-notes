Exceptions

How Java reports that something went wrong, and how to handle it without hiding the problem.

The hierarchy

Throwable
├── Error                       serious JVM problems — do not catch
│   ├── OutOfMemoryError
│   └── StackOverflowError
└── Exception
    ├── RuntimeException        UNCHECKED — compiler does not force handling
    │   ├── NullPointerException
    │   ├── IllegalArgumentException
    │   ├── IllegalStateException
    │   ├── IndexOutOfBoundsException
    │   ├── NumberFormatException
    │   └── ArithmeticException
    ├── IOException             CHECKED — must be caught or declared
    ├── SQLException
    └── (your own)

Checked versus unchecked

CheckedUnchecked (RuntimeException)
CompilerForces catch or throwsSays nothing
MeansAn expected failure of the outside worldA bug, or invalid use of your API
ExamplesFile missing, network down, SQL errorNull reference, bad index, invalid argument

Modern Java code — and Spring in particular — leans heavily on unchecked exceptions, because forcing every caller to handle every failure produces layers of pointless wrapping. Use checked exceptions when the caller can realistically recover; use unchecked ones for programming errors and unrecoverable conditions.

try / catch / finally

try {
    int result = Integer.parseInt(input);
    System.out.println(100 / result);
} catch (NumberFormatException e) {
    System.out.println("Not a number: " + input);
} catch (ArithmeticException e) {
    System.out.println("Division by zero");
} finally {
    System.out.println("Always runs — success, failure or return");
}

Catch blocks are tried in order, so list specific types before general ones. Multi-catch handles several the same way:

catch (NumberFormatException | ArithmeticException e) {
    log.warn("Bad input: {}", e.getMessage());
}

try-with-resources

// anything implementing AutoCloseable is closed automatically, in reverse order
try (BufferedReader reader = Files.newBufferedReader(path);
     Connection conn = dataSource.getConnection()) {

    return reader.readLine();

} catch (IOException e) {
    throw new UncheckedIOException(e);
}

Always prefer this to closing in finally — it is shorter and it handles the case where close() itself throws.

throw and throws

public void setAge(int age) {
    if (age < 0) {
        throw new IllegalArgumentException("Age cannot be negative: " + age);   // throw = raise it now
    }
    this.age = age;
}

public String readConfig(Path path) throws IOException {   // throws = I do not handle this
    return Files.readString(path);
}

Custom exceptions

public class InsufficientFundsException extends RuntimeException {

    private final BigDecimal shortfall;

    public InsufficientFundsException(BigDecimal shortfall) {
        super("Insufficient funds: short by " + shortfall);
        this.shortfall = shortfall;
    }

    public BigDecimal getShortfall() { return shortfall; }
}

Write one when callers need to distinguish this failure from others. Give it the data needed to react — a shortfall, an id, a field name. Extend RuntimeException unless you deliberately want the compiler to force handling.

Preserving the cause

try {
    return repository.load(id);
} catch (SQLException e) {
    throw new DataAccessException("Could not load user " + id, e);   // pass e as the cause!
}
Never drop the cause throw new DataAccessException("failed") without the original exception throws away the stack trace that says what actually happened. Debugging that is guesswork.

Anti-patterns

// 1. Swallowing
try { risky(); } catch (Exception e) { }              // failure becomes invisible

// 2. Printing and continuing as if nothing happened
try { risky(); } catch (Exception e) { e.printStackTrace(); }

// 3. Catching Exception (or Throwable) indiscriminately
try { risky(); } catch (Exception e) { ... }          // also catches bugs you wanted to see

// 4. Control flow by exception
try { return list.get(i); } catch (IndexOutOfBoundsException e) { return null; }

// 5. Losing the message
throw new RuntimeException();                          // says nothing to whoever reads the log

What good handling looks like:

try {
    return paymentGateway.charge(request);
} catch (GatewayTimeoutException e) {
    log.warn("Payment gateway timed out for order {}", order.id(), e);
    return PaymentResult.retryLater();
}

Catch what you can actually do something about; let everything else travel up to a layer that can decide. In a web application that layer is usually a single global handler (Spring's @RestControllerAdvice) that turns exceptions into HTTP responses.

Reading a stack trace

Exception in thread "main" java.lang.NullPointerException:
        Cannot invoke "String.length()" because "name" is null
    at com.example.UserService.validate(UserService.java:42)     ← where it was thrown
    at com.example.UserService.register(UserService.java:28)     ← who called that
    at com.example.Main.main(Main.java:12)                       ← the entry point
Caused by: java.sql.SQLException: connection refused             ← the real culprit
    at ...

Read top line for what, first line of your own package for where, and always scroll to "Caused by" — the root cause is at the bottom.

finally and return

static int tricky() {
    try {
        return 1;
    } finally {
        System.out.println("finally still runs");   // prints, then 1 is returned
    }
}

Never return from a finally block: it discards any exception in flight and silently changes the result.

Validation helpers

Objects.requireNonNull(order, "order must not be null");

if (amount <= 0) throw new IllegalArgumentException("amount must be positive");   // bad argument
if (!isOpen)     throw new IllegalStateException("Account is closed");            // wrong state
if (found == null) throw new NoSuchElementException("No user with id " + id);

Fail fast, at the boundary, with a message that names the offending value. The cost of a good exception message is ten seconds now and hours saved at 3am.

Practice
  1. Write parseAge(String) that returns an int and throws IllegalArgumentException with a helpful message for null, non-numeric and negative input. Test all three.
  2. Create InsufficientFundsException and use it in a withdraw method; catch it in main and print a user-friendly message.
  3. Read a file with try-with-resources, handling NoSuchFileException differently from other IOExceptions.
  4. Deliberately cause a NullPointerException three levels deep and practise reading the stack trace.
  5. Find an example of a swallowed exception (write one), then fix it and explain what the fix makes visible.
