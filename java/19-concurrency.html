Concurrency basics

You will rarely start threads by hand as a junior — but your Spring controllers run on many threads at once, so understanding shared state is not optional.

Why this matters even if you never write a thread

A web server handles each request on a thread from a pool. Every @Service bean is shared by all of them. If a service keeps mutable state in a field, two requests can corrupt it. Most concurrency bugs juniors ship are exactly this: state where it should not be.

Threads

Thread t = new Thread(() -> System.out.println("running in " + Thread.currentThread().getName()));
t.start();          // starts a new thread — calling t.run() would just run it here
t.join();           // wait for it to finish

Thread.sleep(1000); // pause the current thread, throws InterruptedException

Threads are expensive (about 1 MB of stack each). Do not create them per task — use a pool.

Executors: the practical API

ExecutorService pool = Executors.newFixedThreadPool(4);

pool.submit(() -> doWork());                       // fire and forget

Future<Integer> future = pool.submit(() -> compute());
Integer result = future.get();                     // blocks until ready

List<Future<String>> results = pool.invokeAll(tasks);

pool.shutdown();                                   // no new tasks; finish the queue
pool.awaitTermination(30, TimeUnit.SECONDS);
// Java 21: a thread per task, but virtual threads — cheap enough for millions
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (var url : urls) {
        executor.submit(() -> fetch(url));
    }
}   // close() waits for all tasks

Virtual threads (Java 21) make blocking I/O cheap again, which is why Spring Boot 3.2+ can run every request on one.

The race condition

class Counter {
    private int count = 0;
    public void increment() { count++; }     // NOT atomic: read, add, write
    public int get() { return count; }
}

Counter c = new Counter();
// 1000 increments from each of 10 threads
// expected 10000, actual: something less, differently each run

count++ is three operations. Two threads can read the same value, both add one, and both write back the same result — one increment vanishes.

Fixes, from best to heaviest

// 1. Do not share mutable state at all — the best fix
//    local variables are per-thread and always safe

// 2. Atomic types for simple counters
AtomicInteger count = new AtomicInteger();
count.incrementAndGet();
count.addAndGet(5);
count.compareAndSet(expected, updated);

// 3. Concurrent collections
Map<String, Integer> map = new ConcurrentHashMap<>();
map.merge(key, 1, Integer::sum);            // atomic

// 4. synchronized — one thread at a time
public synchronized void increment() { count++; }

private final Object lock = new Object();
void update() {
    synchronized (lock) { ... }             // narrower critical section
}

// 5. Explicit locks when you need timeouts or fairness
private final ReentrantLock lock = new ReentrantLock();
lock.lock();
try { ... } finally { lock.unlock(); }      // ALWAYS unlock in finally

volatile and visibility

private volatile boolean running = true;     // writes are visible to other threads immediately

public void stop() { running = false; }
public void run()  { while (running) { ... } }   // without volatile this may loop forever

volatile guarantees visibility, not atomicity. It fixes the flag above; it does not fix count++.

Immutability is the real answer

public record Money(String currency, BigDecimal amount) { }   // immutable = thread-safe by construction

An object that cannot change cannot be corrupted by concurrent access. Records, List.of(...), String and java.time types are all safe to share freely. Design for that first, reach for locks last.

CompletableFuture

CompletableFuture<String> future = CompletableFuture
        .supplyAsync(() -> fetchUser(id))               // runs on the common pool
        .thenApply(User::name)                           // transform
        .thenCompose(name -> lookupProfileAsync(name))   // chain another async call
        .exceptionally(ex -> "unknown");                 // handle failure

String result = future.join();                            // block for the result

// run several in parallel and wait for all
CompletableFuture.allOf(f1, f2, f3).join();

Useful when a request needs three independent downstream calls: issue them together instead of one after another.

Deadlock

// thread 1: synchronized (a) { synchronized (b) { ... } }
// thread 2: synchronized (b) { synchronized (a) { ... } }
// both wait forever

Prevention: acquire locks in a consistent global order, hold them for as short a time as possible, and prefer lock-free structures.

Rules of thumb for application code

  • Spring beans (@Service, @Repository, @Component) are singletons shared by all requests. Keep their fields final and immutable — dependencies only, never per-request state.
  • Pass per-request data as method parameters.
  • Use ConcurrentHashMap for shared caches; HashMap corrupts under concurrent writes and has historically been able to spin forever.
  • Do not call Thread.sleep in request handling to "wait for" something.
  • If you find yourself writing synchronized in a controller or service, stop and ask why state is shared at all.
  • Database transactions, not Java locks, are how you coordinate across multiple application instances.

Debugging concurrency

jps                       # list running JVMs and their pids
jstack <pid>              # dump all thread stacks — shows deadlocks and stuck threads
log.info("handled on {}", Thread.currentThread().getName());

Concurrency bugs are timing-dependent, so they hide during testing and appear under load. Run a suspect test in a loop hundreds of times before believing it is fixed.

Practice
  1. Write the broken counter: 10 threads × 1000 increments. Run it five times and record the results.
  2. Fix it three ways — AtomicInteger, synchronized, and by not sharing state — and compare.
  3. Use a fixed thread pool to fetch five URLs (or simulate with Thread.sleep) and measure the total time against doing it sequentially.
  4. Chain two CompletableFutures where the second depends on the first, and add an exceptionally handler.
  5. Write a deliberate deadlock, take a jstack dump, and find where it says "Found one Java-level deadlock".
