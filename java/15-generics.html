Generics

Type parameters let one piece of code work with many types while the compiler still checks every use. You have been consuming them since List<String>; now write them.

The problem they solve

// before generics (Java 1.4 and earlier)
List names = new ArrayList();
names.add("Ada");
names.add(42);                          // compiles happily
String s = (String) names.get(1);       // ClassCastException at runtime

// with generics
List<String> names = new ArrayList<>();
names.add("Ada");
names.add(42);                          // compile error — caught immediately
String s = names.get(0);                // no cast needed

Two wins: mistakes move from runtime to compile time, and casts disappear.

Generic classes

public class Box<T> {
    private T content;

    public void put(T content) { this.content = content; }
    public T get()             { return content; }
    public boolean isEmpty()   { return content == null; }
}

Box<String> sb = new Box<>();
sb.put("hello");
String value = sb.get();          // typed, no cast

Box<Integer> ib = new Box<>();
ib.put("hello");                  // compile error

The diamond <> on the right-hand side means "infer it from the left". Conventional parameter names: T type, E element, K/V key/value, R result, N number.

Several parameters

public class Pair<K, V> {
    private final K key;
    private final V value;

    public Pair(K key, V value) { this.key = key; this.value = value; }
    public K key()   { return key; }
    public V value() { return value; }
}

var p = new Pair<String, Integer>("age", 36);

// in modern Java a record is usually better:
record Pair<K, V>(K key, V value) { }

Generic methods

public static <T> List<T> repeat(T item, int times) {   // <T> before the return type
    List<T> result = new ArrayList<>();
    for (int i = 0; i < times; i++) result.add(item);
    return result;
}

List<String> hellos = repeat("hi", 3);       // T inferred as String
List<Integer> zeros  = repeat(0, 5);

public static <T> void swap(T[] array, int i, int j) {
    T tmp = array[i]; array[i] = array[j]; array[j] = tmp;
}

Bounded type parameters

public static <T extends Number> double sum(List<T> numbers) {
    double total = 0;
    for (T n : numbers) total += n.doubleValue();   // allowed: T is a Number
    return total;
}

sum(List.of(1, 2, 3));          // fine
sum(List.of("a", "b"));         // compile error
public static <T extends Comparable<T>> T max(List<T> items) {
    T best = items.get(0);
    for (T item : items) if (item.compareTo(best) > 0) best = item;
    return best;
}

// multiple bounds: one class (first) and any number of interfaces
public static <T extends Number & Comparable<T>> T clamp(T v, T lo, T hi) { ... }

Note that extends here means "is a subtype of", and works for interfaces too.

Generics are not covariant

List<String> strings = new ArrayList<>();
List<Object> objects = strings;      // compile error, even though String is an Object

If that were allowed, someone could objects.add(42) and your List<String> would contain an Integer. Arrays are covariant, which is exactly why they can throw ArrayStoreException at runtime. Generics chose compile-time safety instead.

Wildcards

void printAll(List<?> items) {                 // unknown type: read as Object, cannot add
    for (Object o : items) System.out.println(o);
}

double sum(List<? extends Number> numbers) {   // upper bound: PRODUCER — you read Numbers
    double total = 0;
    for (Number n : numbers) total += n.doubleValue();
    return total;
    // numbers.add(1) would not compile: the actual type might be List<Double>
}

void addNumbers(List<? super Integer> target) { // lower bound: CONSUMER — you write Integers
    target.add(1);
    target.add(2);
    // reading gives you Object
}
PECS Producer Extends, Consumer Super. If the parameter produces values for you to read, use ? extends T. If it consumes values you write into it, use ? super T. If it does both, use plain T.

You will meet this constantly in the standard library:

Collections.copy(List<? super T> dest, List<? extends T> src);
Stream<R> map(Function<? super T, ? extends R> mapper);

Type erasure and its consequences

Generics exist only at compile time; the bytecode keeps no type arguments. List<String> and List<Integer> are the same class at runtime. That explains several limitations:

list instanceof List<String>      // illegal — the information is gone
T item = new T();                  // illegal — cannot instantiate a type parameter
T[] array = new T[10];             // illegal — use (T[]) new Object[10] with @SuppressWarnings
static T field;                     // illegal — static members cannot use the class's T

void handle(List<String> l) { }
void handle(List<Integer> l) { }   // illegal — same erased signature

Workaround when you truly need the runtime type: pass a Class<T> token.

public static <T> T parse(String json, Class<T> type) { ... }
Order o = parse(body, Order.class);

Generic interfaces you already use

public interface Repository<T, ID> {          // exactly the shape Spring Data uses
    Optional<T> findById(ID id);
    List<T> findAll();
    T save(T entity);
    void deleteById(ID id);
}

public class UserRepository implements Repository<User, Long> {
    @Override public Optional<User> findById(Long id) { ... }
    ...
}

When you later write interface UserRepository extends JpaRepository<User, Long> in Spring, this is all that is happening.

Raw types and warnings

List raw = new ArrayList();       // raw type: generics switched off, unchecked warnings
raw.add("anything");

Raw types exist only for compatibility with pre-2004 code. Never write one. Do not sprinkle @SuppressWarnings("unchecked") to silence the compiler either — if you must use it, keep it on the narrowest possible scope and add a comment explaining why the cast is safe.

Practice
  1. Write a generic Stack<T> with push, pop, peek and isEmpty, throwing on an empty pop.
  2. Write <T> List<T> firstN(List<T> list, int n) that returns at most the first n elements.
  3. Write <T extends Comparable<T>> T max(List<T>) and use it on strings, integers and your own Comparable class.
  4. Write a method that copies from a List<? extends T> into a List<? super T> and explain each wildcard.
  5. Try to write new T() inside a generic class, read the error, then implement the same thing with a Supplier<T> parameter.
