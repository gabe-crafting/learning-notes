Testing with JUnit 5

Writing tests is not an advanced topic — it is part of writing the code. Teams expect a junior to deliver features with tests, not features plus a promise.

Setup

<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>5.10.2</version>
    <scope>test</scope>
</dependency>

Tests live in src/test/java, mirroring the package of the class under test. mvn test runs them; so does the green arrow in your IDE.

A first test

package com.example;

import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

class CalculatorTest {

    @Test
    void addsTwoPositiveNumbers() {
        Calculator calc = new Calculator();      // arrange

        int result = calc.add(2, 3);             // act

        assertEquals(5, result);                 // assert
    }
}

Arrange, act, assert — keep the three phases visible and each test focused on one behaviour. Test classes and methods are package-private by convention; no public needed in JUnit 5.

Naming

@Test void withdrawFailsWhenBalanceIsInsufficient() { ... }
@Test void returnsEmptyOptionalWhenUserDoesNotExist() { ... }

@Test
@DisplayName("withdrawing more than the balance throws InsufficientFundsException")
void withdrawTooMuch() { ... }

The name should say what behaviour is expected. When a build fails at 2am, the test name is the error message.

Assertions

assertEquals(expected, actual);
assertEquals(expected, actual, "orders should match");   // message shown on failure
assertNotEquals(a, b);
assertTrue(condition);   assertFalse(condition);
assertNull(x);           assertNotNull(x);
assertSame(a, b);                       // same object reference
assertArrayEquals(expected, actual);
assertIterableEquals(list1, list2);

// exceptions
InsufficientFundsException ex = assertThrows(
        InsufficientFundsException.class,
        () -> account.withdraw(1000));
assertEquals("short by 500", ex.getMessage());

assertDoesNotThrow(() -> service.run());

// group: all run, all failures reported together
assertAll("order",
    () -> assertEquals("A-1", order.id()),
    () -> assertEquals(2, order.items().size()),
    () -> assertTrue(order.total().compareTo(BigDecimal.ZERO) > 0));

// timeouts
assertTimeout(Duration.ofMillis(500), () -> service.fast());

Note the argument order: expected first, actual second. Reversing it produces confusing failure messages.

AssertJ (worth adopting)

import static org.assertj.core.api.Assertions.assertThat;

assertThat(result).isEqualTo(5);
assertThat(names).hasSize(3).contains("Ada").doesNotContain("Bob");
assertThat(order.total()).isEqualByComparingTo("29.99");
assertThat(user).extracting(User::email).isEqualTo("a@b.com");
assertThatThrownBy(() -> account.withdraw(1000))
        .isInstanceOf(InsufficientFundsException.class)
        .hasMessageContaining("short by");

Fluent, readable, and its failure messages are far more informative. Spring Boot's test starter includes it.

Lifecycle

class OrderServiceTest {

    private OrderService service;

    @BeforeEach void setUp()      { service = new OrderService(new InMemoryRepo()); }
    @AfterEach  void tearDown()   { /* clean up */ }

    @BeforeAll static void once() { /* expensive, shared setup */ }
    @AfterAll  static void done() { }
}

A fresh test instance is created for every test method, so tests cannot leak state into each other — provided you do not use static mutable fields.

Parameterised tests

@ParameterizedTest
@ValueSource(strings = {"", "  ", "\t"})
void blankInputIsRejected(String input) {
    assertThrows(IllegalArgumentException.class, () -> new Product(input, 10));
}

@ParameterizedTest
@CsvSource({
    "2, 3, 5",
    "0, 0, 0",
    "-1, 1, 0"
})
void addsCorrectly(int a, int b, int expected) {
    assertEquals(expected, calculator.add(a, b));
}

@ParameterizedTest
@EnumSource(Status.class)
void everyStatusHasALabel(Status status) {
    assertNotNull(status.label());
}

Other useful annotations

@Disabled("flaky — see TICKET-123")     // never leave one without a reason
@Nested class WhenAccountIsClosed { }   // group related tests, with their own @BeforeEach
@Tag("slow")                            // filter which tests run
@RepeatedTest(100)                      // hunting an intermittent failure

Test doubles and Mockito

<dependency>
    <groupId>org.mockito</groupId>
    <artifactId>mockito-junit-jupiter</artifactId>
    <version>5.12.0</version>
    <scope>test</scope>
</dependency>
@ExtendWith(MockitoExtension.class)
class CheckoutServiceTest {

    @Mock  PaymentGateway gateway;          // a fake collaborator
    @Mock  OrderRepository repository;
    @InjectMocks CheckoutService service;   // constructed with the mocks above

    @Test
    void chargesTheCustomerAndSavesTheOrder() {
        Order order = new Order("A-1", new BigDecimal("29.99"));
        when(gateway.charge(any(), any())).thenReturn(PaymentResult.success("tx-1"));

        service.checkout(order);

        verify(gateway).charge("A-1", new BigDecimal("29.99"));
        verify(repository).save(order);
        verifyNoMoreInteractions(gateway);
    }

    @Test
    void propagatesGatewayFailure() {
        when(gateway.charge(any(), any())).thenThrow(new GatewayException("down"));

        assertThrows(CheckoutFailedException.class, () -> service.checkout(order));
    }
}

Mock the things you do not control or that are slow (gateways, repositories, clocks). Do not mock the class you are testing, and do not mock value objects — just create them.

What to test

  • Business rules — discounts, validation, state transitions. This is where bugs cost money.
  • Edge cases — empty, null, zero, negative, maximum, duplicate, out of order.
  • Bugs you fix — write the failing test first, then fix it. It never comes back silently.

Do not test getters, framework behaviour, or implementation details that will change with every refactor. Aim for tests that survive refactoring: assert on behaviour, not on how it was achieved.

The test pyramid Many fast unit tests, fewer integration tests that involve the database or HTTP layer, very few end-to-end tests. Inverting it produces a slow, flaky suite that nobody trusts. Spring's testing tools for the middle layer are in the Spring course.

Test-driven development, in one loop

1. Red    — write a failing test that states what you want
2. Green  — write the simplest code that passes
3. Refactor — clean it up with the test protecting you
   repeat

You do not have to work this way all the time. But doing it for a tricky algorithm or a bug fix is genuinely faster than debugging afterwards.

Coverage

JaCoCo reports the percentage of code executed by tests. Useful for spotting untested areas; useless as a target — 100% coverage with no assertions proves nothing. Look at what is not covered, not at the number.

Practice
  1. Write tests for a Calculator: addition, division, and division by zero throwing.
  2. Test a BankAccount: deposit, withdrawal, insufficient funds, negative amounts rejected.
  3. Convert three similar tests into one @ParameterizedTest with @CsvSource.
  4. Write a service that depends on an interface, then test it with a hand-written fake and again with a Mockito mock. Which did you prefer, and why?
  5. Find a bug in code you wrote earlier. Write the failing test first, then fix it.
  6. Run mvn test from the terminal and read the surefire report in target/.
