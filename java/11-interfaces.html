Interfaces and abstract classes

Interfaces are how Java code stays swappable and testable. If you understand this lesson, Spring will make sense later.

An interface is a contract

public interface PaymentProcessor {
    boolean charge(String customerId, double amount);   // public abstract by default
    void refund(String transactionId);
}
public class StripeProcessor implements PaymentProcessor {
    @Override
    public boolean charge(String customerId, double amount) { ... }

    @Override
    public void refund(String transactionId) { ... }
}

public class FakeProcessor implements PaymentProcessor {   // for tests
    @Override public boolean charge(String c, double a) { return true; }
    @Override public void refund(String t) { }
}

A class must implement every method of every interface it declares, or be abstract itself.

Why bother

public class CheckoutService {
    private final PaymentProcessor processor;      // depends on the contract...

    public CheckoutService(PaymentProcessor processor) {
        this.processor = processor;                // ...not on any implementation
    }

    public void checkout(Order order) {
        processor.charge(order.customerId(), order.total());
    }
}

new CheckoutService(new StripeProcessor());   // production
new CheckoutService(new FakeProcessor());     // test — no network, instant

Three payoffs: you can swap implementations, you can test without the real dependency, and code that depends only on interfaces does not recompile or break when an implementation changes. This is exactly what Spring automates with dependency injection.

Multiple interfaces

public interface Readable  { String read(); }
public interface Writable  { void write(String data); }
public interface Closeable { void close(); }

public class FileHandler implements Readable, Writable, Closeable {
    @Override public String read() { ... }
    @Override public void write(String data) { ... }
    @Override public void close() { ... }
}

One extends, many implements. Interfaces can also extend other interfaces, including several at once.

What an interface may contain

public interface Validator {

    boolean isValid(String input);                   // abstract — the contract

    default String describe() {                      // Java 8+: inherited implementation
        return "Validator: " + getClass().getSimpleName();
    }

    static Validator notEmpty() {                    // static factory, called on the interface
        return input -> input != null && !input.isBlank();
    }

    int MAX_LENGTH = 255;                            // implicitly public static final

    private boolean helper(String s) { return s != null; }   // Java 9+: private helper
}

default methods exist so a library can add a method to an interface without breaking every existing implementation — that is how Collection.stream() was introduced. Use them sparingly in your own code.

Interface versus abstract class

InterfaceAbstract class
How manyA class can implement manyA class can extend only one
StateNo instance fields (constants only)Fields, including mutable ones
ConstructorsNoneYes (called via super)
Methodsabstract, default, static, privateAnything, including protected helpers
Expresses"can do" — a capability"is a" — a partial implementation

Practical guidance: start with an interface. Reach for an abstract class only when several implementations genuinely share fields and code — and even then, consider putting the shared code in a separate collaborator instead.

Implementing standard interfaces

Comparable — natural ordering

public class Product implements Comparable<Product> {
    private final String name;
    private final double price;

    @Override
    public int compareTo(Product other) {
        return Double.compare(this.price, other.price);   // negative, 0, positive
    }
}

List<Product> products = new ArrayList<>(...);
Collections.sort(products);        // uses compareTo
products.sort(null);               // same thing

Comparator — any other ordering

products.sort(Comparator.comparing(Product::getName));
products.sort(Comparator.comparingDouble(Product::getPrice).reversed());
products.sort(Comparator.comparing(Product::getCategory)
                        .thenComparing(Product::getName));

AutoCloseable — try-with-resources

public class Connection implements AutoCloseable {
    @Override public void close() { System.out.println("closed"); }
}

try (Connection c = new Connection()) {
    // use c
}   // close() runs automatically, even if an exception is thrown

Functional interfaces

An interface with exactly one abstract method can be implemented by a lambda — the basis of lesson 16.

@FunctionalInterface
public interface Transformer {
    String transform(String input);
}

Transformer upper = s -> s.toUpperCase();          // lambda
Transformer trim  = String::strip;                 // method reference
System.out.println(upper.transform("hello"));      // HELLO

The standard library already provides the ones you usually need: Function<T,R>, Predicate<T>, Consumer<T>, Supplier<T>, Runnable, Comparator<T>.

Anonymous classes

PaymentProcessor stub = new PaymentProcessor() {   // an unnamed one-off implementation
    @Override public boolean charge(String c, double a) { return true; }
    @Override public void refund(String t) { }
};

Still useful when an interface has more than one method (a lambda cannot be used then). For single-method interfaces, a lambda is shorter and clearer.

Programming to the interface

List<String> names = new ArrayList<>();     // declare the interface type
Map<String, Integer> counts = new HashMap<>();

public List<Order> findAll() { ... }        // return the interface
public void process(Collection<Order> orders) { ... }  // accept the widest type you can use

Widening the parameter type and narrowing the return type is the habit that keeps code flexible.

Practice
  1. Define a Notifier interface with send(String message), implement it as EmailNotifier and SmsNotifier, and write a service that takes one in its constructor.
  2. Write a Shape interface with area() and a default describe(), then implement two shapes.
  3. Make a Student class Comparable by grade, then sort a list three different ways with comparators.
  4. Implement AutoCloseable on a fake resource and prove that close() runs when an exception is thrown inside the try block.
  5. Replace an anonymous class with a lambda in one of your examples and note what the compiler required.
