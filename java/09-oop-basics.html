Classes and objects

The core of Java: bundling data with the behaviour that operates on it, and controlling who can touch what.

Class versus object

A class is the blueprint; an object (instance) is a thing built from it. One BankAccount class, thousands of accounts.

public class BankAccount {
    private String owner;        // fields = the state each object carries
    private double balance;

    public BankAccount(String owner) {   // constructor
        this.owner = owner;
        this.balance = 0;
    }

    public void deposit(double amount) { // behaviour
        if (amount <= 0) throw new IllegalArgumentException("Deposit must be positive");
        balance += amount;
    }

    public double getBalance() {
        return balance;
    }
}
BankAccount acc = new BankAccount("Ada");
acc.deposit(100);
System.out.println(acc.getBalance());   // 100.0

new allocates the object on the heap, runs the constructor, and returns a reference to it.

Fields

public class Product {
    private String name;              // instance field: one per object
    private double price;
    private boolean available = true; // fields DO get a default (unlike locals)

    public static int totalProducts;  // static field: one for the whole class
    public static final double VAT = 0.19;  // constant
}

Instance fields describe an individual object. Static fields describe the class itself — counters, caches, constants. Mutable static state is a frequent source of bugs; keep it to constants.

Constructors

public class Product {
    private final String name;
    private final double price;
    private int stock;

    public Product(String name, double price) {   // main constructor
        if (name == null || name.isBlank()) throw new IllegalArgumentException("name required");
        if (price < 0) throw new IllegalArgumentException("price must be >= 0");
        this.name = name;
        this.price = price;
        this.stock = 0;
    }

    public Product(String name) {     // overloaded, delegates with this(...)
        this(name, 0);
    }
}
  • Same name as the class, no return type.
  • If you write no constructor, Java gives you a no-argument one. Write one yourself and that gift disappears.
  • this(...) calls another constructor and must be the first statement.
  • Validate in the constructor so an object can never exist in an invalid state.

Rule of thumb: fields private, methods as private as they can be. Making a field public means every caller can put your object into an invalid state and you can never change its representation.

Getters and setters

public String getName()  { return name; }
public boolean isActive() { return active; }   // booleans use "is"

public void setStock(int stock) {
    if (stock < 0) throw new IllegalArgumentException("stock cannot be negative");
    this.stock = stock;
}

Do not add a getter and setter for every field reflexively — that is just a public field with extra typing. Add accessors the class's users genuinely need, and prefer meaningful operations (account.withdraw(50)) over setBalance.

Defensive copies

public class Team {
    private final List<String> members;

    public Team(List<String> members) {
        this.members = new ArrayList<>(members);   // copy in
    }

    public List<String> getMembers() {
        return List.copyOf(members);               // unmodifiable copy out
    }
}

Without the copies, a caller holding the same list can mutate your object behind your back.

this

public class Point {
    private int x, y;

    public Point(int x, int y) {
        this.x = x;          // disambiguates field from parameter
        this.y = y;
    }

    public Point moveBy(int dx, int dy) {
        return new Point(this.x + dx, this.y + dy);
    }

    public boolean isSameAs(Point other) {
        return this == other;    // reference identity
    }
}

Object lifecycle and garbage collection

Product p = new Product("Book", 10);   // allocated on the heap
p = null;                              // nothing references it any more
// the garbage collector will free it eventually — you never do it yourself

There is no delete. Objects live as long as something reachable refers to them. "Memory leaks" in Java mean you accidentally kept a reference (typically in a static collection or a cache).

toString, equals and hashCode

public class Product {
    private final String sku;
    private final String name;

    @Override
    public String toString() {          // what println and logs show
        return "Product{sku='" + sku + "', name='" + name + "'}";
    }

    @Override
    public boolean equals(Object o) {   // value equality
        if (this == o) return true;
        if (!(o instanceof Product other)) return false;
        return sku.equals(other.sku);
    }

    @Override
    public int hashCode() {             // MUST agree with equals
        return Objects.hash(sku);
    }
}
The contract Equal objects must have equal hash codes. Override one and you override the other, or your objects will misbehave in HashMap and HashSet (lesson 14). Let the IDE generate both, or use a record (lesson 12), which writes all three for you.

Static methods, blocks and nested classes

public class MathUtils {
    private MathUtils() {}                  // utility class: prevent instantiation

    public static int square(int n) { return n * n; }
}

public class Config {
    private static final Map<String, String> DEFAULTS = new HashMap<>();
    static {                                // static initialiser: runs once, on class load
        DEFAULTS.put("timeout", "30");
    }
}

public class Order {
    private static class LineItem { ... }   // nested: only Order needs it
}

A worked example

public class Library {
    private final String name;
    private final List<Book> books = new ArrayList<>();

    public Library(String name) { this.name = name; }

    public void add(Book book) {
        Objects.requireNonNull(book, "book");
        books.add(book);
    }

    public Optional<Book> findByIsbn(String isbn) {
        for (Book b : books) {
            if (b.getIsbn().equals(isbn)) return Optional.of(b);
        }
        return Optional.empty();
    }

    public int size() { return books.size(); }
}

Notice what the class exposes: operations, not its internal list. That is encapsulation doing its job — the ArrayList could become a Map tomorrow without breaking a single caller.

Practice
  1. Model a BankAccount with deposit, withdraw (rejecting overdrafts) and a transaction history the caller cannot modify from outside.
  2. Write a Rectangle class with area(), perimeter(), isSquare() and a proper toString().
  3. Add a static counter to a class that reports how many instances have been created.
  4. Implement equals and hashCode on a Person keyed by national id, then put two "equal" people into a HashSet and confirm only one survives.
  5. Take any class you wrote earlier and make every field private final, moving validation into the constructor.
