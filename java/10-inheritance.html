Inheritance and polymorphism

How one class builds on another, and why "the same call does different things" is the point of object-oriented design.

extends

public class Employee {
    protected final String name;
    protected double baseSalary;

    public Employee(String name, double baseSalary) {
        this.name = name;
        this.baseSalary = baseSalary;
    }

    public double monthlyPay() {
        return baseSalary / 12;
    }

    public String describe() {
        return name + " earns " + monthlyPay();
    }
}

public class Manager extends Employee {
    private final double bonus;

    public Manager(String name, double baseSalary, double bonus) {
        super(name, baseSalary);      // must be the first statement
        this.bonus = bonus;
    }

    @Override
    public double monthlyPay() {      // overrides the parent version
        return super.monthlyPay() + bonus / 12;
    }
}

A subclass inherits every non-private member of its parent, can add its own, and can replace inherited behaviour by overriding. Java has single inheritance: one extends, but as many implements as you like (lesson 11).

Constructors and super

Constructing a Manager runs the Employee constructor first. If you do not call super(...) explicitly, Java inserts super() — and if the parent has no no-argument constructor, that is a compile error.

Object → Employee → Manager        // construction runs top-down along this chain

Overriding rules

@Override                     // not required, but always write it
public double monthlyPay() { ... }
  • Same name and parameter types (a different parameter list is overloading, not overriding — a classic silent bug that @Override catches).
  • Return type must be the same or a subtype.
  • Access cannot be narrowed: a public method cannot become protected.
  • Cannot throw broader checked exceptions.
  • private, static and final methods cannot be overridden.

Polymorphism

List<Employee> staff = List.of(
    new Employee("Ada", 60000),
    new Manager("Grace", 90000, 12000)
);

for (Employee e : staff) {
    System.out.println(e.monthlyPay());   // each object runs ITS OWN version
}

The variable's type (Employee) decides which methods you may call; the object's actual type decides which implementation runs. That decision happens at runtime — "dynamic dispatch". It is what lets you add a new subclass without touching the loop above.

Upcasting and downcasting

Employee e = new Manager("Grace", 90000, 12000);   // upcast: always safe
e.approveLeave();                                   // compile error: not on Employee

if (e instanceof Manager m) {      // pattern matching, Java 16+
    m.approveLeave();
}

Manager m2 = (Manager) e;          // explicit downcast
Employee other = new Employee("Ada", 50000);
Manager bad = (Manager) other;     // compiles, throws ClassCastException at runtime

Frequent downcasting usually means the design is wrong — the behaviour probably belongs on the parent type as an overridable method.

The Object class

Every class extends Object, directly or indirectly. That gives every object these:

toString()Text form. The default is useless (Product@1b6d3586) — override it.
equals(Object)Default is reference identity. Override for value equality.
hashCode()Must be overridden with equals.
getClass()Runtime type information.
clone(), finalize()Legacy; avoid both.
wait(), notify()Low-level threading (lesson 19).

final and sealed

public final class Money { ... }          // cannot be extended at all

public class Service {
    public final void run() { ... }        // cannot be overridden
}

public sealed class Shape permits Circle, Square { }   // Java 17+: a fixed set of subclasses

String, Integer and the other wrappers are final — that is what makes them safe to share.

When NOT to use inheritance

Inheritance is the tightest coupling in the language: the subclass depends on the parent's internals and breaks when they change. Use it only for a genuine "is-a" relationship where the subclass can stand in for the parent everywhere (the Liskov substitution principle).

Prefer composition:

// fragile: a Stack is not really a List, yet inherits add(), remove(int), etc.
public class Stack<T> extends ArrayList<T> { ... }

// solid: Stack HAS a list, and exposes only stack operations
public class Stack<T> {
    private final List<T> items = new ArrayList<>();

    public void push(T item) { items.add(item); }
    public T pop()           { return items.remove(items.size() - 1); }
    public boolean isEmpty() { return items.isEmpty(); }
}

In modern Java code — and in Spring especially — composition plus interfaces is the normal design, and deep class hierarchies are rare. A good default: inherit from abstractions, compose implementations.

An abstract base class

public abstract class Shape {
    public abstract double area();            // no body: subclasses must supply one

    public String summary() {                 // shared behaviour
        return getClass().getSimpleName() + " with area " + area();
    }
}

public class Circle extends Shape {
    private final double radius;
    public Circle(double radius) { this.radius = radius; }

    @Override public double area() { return Math.PI * radius * radius; }
}

An abstract class cannot be instantiated. It exists to hold behaviour shared by its subclasses while forcing them to fill in the parts only they know. Lesson 11 compares it with interfaces.

  2. Model Vehicle → Car, Motorcycle, Truck with an overridden describe(), and call it polymorphically.
  3. Override toString() on a subclass and have it reuse super.toString().
  4. Write a method taking an Employee that behaves differently for a Manager, first using instanceof, then redesign it so no instanceof is needed.
  5. Rewrite one of your inheritance examples using composition, and write down which version you would rather maintain and why.
