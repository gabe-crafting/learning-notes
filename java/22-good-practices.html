Junior developer practices

The parts of the job that are not the language: writing code others can read, working with git, debugging, and surviving code review.

Clean code, concretely

// names that carry information
int d;                          →  int daysSinceLastLogin;
List<User> list;                →  List<User> activeUsers;
void process(Order o);          →  void submitForFulfilment(Order order);
boolean flag;                   →  boolean eligibleForDiscount;

// no magic numbers
if (user.age() >= 18)           →  if (user.age() >= LEGAL_ADULT_AGE)
Thread.sleep(86400000);         →  Thread.sleep(Duration.ofDays(1).toMillis());

// comments explain WHY, not WHAT
// increment i
i++;
// the gateway rejects amounts below 1.00, so round up small charges
amount = amount.max(MINIMUM_CHARGE);
  • Small methods, one responsibility. If you need "and" to describe it, split it.
  • Fail fast. Validate arguments at the entry point of a class, not deep inside.
  • Immutability by default. final fields, records, defensive copies.
  • Don't repeat yourself — but don't over-abstract either. Two similar blocks are fine; three is a pattern worth extracting. Premature abstraction is harder to undo than duplication.
  • Delete dead code. Git remembers it; commented-out blocks just rot.
  • Consistent formatting. Whatever the team uses. Set the IDE to format on save.

Package structure

// by layer — common, fine for small services
com.example.shop
├── controller
├── service
├── repository
└── model

// by feature — scales better as the codebase grows
com.example.shop
├── order
│   ├── OrderController.java
│   ├── OrderService.java
│   └── OrderRepository.java
├── customer
└── shared

Either is defensible. Follow whatever the codebase already does — consistency beats your personal preference.

Git for daily work

git checkout -b feature/order-cancellation
# ... edit ...
git status                       # what changed
git diff                         # review before staging — always
git add -p                       # stage selectively, hunk by hunk
git commit -m "Add order cancellation with refund"
git push -u origin feature/order-cancellation

git pull --rebase origin main    # keep history linear
git log --oneline --graph -20

Commit messages

fix stuff                                        ✗
Add cancellation endpoint for pending orders     ✓

Add cancellation endpoint for pending orders     ✓✓

Orders can now be cancelled while still PENDING. Cancelling
issues a refund through the payment gateway and moves the
order to CANCELLED. Shipped orders are rejected with 409.

Closes #412

Imperative mood, a subject line under ~72 characters, and a body explaining why when it is not obvious. One logical change per commit — a commit that touches a feature, a refactor and a formatting pass is impossible to review or revert.

Pull requests and code review

Opening one: keep it small (a few hundred lines beats a thousand), describe what and why, say how you tested it, and review your own diff before asking anyone else. Self-review catches an embarrassing amount.

Receiving comments: they are about the code, not about you. Ask when you do not understand, push back with reasoning when you disagree, and say "good catch" when someone is right. Reply to every comment, even just "done".

Reviewing others: ask questions rather than issuing orders ("what happens if this list is empty?" beats "this is wrong"). Distinguish blocking issues from preferences, and approve when it is good enough — perfect is not the bar.

Debugging

  1. Read the error. The whole thing, including "Caused by" at the bottom. Most stack traces name the file and line.
  2. Reproduce it reliably. A bug you cannot trigger on demand is a bug you cannot verify fixed.
  3. Narrow it down. Binary search the code path: what is the last point where the data is still correct?
  4. Use the debugger. Breakpoints, step over/into, watch expressions, and conditional breakpoints (orderId.equals("A-1")) beat scattering print statements.
  5. Question your assumptions. The bug lives where you are certain there is no bug.
  6. Write a failing test that captures it, then fix it.

Asking for help well

✗ "It doesn't work, can you help?"

✓ "POST /orders returns 500 when the cart is empty. The stack trace says
   NullPointerException in OrderService:88 on cart.items(). I checked the
   request body and items is absent, so I think the DTO deserialises to null
   rather than an empty list. I tried adding @NotEmpty but the exception
   happens before validation. Is validation supposed to run before the service?"

Say what you expected, what happened, what you already tried, and what you think is going on. Time-box your struggling — 30 to 60 minutes stuck is the point to ask, not day three.

Security basics you are expected to know

  • Never concatenate SQL. Use parameters — WHERE id = ? — or you have written an injection vulnerability.
  • Never log secrets — passwords, tokens, card numbers, full personal data.
  • Never commit credentials. Environment variables or a secret manager; add .env to .gitignore. If you do commit one, rotate it — deleting the commit is not enough.
  • Hash passwords with bcrypt or Argon2, never MD5 or SHA-256 alone.
  • Validate all input at the boundary — anything from a client is hostile until checked.
  • Keep dependencies updated; known vulnerabilities are the most common real-world breach.

Performance, in the right order

  1. Make it correct.
  2. Make it clear.
  3. Measure — profile, time it, look at the query count.
  4. Only then optimise the thing the measurement pointed at.

In web applications the answer is almost never Java-level micro-optimisation. It is a missing database index, an N+1 query, or a call in a loop that should have been one batch call.

Reading a codebase you did not write

Start at an entry point (a controller, a main) and follow one request all the way down. Use "find usages" more than "read every file". Run the tests — they document intent. Change something small and see what breaks; that tells you where the load-bearing walls are.

A junior's checklist before opening a PR

  • Does it compile and do all tests pass locally?
  • Did I add tests for the new behaviour and for the edge cases?
  • Did I read my own diff line by line?
  • Any leftover System.out.println, TODO, or commented-out code?
  • Are names clear enough that a reviewer will not have to ask?
  • Does the error handling do something useful, or does it swallow?
  • Have I updated the README or docs if the behaviour changed?

Where to go next

  • The Spring course — the framework you will actually be hired to use.
  • SQL. Not optional. Joins, indexes, transactions, and reading an execution plan.
  • HTTP and REST. Status codes, methods, headers, idempotency, caching.
  • Docker. Enough to run a database locally and containerise your app.
  • Books worth the time: Effective Java (Bloch) once you are comfortable; The Pragmatic Programmer for the craft.
  • Practice: build something real that you use. A finished small project teaches more than fifty tutorials.
Practice
  1. Take your oldest exercise from this course and refactor it: better names, smaller methods, no magic numbers, tests added.
  2. Make three commits with well-written messages and read back git log — would a stranger understand the change?
  3. Review a pull request in an open-source project and write one useful comment.
  4. Use the debugger — not print statements — to find the value of a variable three calls deep.
  5. Write a README for one of your projects: what it does, how to run it, how to test it.
