Maven, Gradle and packaging

How a Java project declares its dependencies, gets compiled the same way on every machine, and turns into something you can actually run.

What a build tool does

  • Downloads dependencies (and their dependencies) from a repository.
  • Compiles source into target/classes with the right classpath.
  • Runs tests and fails the build when they fail.
  • Packages a jar, with a reproducible result on any machine or CI server.

Maven is the most common in enterprise Java and is what Spring Initializr defaults to. Gradle is common in newer projects and Android. Learn Maven first; Gradle's concepts map onto it.

pom.xml

<project xmlns="http://maven.apache.org/POM/4.0.0">
    <modelVersion>4.0.0</modelVersion>

    <groupId>com.example</groupId>        <!-- your organisation -->
    <artifactId>shop-api</artifactId>     <!-- the project name -->
    <version>1.0.0-SNAPSHOT</version>     <!-- SNAPSHOT = still in development -->
    <packaging>jar</packaging>

    <properties>
        <maven.compiler.release>21</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>

    <dependencies>
        <dependency>
            <groupId>com.fasterxml.jackson.core</groupId>
            <artifactId>jackson-databind</artifactId>
            <version>2.17.1</version>
        </dependency>
        <dependency>
            <groupId>org.junit.jupiter</groupId>
            <artifactId>junit-jupiter</artifactId>
            <version>5.10.2</version>
            <scope>test</scope>
        </dependency>
    </dependencies>
</project>

Those three coordinates — groupId : artifactId : version — identify every Java library in existence. Search them on Maven Central.

Scopes

compile (default)Needed everywhere, packaged into the artifact
providedNeeded to compile, supplied at runtime by the container
runtimeNot needed to compile — JDBC drivers, for example
testOnly for tests; never shipped

The lifecycle

mvn clean          # delete target/
mvn compile        # compile main sources
mvn test           # compile and run tests
mvn package        # build the jar (runs test first)
mvn verify         # run integration tests and checks
mvn install        # copy the artifact into your local ~/.m2 repository

mvn clean package                 # the command you will type most often
mvn test -Dtest=OrderServiceTest  # a single test class
mvn package -DskipTests           # skip tests (compiles them); -Dmaven.test.skip skips compiling too
mvn dependency:tree               # show the full dependency graph
mvn versions:display-dependency-updates

Phases run in order: asking for package runs everything before it. Dependencies are cached in ~/.m2/repository; the first build downloads a lot, later ones are fast.

Transitive dependencies and conflicts

Your dependencies bring their own. When two versions of the same library appear, Maven picks the one nearest the root of the tree — which is sometimes not the one you want.

mvn dependency:tree -Dincludes=com.google.guava
<dependency>
    <groupId>com.example</groupId>
    <artifactId>some-lib</artifactId>
    <version>1.0</version>
    <exclusions>
        <exclusion>
            <groupId>commons-logging</groupId>
            <artifactId>commons-logging</artifactId>
        </exclusion>
    </exclusions>
</dependency>

NoSuchMethodError at runtime almost always means two versions of a library are on the classpath. The dependency tree is where you look.

dependencyManagement and parents

<dependencyManagement>
    <dependencies>
        <dependency>                        <!-- version declared once, inherited by modules -->
            <groupId>org.junit</groupId>
            <artifactId>junit-bom</artifactId>
            <version>5.10.2</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

This is exactly what spring-boot-starter-parent does for you in the next course: it pins consistent versions for hundreds of libraries so you can omit <version> entirely.

Building a runnable jar

A plain mvn package jar contains only your classes — running it fails as soon as it needs a dependency. Two solutions:

<!-- 1. Shade plugin: bundle everything into one "fat jar" -->
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-shade-plugin</artifactId>
    <version>3.5.3</version>
    <executions>
        <execution>
            <phase>package</phase>
            <goals><goal>shade</goal></goals>
            <configuration>
                <transformers>
                    <transformer implementation="org.apache.maven.plugins.shade.resource.ManifestResourceTransformer">
                        <mainClass>com.example.Main</mainClass>
                    </transformer>
                </transformers>
            </configuration>
        </execution>
    </executions>
</plugin>
java -jar target/shop-api-1.0.0-SNAPSHOT.jar

2. In Spring Boot you get this for free — spring-boot-maven-plugin builds an executable jar with an embedded web server.

Gradle, for orientation

plugins {
    id 'java'
}

group = 'com.example'
version = '1.0.0-SNAPSHOT'

java {
    toolchain { languageVersion = JavaLanguageVersion.of(21) }
}

repositories { mavenCentral() }

dependencies {
    implementation 'com.fasterxml.jackson.core:jackson-databind:2.17.1'
    testImplementation 'org.junit.jupiter:junit-jupiter:5.10.2'
}

test { useJUnitPlatform() }
./gradlew build       # always use the wrapper, not a locally installed gradle
./gradlew test
./gradlew bootRun

Same ideas, terser syntax, faster incremental builds, and a build script that is real code — which is both its strength and its risk.

The wrapper

./mvnw clean package        # Linux / macOS
mvnw.cmd clean package      # Windows

The wrapper scripts and their .mvn/ folder are committed to git so that everyone — including the CI server — builds with the same tool version. Use them when a project provides them.

Semantic versioning

MAJOR.MINOR.PATCH        e.g. 2.7.3
MAJOR — incompatible API changes
MINOR — new features, backwards compatible
PATCH — bug fixes
-SNAPSHOT — a moving development version, re-downloaded regularly
Practice
  1. Create a Maven project from scratch by writing pom.xml by hand — no IDE wizard — and compile it.
  2. Add Jackson and JUnit, write one class that serialises an object and one test for it, and run mvn clean package.
  3. Run mvn dependency:tree and identify one transitive dependency you never asked for.
  4. Configure the shade plugin and run your app with java -jar.
  5. Break the build on purpose by making a test fail, and confirm that mvn package refuses to produce a jar.
  6. Convert the same project to Gradle and compare the two build files.
