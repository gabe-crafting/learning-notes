Tooling and project setup

Get a JDK installed, an IDE that helps rather than hides, and a project layout that matches what every Java team uses.

Installing a JDK

"Java" downloads are confusing because several vendors ship the same OpenJDK code. Any of these is fine and free for commercial use:

  • Eclipse Temurin (adoptium.net) — the safe default.
  • Amazon Corretto, Microsoft Build of OpenJDK, Azul Zulu — same thing, different vendor support.
  • Oracle JDK — has licence conditions that vary by version; most teams avoid the question entirely by using Temurin.

On Windows the simplest route is a package manager:

winget install EclipseAdoptium.Temurin.21.JDK

Then open a new terminal and check:

java -version
javac -version

If java works but javac does not, you installed a JRE rather than a JDK.

Managing several versions

Real work often means one project on Java 17 and another on 21. Tools that switch for you: SDKMAN! (Linux/macOS/WSL) and jenv. On Windows, setting JAVA_HOME per project or letting your IDE point at a specific JDK is usually enough.

echo $JAVA_HOME        # bash / WSL
$env:JAVA_HOME         # PowerShell

JAVA_HOME points at the JDK folder (not bin). Maven, Gradle and many scripts read it.

The standard project layout

Maven defined it, Gradle adopted it, and effectively every Java project now uses it:

my-app/
├── pom.xml                                  build file (or build.gradle)
├── src/
│   ├── main/
│   │   ├── java/com/example/app/Main.java   production code
│   │   └── resources/application.properties non-code files
│   └── test/
│       ├── java/com/example/app/MainTest.java  tests
│       └── resources/                          test-only files
└── target/                                  build output (never committed)

Two rules follow from it: the package com.example.app must live in folders com/example/app, and anything under resources ends up on the classpath, readable at runtime.

Creating a project

You will use Maven properly in lesson 21; for now, this is enough to generate a skeleton:

mvn archetype:generate -DgroupId=com.example -DartifactId=my-app \
    -DarchetypeArtifactId=maven-archetype-quickstart -DinteractiveMode=false
cd my-app
mvn compile          # compile into target/classes
mvn test             # compile and run tests
mvn package          # build a jar in target/

Or simply let the IDE do it: New Project → Java → Maven. Do it by hand once anyway, so you know what the IDE generated.

jshell: a scratchpad for the language

Trying out a snippet does not need a class or a main. Java ships a REPL:

$ jshell
jshell> int x = 21
x ==> 21
jshell> "hello".toUpperCase()
$2 ==> "HELLO"
jshell> /exit

Use it constantly while working through the next few lessons — it removes all ceremony from experimenting.

The classpath, briefly

The JVM does not scan your disk for classes; it looks along the classpath, a list of folders and jars.

java -cp target/classes com.example.app.Main
java -cp "target/classes;libs/*" com.example.app.Main   # Windows separator is ;  (Linux/macOS use :)

"ClassNotFoundException" and "NoClassDefFoundError" almost always mean the classpath is missing something. Build tools construct it for you, which is most of why they exist.

Version control from the start

Initialise git in the project and ignore build output:

git init
printf 'target/\n*.class\n.idea/\n*.iml\n' > .gitignore
git add . && git commit -m "Initial project skeleton"
Practice
  1. Install a JDK 21 and confirm both java -version and javac -version work in a fresh terminal.
  2. Create a Maven project called playground, put a Main class in package com.example.playground, and run it from the IDE and from the command line.
  3. Open jshell and evaluate five expressions — some arithmetic, some string methods.
  4. Commit the project to git with a sensible .gitignore. Confirm target/ is not tracked.
